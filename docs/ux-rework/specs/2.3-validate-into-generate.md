## What is wrong today

- **A12 (major), B10 (major).** Generate stays disabled until the player presses Validate
  (`WorkflowBar.tsx:159-167`: `disabled={... || validationStatus !== 'valid'}`, tooltip "Validate the configuration
  first"). Any edit, even toggling the generation-only switch "Search for fewer wake-ups", makes the last Validate "out
  of date" (`App.tsx:194-198`, a key comparison over the whole config) and turns Generate off again. The newcomer cannot tell
  why there are two buttons; the expert pays Configure, find the row, edit, Validate, Generate for every tweak (shots 17,
  18, 27).
- **Validate yanks the page.** `handleValidate` (`App.tsx:204-209`) switches to Configure and smooth-scrolls to the
  Validation panel at the very bottom of the page, away from the row that was being edited (B10).
- **The Transfer Plan and "Exclude from LCM" sit on the main path.** They live in the Validation card
  (`ValidationPanel.tsx`), a full-size panel under every build. A newcomer reads a table of fractions that they cannot
  act on (A12 asks to move it to an expert section).
- **What the check is.** `validate` in `useSimulationWorker.ts:353-363` posts `{ type: 'validate' }`; the worker answers
  `validated` or `validation-failed` (`worker/simulation.worker.ts:176-186`), which runs the engine's `validateConfig`
  (`clock-generator/src/crafting/plan/validate-config.ts`): the inserter-coverage assertion, one prepare run, the
  crafting-cycle plan and the transfer plan. It reads **no** generation-only setting (the engine reads
  `search_for_fewer_wake_ups` only in `alternatives.ts`/`rank.ts`, and `non_moving_belts` only in `clockOfPlan`,
  `alternatives.ts` and `rank.ts`, all after the plan). It is cheap next to a generation (one prepare run against hundreds
  of simulations), so running it at the front of every Generate is acceptable.

## Change

- **Generate checks first.** One press does everything:
  - the build has problems the form can name (1.4's `problemsOf`): switch to Configure, move focus to the first one
    (1.4's `focusProblemTarget`) and stop. Nothing is checked or generated.
  - otherwise it runs the check in the worker. The button reads "Checking...". If the check **fails**, the page switches to
    Configure and focuses the engine's message (an error alert at the top of Configure). If it **passes**, Generation
    starts and the page switches to Results, as Generate does today.
  - if the build is unchanged since a check that already passed, the check is skipped and Generation starts at once. If it
    is unchanged since a check that failed, the page goes to that error again without re-running it.
- **Generate is never greyed out by the build or by an edit.** It is off only while something is running (a check or a
  generation). So editing never disables it (B10), and a newcomer on an empty build can press it and be taken to the
  first thing to fill in (A12, and A6's "click it to go to the field"). 1.4's visible red text and "N problems" chip
  stay, as the explanation that the click will go there.
- **"Check only" replaces Validate.** An outlined secondary button next to Generate. It runs the same check and **never
  switches views or scrolls**. With problems it does not run: it only moves keyboard focus to the red text in the bar (no
  scroll), so the press is never silent. The result shows where the player is: a "Check passed" or "Check failed" chip in the
  bar (and 1.11's live announcement), the message in Configure, and the swing plan in Advanced.
- **No "Changed since validation" state any more.** Nothing needs the player to re-check, because Generate does. The
  out-of-date chip goes; a changed build just stops showing the "Check passed" chip.
- **Generation-only settings do not make a check out of date** (B10): turning "Search for fewer wake-ups" or the belt
  switch on or off keeps the last check valid. Everything else still does.
- **The Transfer Plan and "Exclude from LCM" move into Advanced Overrides,** right under the LCM Override and Force
  Output Swings fields. The old Validation card is deleted. The plan shows after any check (from Generate or Check only);
  before the first check it says so and offers its own "Check only" button; after an edit it is dimmed with a one-line
  note, as the card did.
- **Search deeper (1.7) goes through the same check.** One shared function runs "check, then start" for both buttons.
- **The "Generate again" in 1.1's banner, tooltip and dialog now holds.** After an edit, Generate is on and checks again
  by itself (PROGRESS follow-up "1.1 → 2.3").

### The decision, as a pure function

`decideGenerate` is the one place that says what pressing Generate does. First match wins.

| # | Input | Decision | What the page does |
|---|---|---|---|
| 1 | not initialized, or a generation is running, or a check is running | `wait` | nothing (the button is off) |
| 2 | `problems.length > 0` (1.4's `problemsOf`; a coverage answer still pending adds none) | `go-to-problem` with `problems[0]` | switch to Configure (and the List when `needsListView`), focus its target |
| 3 | `checkStatus === 'invalid'` (the last check failed for this exact build) | `go-to-check-error` | switch to Configure, focus `validation-error` |
| 4 | `checkStatus === 'valid'` (passed for this exact build) | `generate` | start Generation, switch to Results |
| 5 | `checkStatus` is `none` or `out-of-date` | `check-first` | run the check; then `afterCheck` below |

`decideCheckOnly` (the secondary button):

| # | Input | Decision | What the page does |
|---|---|---|---|
| 1 | not initialized, or a generation or check is running | `wait` | nothing |
| 2 | `problems.length > 0` | `show-problems` | focus the red text in the bar (`focusBarNote`), no scroll, no view change |
| 3 | otherwise | `check` | run the check; no view change, no scroll |

`afterCheck(outcome)` for `check-first`: `valid` -> `generate`; `invalid` -> `go-to-check-error`; `dropped` (Import, Paste or
Reset replaced the build, or a newer check took over) -> `stop`, silently.

`problems` includes coverage problems once `useInserterValidation` has answered. Before it has, `problemsOf` returns only
the target and machine problems and the engine's own check catches a missing inserter (its message goes to the
top-of-Configure alert). A coverage answer that is a moment behind an edit can send the player to a row they just fixed;
accepted (the window is one worker round trip), see Risks.

## Risks and checkpoints

- **No checkpoint tripped in the orchestrator's list.** The glossary is approved ("Check only" is in 1.12's row 10) and the item adds no
  dependency, no engine change, no CI change. Four design calls go beyond the plan's wording; **the orchestrator should confirm them

  1. **Generate is enabled even when the build has problems, and goes to the first one on press** (the owner's "stops on Configure at
     the first problem"). This replaces 1.4's disabled-with-a-reason model for Generate; 1.4's red text and chip stay. The alternative

  2. **The "Changed since validation" chip and the Validation card are deleted.** Nothing needs re-checking by hand now. 1.14's
     filled-yellow treatment of that chip disappears with it (the yellow stays for Copy and stale).
  3. **Generation-only switches do not invalidate a check** (B10 asks for this; the plan item does not say it). Small and tested.
  4. **The engine's reason for a failed check shows as an alert at the top of Configure,** not at the bottom in a card.
- **Duplicate work.** A Generate on a build never checked runs `validateConfig` and then the generation's own plan step, which repeats the
  prepare run. The capture prints the check time; if it is over about 5 seconds on the largest sample, report it as a follow-up (a
  future engine change could let the `plan` request reuse the check). Skipping the check when it already passed (`decideGenerate` row

- **Stale coverage answer.** `useInserterValidation` keeps the previous issues until the new answer arrives, so Generate pressed in the
  same instant as a fix can go to a row that was just fixed. One worker round trip; accepted. The fix, if the audit finds it, is to
  treat issues as pending after an edit (a `useInserterValidation` change, out of scope here).
