# 1.6 Make the clock pick explainable
Findings: A9, A11, B12, B14, C7  ·  Implementer model: opus  ·  Branch: feat/ux-rework-p1-recommended-clock

Line numbers are for `clock-generator-ui/src` at the head of `feat/ux-rework-p1` (2da8d1d), which does not have 1.1 yet.
1.1 merges first and shifts `useSimulationWorker.ts`, `App.tsx` and `ResultsWorkspace.tsx`: find the code by name. This

## What is wrong today

- **Nothing marks or explains the pick (A9, B12, C7).** `publishAlternatives` (`useSimulationWorker.ts:161-169`) selects
  `combined.selected_index` unless the player has picked (`userSelectionRef`, `:134`). The selected row only gets a
  filled radio and a tint (`ClockAlternativesPanel.tsx:149-155`). After the player picks another row, nothing says which
  row the tool recommended, because the recommendation is not stored anywhere: it is only the starting value of
  `selectedAlternativeIndex`.
- **The rule is buried (A11, C7).** `ClockAlternativesPanel.tsx:84-100` is one ~140-word paragraph. The rule is in its
  middle: "The one selected for you has the fewest wake-ups ... among those that hold the target rate and get back to it;
  a clock that leaves belt pickup slack out for a non-moving belt is only selected when no clock for a moving belt holds
  it. With 'Belts do not move' on every clock is made without the slack."
- **Unstable rows land in the middle (B14).** Rows are `alternatives` in engine order, filtered
  (`:73-75`). "Show N unstable clocks" (`:223-231`) puts them back between the stable ones and shifts the selected row.

## The selection rule (quoted, so the reason text can be built from it)

It lives in the engine: `clock-generator/src/crafting/rank.ts`, `combineClockAlternativeRuns` (`:110-149`), with the
inputs worked out by `rankingOf` (`:46-59`). The page already gets all of it on every clock as
`ClockAlternativeView.ranking` (`worker/types.ts:114`, copied in `simulation.worker.ts:106`). Each alternative is ranked
by this tuple, smaller wins, and of equals **the first listed** wins:

1. `meets_target_rate ? 0 : 1`. Meets the rate = the verdict is `stable` and the rate is within 1e-6 of the target.
   **On a build with a deadlock risk** (`deadlockRisk !== null`) "no recovery" counts as holding too (`rank.ts:49`),
   because the recovery trials do not see the deadlock.
2. If it does not meet the rate: how near it is, `round(|rate_off_target| * 1000)`; else 0.
3. If it does not meet the rate: `holds_expected_output ? 0 : 1` (verdict is not `unstable`); else 0.
4. `matches_belt_choice ? 0 : 1`. False for a clock made without belt pickup slack when the config does not say the
   belts stand still (`overrides.non_moving_belts`). A clock with a period that is not a whole number of ticks never
   gets the slack and counts as matching. With `non_moving_belts: true` every clock matches.
5. `round(wake_ups_per_minute * 1000)`; `null` (not counted) ranks after any count.
6. `window_count` (`ranking_window_count`: windows without the output feeders').

Plain words: **a clock that holds the rate and is made for your belt comes first; of those, the fewest wake-ups; then
the fewest windows; then the first listed.** If none holds the rate, the one nearest to it.

Two facts that matter for the design:
- The page can recompute the pick from the list alone, with the same function: `combineClockAlternativeRuns([{ signature:
  'x', alternatives }], it => it.ranking).selected_index` gives the engine's `selected_index` for the same list, since
  one run has nothing to de-duplicate. That is why the recommendation can be a pure function of `alternatives` and needs
  no state of its own to reset (see Decision 1).
- `alternatives` is a **streaming** list. `publishAlternatives` runs after the plan and after every task, and builds the
  list from `generation.runs` in a fixed task order, so a run that finishes late but sits earlier in the order is
  inserted **before** clocks already on screen. Indices therefore shift while a generation runs; ids do not
  (this is why `userSelectionRef` holds an id).

## Change

- **A "Recommended" chip on the tool's pick.** In the Clock column, next to the clock's name, a filled chip (primary
  colour, text "Recommended", not colour-only). It marks the clock the rule above picks, whichever row is selected.
- **A one-sentence reason above the table**, built from the rule and the run's settings, after the clock's name:
  "**Recommended: 3 output swings per cycle.** Fewest wake-ups among the clocks that hold 240/s on a moving belt."
  The reason varies with the inputs (table below).
- **"Back to recommended"** appears next to that sentence only while the selected clock is not the recommended one.
  It selects the recommended row, clears the player's pick (so the selection follows the recommendation again while
  clocks are still coming in), and puts the keyboard focus on the recommended row's radio.
- **The intro shrinks to one line plus a "How clocks are chosen" disclosure.** Line: "Each clock was tested in the
  simulator. Select a row to see its blueprint and timelines." The disclosure (MUI `Accordion`, collapsed) holds the
  rule in plain words and a "This run" line with the belt assumption and whether the slower searches ran.
- **Unstable rows go to the bottom under a divider.** The stable rows keep their order and never move when "Show N
  unstable clocks" is pressed. The unstable rows follow a labelled divider row ("Unstable clocks"). The recommended
  and the selected row are always shown, even when the rest of the unstable group is hidden.
- **Not changing:** the deadlock-risk alert, the "None of the clocks tried ..." notes (moved, text kept), the table
  columns and their headers (1.10 owns the units), the "Not searched" alert and everything below the table (1.7), the
  Workflow bar, and the engine.

### Decision 1: the recommended index is derived, not stored

`useSimulationWorker` gets `recommendedIndex`, computed by `useMemo` from `alternatives` with a pure function
(`recommendedIndexOf`, which wraps the engine's `combineClockAlternativeRuns`). The plan says "track the auto-picked
index separately from the selected one"; this does, and it cannot go out of date: `clearResults` (1.1) and
`runSimulation` empty `alternatives`, which makes it `null`, so nothing extra has to be reset. The selected index stays
what it is today (the player's pick by id, else the engine's pick). Storing the engine's `selected_index` in state
would also work but adds a thing for `clearResults` to forget.

### Decision 2: while a generation streams, the recommendation moves and the player's pick does not

- **Does the recommendation move?** Yes. It is the best of the clocks that have arrived, so it can change when a later
  clock beats it. The chip moves with it. While `isRunning` the reason line starts with "More clocks are still being
  made, so this may change." and the chip reads "Best so far" instead of "Recommended". When the run ends it turns into
  "Recommended" (no live region: nothing is announced on every update).
- **Does the player's pick survive?** Yes, as today: `userSelectionRef` holds the clock's id and `publishAlternatives`
  looks it up in each new list (`:163-165`), so an index shift does not move it. If the player picked a clock that is
  later dropped as a duplicate (an earlier-ordered run with the same windows arrived), the selection falls back to the
  recommendation, as today.
- **Selecting the recommended row is a pick like any other.** It pins that clock; if a better one arrives later, the
  chip moves away and "Back to recommended" appears. Only the link (`selectRecommended`) clears the pin.
- **Before the player has picked**, the selected clock follows the recommendation as it moves (today's behaviour, now
  stated). The selected row can therefore change while the table fills. Not new, and the alternative (freezing on the
  first clock) would select a worse clock.

## The reason text (a pure function, so 2.5's summary card can reuse it)

`recommendationReason(alternatives, recommendedIndex, rule, final)` returns the sentence after "Recommended: {label}.".
It reads only fields the view already has: the selected row's `ranking`, `verdict`, `beltLabel`, `assessment`, and the
other rows' `ranking` for ties. `rule` is `{ nonMovingBelts, searchedForFewerWakeUps }`, read from the config the
generation ran with. `rate` is the target, `assessment.items_per_second - ranking.rate_off_target`, printed like
`rateWarning.ts:36` does (`Number(x.toFixed(2)).toString()`: 240 prints "240", 12.5 prints "12.5", 0.333333 prints
"0.33").

"Contenders" = the clocks with `meets_target_rate && matches_belt_choice`, the ones the rule puts first. The belt phrase
(`B`) is: `rule.nonMovingBelts` → " with belts that stand still"; else `beltLabel` starts with "moving" → " on a moving
belt"; else (`beltLabel` is empty because no clocked inserter picks up from a belt, or the clock is a subtick clock made
without the slack) → nothing.

| Situation (from the rule's inputs) | Sentence (named constants; wording is draft until the glossary, 1.12) |
|---|---|
| The pick meets the rate, matches the belt, and has competition. The normal case | "Fewest wake-ups among the clocks that hold {rate}/s{B}." |
| Same, and other contenders tie it on wake-ups (equal to a thousandth) | the sentence above + " {n} other clock(s) tie on wake-ups, so the fewest inserter windows decided." If windows tie too: "... and on windows, so the first listed was chosen." |
| The pick is the only contender | "The only clock that holds {rate}/s{B}." |
| The pick's wake-ups were not counted (so none of the contenders') | "Fewest inserter windows among the clocks that hold {rate}/s{B}. Wake-ups could not be counted for them." |
| The pick meets the rate on a build with a deadlock risk and its verdict is "no recovery" | the first sentence above + " The recovery trials do not decide on this build." The existing deadlock alert says why |
| The pick meets the rate but does **not** match the belt (only possible with `nonMovingBelts` false) | "No clock made for a moving belt holds {rate}/s, so this one, made for belts that stand still, has the fewest wake-ups of those that do. It may fail on a moving belt." |
| No clock meets the rate | "No clock holds {rate}/s. This one runs nearest to it, at {its rate}/s." + if another clock is equally near (to a thousandth) and the pick holds its output while that one does not: " Of the equally near clocks, it is the one that holds its output from a clean start." |
| `final` is false (a generation is running) | "More clocks are still being made, so this may change. " in front of any of the above |
| `recommendedIndex` is null | empty string (the panel shows no line) |

How each input shows:
- **Belt assumption** (`overrides.non_moving_belts`, i.e. "Belts do not move"): changes `B`, and with it on the "does not
  match the belt" row cannot occur.
- **Search mode** (`overrides.search_for_fewer_wake_ups`): does **not** change the rule, only which clocks exist, so it
  does not change the sentence. It is stated in the disclosure's "This run" line: "The slower searches for fewer
  wake-ups were run." or "The slower searches were only run if no other clock was stable." This is also where 1.7's
  wording about a deeper search can link later. The "Not searched" alert stays untouched.
- **Rate held or not**: the two top-level branches (first four rows vs the "No clock holds" row).
- **Ties**: the tie rows; wake-ups are compared to a thousandth and windows exactly, as `rank.ts` does.

The disclosure body ("How clocks are chosen"), as named constants in the same file:
1. "Each clock is simulated driven only by its windows, starting at several points. One that holds the target rate is
   then tried for backpressure loss: each input stops arriving for a while and each output stops being taken away, and
   the build has to get back to its rate by itself. A clock that does all of that is Stable."
2. "The clock picked for you is the Stable one with the fewest wake-ups. If clocks tie, the one with fewer inserter
   windows. If none is Stable, the one that runs nearest to the target rate."
3. "A clock made for a moving belt keeps each belt inserter's window open a few ticks longer (belt pickup slack). A clock
   made without it is only picked when no clock for a moving belt holds the rate. With 'Belts do not move' on, every
   clock is made without the slack."
4. This run: "This run assumed {moving belts | belts that stand still}. {searches line}"
   (Item 2.4 will turn the belt assumption into a visible question and can add a link beside this line.)

The old text (`ClockAlternativesPanel.tsx:84-92`) is the source; keep its facts, and lose "(counted from one start of the
clock)" and "batched swings", which the column tooltips already say.

## Acceptance criteria

- [ ] After a generation finishes, exactly one row has a "Recommended" chip, and it is the row the engine selected
  (`rank.ts` `selected_index`) when the player has not picked anything (A9, B12, C7).
- [ ] The line above the table reads "Recommended: {that clock's label}. {reason}", and the reason matches the table
  for the run: default logistic science says "Fewest wake-ups among the clocks that hold 240/s on a moving belt."; the
  same build with `non_moving_belts: true` says "... with belts that stand still." (A9, A11).
- [ ] Selecting another row moves the radio and the tint, **not** the chip; "Back to recommended" appears next to the
  line. Pressing it selects the recommended row, hides the link, and leaves keyboard focus on that row's radio
  (B12).
- [ ] With the recommended row selected there is no "Back to recommended".
- [ ] The Potential Clocks intro is one line of at most 25 words. The old rule text is reachable under a collapsed
  "How clocks are chosen" disclosure that opens with Enter/Space and shows the run's belt and search settings (A11, C7).
  The line and the recommendation line are at most 72ch wide.
- [ ] Rows with a verdict other than Stable come after all Stable rows, under a labelled divider. "Show N unstable
  clocks" does not move any Stable row or the selected row (B14). With nothing Stable there is no divider.
- [ ] With the unstable rows hidden, the selected and the recommended row still show.
- [ ] While a generation is running: the chip reads "Best so far" and the reason starts with "More clocks are still being
  made". Select a row early; after the run ends that clock is still selected, and the chip is on the engine's pick, with
  "Back to recommended" showing if they differ.
- [ ] A new Generate, an Import, Paste or Reset (1.1's `clearResults`) leave no chip, no recommendation line, and no
  "Back to recommended" from the previous run.
- [ ] A build with a deadlock risk (utility science) keeps its alert and the reason says the recovery trials do not
  decide.
- [ ] Every user-visible string of this item is a named constant in `utils/recommendedClock.ts`.
- [ ] No new dependency; `npm test`, `npm run lint`, `npm run knip`, `npm run check:icons` and `npm run build` pass in
  `clock-generator-ui`. `clock-generator` is not touched.
