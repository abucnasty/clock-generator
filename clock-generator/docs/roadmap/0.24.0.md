# 0.24.0: ship faster

This is the plan for release 0.24.0: what it is for, its packages in order and what it leaves for later. It is kept while the release is in flight and dropped when 0.24.0 is released. Live status is on the Real Boy board, https://github.com/users/abucnasty/projects/2, item "0.24.0 · Ship Faster"; this page does not follow every merge. The milestones and follow-ups it names are in [ROADMAP.md](../ROADMAP.md).

## What the release is for

0.24.0 is about developer experience and a fast turnaround from an edit to a merged change, and nothing else. Checking a change of the generator takes long and a large build takes a lot of memory, so fewer checks run at once and each change waits for them. The release shortens that loop: less memory per run, a blast of the samples that takes minutes, a generation suite that CI runs in parallel, local test runs that are quick, and no check that covers what another already covers. The composition refactor, the graph and the planner follow in [0.25.0](0.25.0.md) and [0.26.0](0.26.0.md), where the shorter loop pays.

The start, measured before any change of the release: the blast of the samples 21 minutes, the generation suite in CI 7.6 minutes, and the peak memory of the processing-unit sample 3.28 GB. Times are for comparison with each other and depend on the machine.

Done means:

- Speed: the blast of the samples as built takes a few minutes; the generation suite in CI takes under about 4 minutes; the local `npm test` and the generation project are timed and the slowest files cut.
- Memory: the peak memory is low enough to run more checks at once; the parallel-runs package sets how much more from the measured peaks.
- Process: a change is pushed as a draft pull request as soon as its fast checks pass; checks run side by side; no coverage is duplicated.
- No regression: every sample's selected clock and verdict are unchanged unless a change says so.
- Measured once: memory and speed of the release candidate are compared with the start above. Individual changes are not timed.

Nothing of the generator's behaviour is meant to change, and the goals keep their order ([GOALS.md](../../GOALS.md)): goal 1, the clock meets its target exactly and recovers; goal 2, the fewest wake-ups. The one change of a result is the fix of `0.24/backed-refill`, stated per sample. Search-only changes keep every result identical. The time spent searching at generation does not grow ([working rules](../working-rules.md), rule 6).

Engine and UI are 0.24.0, each with one unreleased changelog entry.

## Packages, in order

Packages are named `0.24/<code>`. One engine change merges at a time.

### 1. Memory

**`0.24/memory`**, memory reduction, measured by spot checks. The known slow configurations and every science configuration are generated one at a time on the release and on master, and their time and peak memory compared; the times of a blast are not used, since they are noise. The count of simulated candidates for each job is stated beside them. Every step keeps the results identical: a full blast with no move and a comparison of the insights, descriptions and histories of all config jobs with master. In order:

- Transitions in typed columns. Per entity, the tick, the from and to status and the reason, about 10 bytes a transition against 64 to 72. The history is sealed once when the recorded run ends and shared by the memo, every trial and every alternative. The UI receives the columns with a table of reason texts, and the insights, timelines and hover texts read the same as before. Saved results are dropped when the schema version changes. Merged (#454): the peak memory of the processing-unit sample went from 3,282 to 960 MB.
- The memo keeps no simulation context (#462).
- Allocation churn, one change per allocator: the transfer tracker's snapshots during warm-up and the stock recorder's per-tick work. The other allocators found in the profile of agricultural science (37 GB allocated in 40 seconds) become part of the composition refactor's per-tick rules in [0.25.0](0.25.0.md), so they are not tuned before it removes them.
- Bounding the memo by bytes is skipped: the memo measures 155 MB against the 300 MB at which it would pay.

Done when every spot-check job takes less peak memory than on master and is no slower, with the figures per job.

### 2. Faster checks

**`0.24/blast`**, the blast of the samples as built. Clocks are generated only for the belt mode a sample is configured with, not for both; the recording is off; the slowest jobs run first so that the parallel processes finish together. Merged (#459): the blast went from 21 minutes to 2 minutes 51 seconds. The thaeln cell 09 sample is back in the blast (#463), at 22.6 seconds. A digest of the blast's results with the clock hashes, in the blast's scripts, makes one pass show what moved. Two small fixes go with it: the blast's exit code when it runs a subset only, and the stale references to the generation test files that were split. Done when the digest is in and the blast is timed once on the release candidate.

**`0.24/ci`**, the generation suite in CI in 8 shards, with the slow files split. Merged (#461): 7.6 to 3.7 minutes.

**`0.24/mechanics-unit-tests`**, fixture families as unit tests. The families of front entrance and exit, over the hood, belt pickup, blocked output and containers become mechanics unit tests, which take seconds and are pinned to the recorded figures. Their generation tests go, which cuts CI time. Done when each family's unit tests pass against the recorded figures and the generation tests they replace are removed, with nothing left uncovered.

**`0.24/local-tests`**, faster local test runs. The Vitest worker cap is raised from measured peaks, `npm test` and the generation project are timed locally, and the slowest files are cut: the container-output test takes one test and about 4 minutes in CI. Done when the local runs are timed before and after and the slowest files are cut or split.

### 3. Fixes

**`0.24/backed-refill`**, the backed-up window floor (#456). The refill of a backed-up belt is bounded by the belt's speed. A model correction: it is reported apart from the search-only changes, and any sample whose result moves is listed with the reason.

**`0.24/quick-wins`**, the open issues that are quick to fix. The open issues are triaged first, and the ones that take a few lines are fixed alongside the changes above. Done when the triage is written and each quick fix on it is made or dropped with a reason.

### 4. More parallel runs

**`0.24/parallel-runs`**, more parallel test runs, after the memory package. The blast's job count is set from the measured peaks, the guard cap is sized from them, per-job heap flags are used where they pay (they cut the peak of the processing-unit sample by 34% for about 10% more time), and the generation suite is timed again. Done when the blast and the suite run more jobs at once than at the start with no throttling and no out-of-memory stop.

### 5. The release candidate

Memory and speed are measured once against the start, with the blast, the generation suite in CI, the local tests and the spot checks of the memory package; then the checks and the pull request into master.

## Decisions before it starts

- `0.24/ci`: whether the blast runs in CI, sharded on GitHub runners as the generation tests are, so that it runs off the developer's machine; decided once `0.24/parallel-runs` shows how many blast jobs fit on one machine.
