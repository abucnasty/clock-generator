## What is wrong today

- After a generation, `ClockAlternativesPanel.tsx:215-221` shows an info `Alert`: "Not searched: Observed windows,
  Uneven output swings, Shifted swings and Full-hand output swings. A clock made without a search is stable, so the
  searches, which take most of the time of a generation, could only find one with fewer wake-ups. To run them, turn on
  "Search for fewer wake-ups" under Advanced Overrides and generate again." It lists four engine internals, reads like a
  failure (A22), is about 60 words (C27) and sends the player on a round trip to a switch in another view (B15).
- Where it comes from. The engine skips four "searches" (`crafting/alternatives.ts`: `onlyWhenNeeded` at :118-120,
  `generateClockAlternatives` at :551-600) when a clock made without a search can already be selected as stable
  (`searchesAreNeeded`), unless `config.overrides.search_for_fewer_wake_ups` is `true`. In the site this is decided in
  `useSimulationWorker.ts`: `dispatchTasks` (:171-195) puts the waiting searches in `generation.skipped`, and
  `publishAlternatives` (:161-169) copies their labels into the `skippedSearches` state (:132, returned at :383), which
  `App.tsx:490` passes to `ResultsWorkspace` (`:33`, `:97`) and on to the panel (`:56`, `:62`).
- The flag reaches the engine only through the config object: `runSimulation` (:312-334) stores `config` in the
  `Generation` and every worker message (`plan`, `task`) carries `generation.config`. So the site can run one
  generation with the flag on without touching the form. **No engine change is needed.**
- The only place to set the flag is the switch "Search for fewer wake-ups" in `OverridesForm.tsx:121-142` (form field
  `overrides.search_for_fewer_wake_ups`, set with `updateOverrides`, `App.tsx:140`, `:465`).
- Which build to try: `science/chemical-science/chemical-science.json` skips the searches by default (asserted in
  `clock-generator/src/crafting/search-when-needed.generation.test.ts`: batched swings is stable at 20.4 wake-ups a
  minute, and the shifted-swings search finds a stable clock at 10.1). The review's shot 20 (logistic science) also
  showed the notice. `science/automation-science` is the opposite: no clock without a search is stable, so the
  searches run and nothing is skipped.

## Change

- **The "Not searched" list is gone.** When searches were skipped, the panel shows an info alert with one line:
  "We stopped once we found a working clock. A deeper, slower search might find one with fewer wake-ups." and, on the
  right, a **Search deeper** button. Under the line is a checkbox "Keep it on for this build" with a short caption.
- **When it shows.** Only when at least one search was skipped (`skippedSearches.length > 0`), a generation is not
  running, and the results are not stale (1.1's `staleFor` is null). It never shows while the clocks are still being
  made, since the player cannot yet know whether the searches will be needed. While the results are stale, the 1.1
  banner already says to generate again, and a deeper search of a different build would not match the clocks on screen.
  When no search was skipped (they ran because they were needed, or the flag is on) the old alert is not replaced by
  anything about the offer.
- **Search deeper** generates for the build as it stands, with `search_for_fewer_wake_ups` on for this run only. It
  works like Generate: it clears the results, shows progress and the "computing…" rows, and stays on Results. The saved
  build, the form and the Advanced Overrides switch do not change.
- **Keep it on for this build** (checkbox, unchecked each time, not remembered between visits). When ticked, Search
  deeper also sets "Search for fewer wake-ups" in the form, which is saved with the build like any other setting, so
  every later Generate searches deeper too. Its caption: 'Turns on "Search for fewer wake-ups" in Advanced Overrides.'
- **What shows after a deeper run** (instead of the offer, same place and shape, no button):
  - one-run: "We searched deeper for this run. These clocks include the slower searches."
  - kept on (the form's switch is on): "Deeper search is on for this build. To stop it, turn off "Search for fewer
    wake-ups" under Advanced Overrides." This also shows after every normal Generate while the switch is on.
  - A normal Generate afterwards searches as before and shows the offer again if it skips (a one-run override does
    not stick).
- **No "found N fewer wake-ups" comparison.** The pick after a deeper run is simply the best of all the clocks
  (`selected_index` ranks the searches' clocks with the others), so whether it changed is visible in the table and the
  "Recommended" chip (1.6). A before/after comparison would need the previous run kept, which belongs to Phase 3
  ("keep the results"). Listed as a possible follow-up, not built here.

## The one-run override and 1.1's recorded key (resolved)

1.1 records, in `runSimulation`, `setGeneratedFor(generatedForOf(config))` where `config` is the argument, and shows the
"stale" banner when `generatedFor.key !== configKeyOf(exportConfig())`. If the one-run override were applied to that
`config`, its key would carry `search_for_fewer_wake_ups: true` while the form's would not, and the results would look
stale the moment they arrived. So:

- `runSimulation` gets a fourth parameter `searchDeeper = false`. It builds the config for the engine from the form's
  config and records the key of the **form's** config:
  ```
  const { engineConfig, generatedFor, searchedDeeper } = planGenerationRun(config, searchDeeper);
  setGeneratedFor(generatedFor);      // key of `config`, as the form exports it: no false "stale"
  setSearchedDeeper(searchedDeeper);
  ... generationRef.current = { runId, config: engineConfig, ... };
  worker.postMessage({ type: 'plan', runId, config: engineConfig, ... });
  ```
  `config` is used for nothing else in the function. (Everything downstream reads `generation.config`, so the whole run,
  the plan and every task, uses `engineConfig`.)
- **One run only:** `App` calls `runSimulation(exportConfig(), debugSteps, streamLogs, true)`. The key recorded is the
  form's, so nothing looks stale, and the form is untouched.
- **Keep it on:** the form does change, so the key must be the **new** form's key. `App` computes
  `const kept = withDeeperSearch(exportConfig())`, calls `updateOverrides('search_for_fewer_wake_ups', true)`, then
  `runSimulation(kept, debugSteps, streamLogs)` (flag already in `kept`, so `searchDeeper` stays false). `kept` is built
  with the same spread order as `edits.updateOverrides` + `formDataToConfig` (a new key goes last in `overrides`, an
  existing one keeps its place), so `configKeyOf(kept)` equals the key of the form once the state update lands, and the
  banner does not show. This equality is the one thing that can silently break the feature, so it has its own test.
  The state update is asynchronous, but `kept` is computed from the config in the click handler's closure, so the
  generation does not depend on it.
- **After the player later edits and generates again** nothing special happens: normal rules.
- Side effect, accepted: turning the flag on makes "Validate" out of date (`App.tsx:193`, key differs), so the "Changed
  since validation" chip appears after a "keep it on" run. It does today too when the switch is toggled by hand.

## Risks and checkpoints
- **No checkpoint is tripped.** No new dependency, no engine change, no CI, workflow or `.claude` change, nothing the
  plan contradicts. `skipped_searches` is already produced by the engine and reaches the UI; the flag already exists in
  the config schema (`clock-generator/src/config/schema.ts:470`).
- **Plan beats the reviews where they differ.** A22 says the button "turns on the setting and generates again" (a
  permanent change); B15 says generate with the flag for this run and offer to make it the default; C27 labels the button
  "Search for fewer wake-ups and generate". The plan (this run, plus an option to keep it on; label "Search deeper") is
  what this spec follows.
- **The key trap (see "The one-run override").** The failure to guard against is recording the engine config's key: the
  results would look stale right after a one-run deeper search. The tests above exist for that; the implementer should
  not "simplify" `runSimulation` back to a single `config`.
- **State that can go out of date.** `searchedDeeper` must be cleared by 1.1's `clearResults` and reset on every
  `runSimulation`; `keptOn` is the live form value and is only trusted when the results are not stale (the notice is
  hidden when they are).
- **Copy and the glossary (1.12).** "Wake-ups" is the glossary's term and the plan's own sentence; "clock" and "build" are
  used as elsewhere. If the owner's glossary changes any of them, the constants in `utils/deeperSearch.ts` are the only
  place to edit. The "Search for fewer wake-ups" switch label in `OverridesForm.tsx:141` is quoted in two strings; if 1.12
