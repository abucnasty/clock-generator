### Choices where the owner has a real decision

1. **What a wake-up is. The plan's definition does not match the number on screen.**
   - The plan says "wake-up: one start of a wake window". But the table's "Wake-ups (per min)" is computed in the engine
     (`clock-generator/src/crafting/wake-ups.ts`) as the game's own wake-ups: a machine finishing a craft wakes the
     enabled inserters waiting on it. A long window holds many wake-ups; a window can hold none. So a player who counts
     window starts would get different numbers.
   - Options: (a) the plan's wording; (b) the accurate one in the table above. Under (b) the wake window explains *why*
     the number falls: the clock keeps the inserter off between its wake windows, so there is no one to wake.
   - **Recommend (b).** The existing tooltip at `ClockAlternativesPanel.tsx:133` is already accurate; Part B only
     tightens it. Also keep "start" out of the vocabulary: the tooltips say "one start of the clock" for the *place in the
     period the clock starts at*, which must not read as "start of a window". Say "start point" there.
2. **Whether "hand" survives.** (a) Keep it for the load only ("hand size", "Hand Quantity", "a full hand"), swing for
   the trip. (b) Drop it everywhere (needs a replacement for "full-hand output swings", an engine search name).
   **Recommend (a).** It is Factorio's own word, and in the UI 4 of the 7 uses are the load already.
3. **Check or Validate, and when.** (a) Rename the button and chip now. (b) Keep "Validate" until 2.3 folds it into
   Generate and adds "Check only", and use "check" in sentences from now. **Recommend (b):** renaming twice in one phase
   is churn, and Part B fixes the one place where the sentence and the button disagree ("Re-run the simulation" becomes
   "Validate again", the button's name today).
4. **Enable control or enable rule.** Options: keep "Enable Control" (matches `enable_control` in the JSON and the
   review's screenshots); "Enable rule" (matches 1.8's "Discard changes to Inserter 3's rule?" and 1.13's "Enable:
   Auto"); "Switch-on rule". **Recommend "enable rule", "rule" for short**, and "override" only for Advanced Overrides.
   Mode labels (B32): **Auto, Always on, Never on, Clocked, Conditional**, each with a plain gloss, title case instead of
   the raw enum.
5. **Machine type label.** Options: "Assembler" (the dialog today), "Machine" (the list today, but it is also the generic
   word, so "Machine / Furnace / Biochamber" reads as machine vs machine), "Assembling machine" (the game's name; C30's
   proposal). **Recommend "Assembling machine"** in both places. The select grows (see Risks).
6. **Backpressure loss.** Options: keep (precise, jargon); "jam" ("recovers from a jam", the plan's 2.5 wording);
   "stall". **Recommend "jam"** in sentences, with the exact cause kept after the colon ("after coal stops arriving").
7. **Wake window.** The plan's term. Alternatives: "on window", "active window". **Recommend the plan's term**: it
   links to wake-up, and 2.6's "Wake windows" view already uses it. Revisit after the Phase 2 review if newcomers
   misread it.
8. **Clock vs "Copy old clock…".** 1.1 chose "Copy old clock…" for a button that copies a blueprint. Under the glossary
   a clock is the thing the tool makes and the blueprint is the string that carries it, so the shorthand is fine.
   Recommend keeping the plan's wording; flagging only so the owner knows it is a conscious shorthand.

### Engine text (decision for the owner, default: leave it)

Clock names, descriptions and the Insights prose are written in `clock-generator/src/crafting/` and shown as they
come: `alternatives.ts` (about 99 strings: 36 mention swings, 12 hands, 20 windows), `insights.ts` (about 125: 21 hands,

- Labels are identifiers. `generate-blueprint.generation.test.ts:104`, `clock-belt.generation.test.ts:46-180`,
  `agricultural-science.generation.test.ts:51`, `search-when-needed.generation.test.ts:9` and
  `metallurgic-science.generation.test.ts:35` assert them, `verify-recording.ts:25` accepts them on the command line,
  and `useSimulationWorker.ts:59` (`PRIMARY_STEP`) matches one by name. One insight title is asserted too
  (`output-swings.generation.test.ts:271`). The generation tests run only on PRs to `master`.
- 1.6 / 2.5 already plan to name clocks by trade-off in the UI ("Recommended", "Fewest wake-ups"), with the technical
  name as a second line, and to collapse the Insights prose behind "Why?".

Options: (A) leave engine text alone in 1.12 and let 2.5 rewrite what it keeps, with this glossary as its input;
(B) edit the prose now (engine change, generation tests to run with `gh workflow run`). **Recommend (A).** Under (A) the
UI still shows "hands" and "windows" in the Insights tab and in each clock's "How it is made" popover until 2.5; the
copy-check script reports those lines so nobody mistakes them for missed work.

### Where the glossary lives, and a Terms popover

- **In the code or only in docs?** Only in docs, plus the README table. A `glossary.ts` of terms and definitions has no
  consumer unless something renders it, and `npm run knip` (CI) fails on an unused export or file. The strings
  themselves stay where they are used; where a word repeats in three or more places the implementer shares one constant
  (`MACHINE_TYPE_LABELS`, the enable-mode labels), not a catalogue.
- **A "Terms" popover is a suggestion, beyond the plan.** A-newcomer #5 asks for one. If the owner wants it: a "Terms"
  item in the ⋮ menu and an (i) by the Results table headers, opening a popover that lists rows 1-16, built as a
  focusable control (1.11) and fed by a new `glossary.ts` (then it has a consumer and knip is happy). Fits best in 2.5,
  when Results is rebuilt. Not part of this item.
