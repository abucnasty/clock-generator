## Decisions

### One snapshot, not a stack

There is a single slot. A second undoable action while a snackbar shows replaces it (new text, new 10 seconds).
Undo then restores the form as it was just before that second action, so the first action stays done.

Why not a stack: below, the snackbar is withdrawn as soon as the build changes in any other way. Then an older entry could
never be undone without losing the later change, so a stack would give nothing. It would also be the "history" the owner
ruled out.

### Undo is withdrawn when the build changes some other way

The snapshot is the whole `ConfigFormData` from before the action. Restoring it would also throw away anything edited since.
So the snackbar disappears as soon as the form differs from the one the action produced (a typed value, a toggle, a reorder,
an Exclude chip). Clicking Generate, Validate, switching Configure/Results or List/Diagram changes no form data and keeps it.

This is a refinement of the plan's "Undo restores the snapshot", chosen so Undo never silently drops edits. **The
orchestrator should confirm.** The alternative is to keep the button and let Undo overwrite later edits; not recommended.

"Differs" is by value, not by object identity (`JSON.stringify`), because a field that commits on blur may produce a new but
equal object. Without that, clicking Undo while a number field has focus could withdraw the button before the click lands.

### What Undo restores for Import, Paste and Reset

Item 1.1 clears the generated clocks, the Validation result and any running generation (`onBuildReplaced` = `clearResults`)
on Import, Paste and Reset. **Undo restores the form only**; it does not bring the clocks back (restoring them would need
the worker state, and 1.1 drops it on purpose). So:

- Results stays on "Nothing generated yet" after the Undo, and the Validation panel stays unvalidated.
- When there were results at the moment of the action (`alternatives.length > 0 || isRunning` in `App.tsx`), the Undo
  replaces the snackbar with a plain message for 8 seconds: "Build restored. The clocks you had generated were cleared; click
  Generate to make them again." (constant `UNDO_RESULTS_NOTE`). With no results it just closes.
- The first snackbar's text stays "{What happened}. Undo", the same for every action. The warning comes after the click, when
  it matters, so the first text stays short.
- Undo after a **row delete, chest switch or Drills off** needs no note. 1.1 keeps the clocks on screen under its stale
  banner for those, and the restored form has the same config key, so the banner goes and "Copy blueprint" comes back by
  itself.

### Undo and localStorage

Nothing new is saved by hand. Undo calls `setConfig(snapshot)`, and the existing save effect (`usePersistedConfigForm.ts:
191-195`) writes the restored form, the same way it wrote the deleted or reset one. A test checks the two serialise to the
same text.

- **Reset.** `resetConfig` removes the key and sets a default form; the effect then saves the default. Undo overwrites it with
  the snapshot. Nothing else needs touching.
- **Reload during the 10 seconds.** The snapshot lives in memory only, so a reload loses the chance to Undo (and the reload
  shows the already-changed saved form). That is accepted; "keep the last 5 builds" is a Phase 3 item (3.4).
- **`_uuid`.** The saved text drops `_uuid` (`saveConfigToStorage`, :129-138) but the in-memory snapshot keeps them, so
  restored rows keep their React keys. After 1.8 the snapshot carries `_forced_always` too, which is right. 1.9 will renumber
  ids on delete; the snapshot is the whole form, so it is unaffected.
- **Before the saved config is loaded** (`isConfigLoaded` false, a split second at start-up): the form in state is the default
  one, not the player's saved one. An Import or Reset in that window cannot be undone correctly, so the snackbar shows its text
  **without an Undo button** (the snapshot is `null`). The action still works as today.
- No snapshot is taken for an action that cannot change the form (a delete of a row that does not exist, switching a chest to
  its own type, Drills off when they are already off). The wrapper must not offer Undo for those.

### The snapshot is the form object itself

Form state is only ever replaced, never edited in place (`utils/configForm/edits.ts` are pure functions), so the snapshot is
a reference to the previous state object, with no copy. A vitest case freezes a form deeply and runs every edit on it, so a
future in-place edit fails the test rather than corrupting an Undo.

## Change

- After Reset, Import Config, a paste from Factorio, a row delete (List or Diagram dialog), Mining Drills off, or a chest-type
  switch, a snackbar reads "{What happened}" with an **Undo** button, for 10 seconds. Undo puts the whole build back exactly
  as it was, and the saved copy follows.
- A new such action replaces the snackbar. Editing anything else, or 10 seconds, removes it. Clicking elsewhere on the page
  does not.
- The Undo snackbar is drawn at the app root, over the sticky footer (the existing import snackbar, inside the app bar, is cut
  by the footer; A14, fixed for good by 1.5). Its text is read aloud when it appears.
- Import and Paste no longer show their separate "imported successfully" toast, since the Undo snackbar says it. Export and
  the error toasts are unchanged.
- In the ⋮ menu, Reset Configuration sits under a divider, in the error colour, at every width.

1. **`utils/undoSnapshot.ts` (new).** Pure, no React. Imports types from `./configForm/formData`.
   - `interface UndoEntry { id: number; message: string; before: ConfigFormData; snapshot: ConfigFormData | null;
     after?: ConfigFormData; resultsCleared: boolean }`. `before` is the form when the entry was made. `snapshot` is `before`
     when Undo is offered and `null` for an entry with no Undo button (before load, or the follow-up notice). `after` is absent
     until the action's own result has been seen ("unsettled").
   - `createUndoEntry(id: number, message: string, before: ConfigFormData, canUndo: boolean, resultsCleared: boolean): UndoEntry`.
   - `settleUndoEntry(entry: UndoEntry | null, form: ConfigFormData): UndoEntry | null`:
     - `null` gives `null`;
     - unsettled and `sameForm(form, entry.before)`: keep the entry (same object); unsettled and different: return it with
       `after: form`;
     - settled and `sameForm(form, entry.after)`: keep it (same object, so `setState` bails out); settled and different: `null`.
   - `sameForm(a, b): boolean`: `a === b || JSON.stringify(a) === JSON.stringify(b)`.
   - `undoOutcome(entry: UndoEntry, nextId: number): { form: ConfigFormData; next: UndoEntry | null } | null`: `null` when
     `snapshot` is `null`; else `form` is the snapshot and `next` is a message-only entry (`createUndoEntry(nextId,
     UNDO_RESULTS_NOTE, snapshot, false, false)`) when `resultsCleared`, else `null`.
   - `describeRemoval(form: ConfigFormData, kind: EntityKind, index: number): string | null`: "{Kind} {id} deleted" using the
     entity's stored `id`, `null` if the index is out of range. (The row chips show position and the diagram shows the id until
     1.9 makes them equal; the stored id is what the Diagram dialog title uses.) Drills are in `form.drills?.configs`.
   - `describeChestSwitch(form, index, newType: ChestType): string | null`: "Chest {id} changed to {Buffer Chest|Infinity
     Chest}", `null` if the chest is already that type or does not exist. Use `isBufferChest`/`isInfinityChest` from
     `./configForm/formData`.
   - `describeDrillsOff(form): string | null`: `null` when `form.drills` is undefined.
   - `describePaste(parts: string[]): string` ("Imported 3 machines, 2 inserters from Factorio").
   - **Constants, so 1.12 changes one place:** `UNDO_DURATION_MS = 10_000`, `UNDO_NOTICE_DURATION_MS = 8_000`, `UNDO_LABEL =
     'Undo'`, `UNDO_RESET_MESSAGE`, `UNDO_IMPORT_MESSAGE`, `UNDO_DRILLS_OFF_MESSAGE`, `UNDO_RESULTS_NOTE`, and the entity
     labels map. Export only what another file or the test uses (knip fails on unused exports).

3. **`hooks/useUndo.ts` (new).** `useUndo(config: ConfigFormData, setConfig: React.Dispatch<React.SetStateAction<ConfigFormData>>,
   isLoaded: boolean)`. Style like the other hooks in `src/hooks/` (named export, 4-space indent, single quotes, semicolons).
   - Keeps `configRef` (updated in a `useEffect` on `config`, never during render) and `isLoadedRef`, so a callback created

   - `const [entry, setEntry] = useState<UndoEntry | null>(null)`.

     (the repo uses `eslint-plugin-react-hooks` 7): `const settled = settleUndoEntry(entry, config); if (settled !== entry)

## Tests

`clock-generator-ui` has vitest only, running in Node. **No jsdom, no testing-library.** The plan's "done when" is vitest
cases for snapshot and restore. All the logic is in `utils/undoSnapshot.ts`.

New `utils/undoSnapshot.test.ts` (same style as `utils/configForm/edits.test.ts`; build forms with `createDefaultConfig`, the
file's helpers and `configToFormData` from `configMapping.ts`; use a form with 2+ machines, inserters that reference them, a
belt, a chest, drills and a rule):
- **Restore after each delete.** `it.each` over machines, inserters, belts, chests and drills: snapshot the form, apply the real
  `edits.removeX`, settle the entry with the result, and check `undoOutcome(...).form` is the original object and deep-equals
  it (a deleted machine's inserter ends are back, `next_ids` is back).
- **Restore after Reset and Import.** `after = createDefaultConfig()` and `after = configToFormData(otherConfig)`: the outcome
  form is the original.
- **Restore after a paste.** The five `replaceX` edits applied one after another, one snapshot taken before the first: the
  outcome is the form from before all of them.
- **Restore after Drills off and a chest switch** (`edits.disableDrills`, `edits.switchChestType`): the drills and productivity
  level, and the chest's old type and fields, are back.
- **Persistence.** `serializeConfig(outcome.form) === serializeConfig(original)` (import `serializeConfig` from
  `hooks/usePersistedConfigForm`, added by 1.8), and `readSavedConfig(serializeConfig(outcome.form))` keeps the rows, rules and
  `_forced_always` (uuids are regenerated, so compare after removing `_uuid`).
- **Second action replaces the first.** An entry made from the form after delete 1, for delete 2, restores to the state with
  delete 1 still done.
- **Snapshots are never mutated.** Deep-freeze a form, run every `edits` function used by the app on it
  (`update*`, `add*`, `remove*`, `reorder*`, `replace*`, `switchChestType`, `enable/disableDrills`, `updateOverrides`) and
  `applyInserterFix` where easy; none throws, and the form still equals its `JSON.stringify` taken before.
- **Settling.** Unsettled entry with the unchanged form stays unsettled (same object); unsettled with a changed form gets
  `after`; settled with a deep-equal copy of `after` is kept (same object); settled with an edited form gives `null`; `null`
  stays `null`; an entry with `snapshot: null` settles and withdraws the same way using `before`.
- **`undoOutcome`.** `null` for a `snapshot: null` entry; for `resultsCleared: true` the `next` entry is message-only (no
  snapshot) with the `UNDO_RESULTS_NOTE` text; for `false`, `next` is `null`.
- **Messages.** `describeRemoval` for all five kinds uses the stored id (delete the middle of three and check the label of the
  last row reads its id), and is `null` for an out-of-range index and for drills when `drills` is undefined;
  `describeChestSwitch` is `null` for the same type; `describeDrillsOff` is `null` without drills; `describePaste(['3 machines',
  '2 inserters'])` reads "Imported 3 machines, 2 inserters from Factorio".

## Risks and checkpoints

- **No owner checkpoint from `ORCHESTRATOR.md` is tripped.** No new dependency (MUI `Snackbar`, `Divider` and `Button` are
  already used), no CI, release or `.claude` change, no id change, no glossary term used. Nothing here contradicts an owner
  decision.
- **For the orchestrator to confirm, not owner questions:**
  - *Withdrawal on other edits* (Decisions). The plan says only "Undo restores the snapshot".
  - *The two additions* (Drills off, chest-type switch). Beyond the plan's list, inside "every destructive action".
  - *Import and Paste lose their separate success toast.* The copy changes from "Configuration imported successfully!" to
    "Configuration imported", and from "Imported … from Factorio!" to "… from Factorio".
  - *Undo does not restore generated clocks* after Import, Paste and Reset (the notice says so). Restoring them would mean
    undoing 1.1's decision to clear them.
- **Copy and the glossary (1.12).** The strings use "Configuration", "build" and "clocks", the words the plan and 1.1 already
  use. All strings are constants in `utils/undoSnapshot.ts`. If the owner's glossary renames them, change that file (and the
  one place the paste text is built).
- **Keyboard and timing (WCAG 2.2.1).** The snackbar is the last thing in the document, so a keyboard user would tab through the
  whole page to reach Undo inside 10 seconds. MUI pauses the timer while the pointer is over it; check in the screenshots run
  whether focus also pauses it. The text is announced (the snackbar content has `role="alert"`). A global Undo shortcut is not in
  the plan and is not added; raise it with the owner or leave it to 1.11 (accessibility) if the UX audit flags it.
- **Overlap with the other snackbars.** The import/export/error toast (`ConfigImportExport.tsx`, bottom centre, 4 s) and 1.2's
  "Copied." stop-gap (bottom centre after 1.2) share the Undo snackbar's anchor. They can overlap for a moment if both show
  (rare). 1.5 puts all of them in one place; do not solve it here. `UNDO_SNACKBAR_ANCHOR` and the single render point in
  `App.tsx` are what 1.5 moves.
- **A no-op action with an unsettled entry.** The wrappers only offer Undo when the action will change the form
  (`describe*` return `null` otherwise). Import and Reset always produce a new form (new `_uuid`s). If a future action is added
  that can return an equal form, its entry would stay unsettled and a later edit would be taken for it; keep that rule.
- **Row labels until 1.9.** "Inserter 3 deleted" uses the stored id. A List row's chip shows its position, which differs after
  earlier deletes until 1.9 renumbers. The Diagram shows the id, so the id is the more consistent pick; 1.9 removes the gap.
- **Overlap with other items (merge order).** 1.1 and 1.2 first (shared `App.tsx`, `ConfigImportExport.tsx`; 1.2 adds the
  narrow-only divider and the Import/Export items this item must keep), then 1.8 (`serializeConfig`). 1.4 (`App.tsx`) and 1.5
  (`ConfigImportExport.tsx`, snackbar placement) overlap and should merge in plan order after this one, or be re-checked. 1.9
  changes `edits.ts` removes; the snapshot is the whole form, so nothing here changes, but the `describeRemoval` id label and
  `next_ids` in the restore test change with it. 1.11 gives the trash icons accessible names; this item does not touch the
  forms, so there is no conflict.
- **Persistence edge.** A reload inside the 10 seconds drops the Undo (memory only). Accepted above.
- **Old entry vs. async import.** `handleFileChange` and the paste handler run after an `await`; they call `onUndoable` right
  before the edit, which reads the current form from a ref, so a form edited while the file was being read is the one saved.
