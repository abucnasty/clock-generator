### 1. Rejected Copy: exact attempted string and an accessible recovery

`src/hooks/useCopyBlueprint.ts` owns shared `copied`, `request`, `confirmingStale`, `confirm`, `cancel`.
Current private `CopyBlueprintOptions` accepts `blueprintString`, `rateWarning`, `staleFor: GeneratedFor|null`,
`running`, `onCopied(warning,whileRunning)`, `onPinned?()`. Its catch only logs. `App.tsx:368–380` supplies
success/warning through `useNotify`/`useAnnounce`, and `pinSelected` uses the selected alternative index.
`DetailsPanel.tsx` privately owns its tab; `BlueprintOutput.tsx` hides the string while stale. Therefore a recovery
which merely focuses the current Blueprint string cannot reliably reveal the attempted old/changed clock.

Approved exact additions:

```ts
export interface BlueprintCopyFailure {
  blueprintString: string;
  rateWarning: string | null;
  staleFor: GeneratedFor | null;
  running: boolean;
}
// CopyBlueprintOptions additions:
copyIdentity: object | null;
onCopyFailed: (failure: BlueprintCopyFailure) => void;
onCopyAttempt?: () => void;
```

App supplies a memoized opaque identity with dependencies `library.currentId`, `generatedFor`, selected clock `id`,
`blueprintString`, `staleFor`; the hook keeps the latest identity in a ref and captures it per write. Use a request
sequence to stop an older settlement replacing a later request's feedback; retire pending work on unmount. On reject,
call `onCopyFailed` with the attempted values (never the values read after await), set no success, pin nothing.
On success retain callbacks/pinning only when the captured identity still equals current identity and the request is latest. After that validation invoke the LATEST callbacks: the selected clock id may remain stable while its index moves. A late success must not pin an old index in a replacement build/run or mark another clock Copied.
Approved superseded-success policy: omit its UI callbacks;
the clipboard may contain the earlier string but current context/selection stays unchanged. Rejection remains recoverable
as a clearly labelled attempted-string snapshot even if selection changes; a newer attempted copy supersedes older feedback.

Each nonempty-blueprint request advances its sequence, clears prior success/timer and invokes the latest optional onCopyAttempt once BEFORE confirmation/write. Confirm reuses that sequence and the captured identity/snapshot; never call onCopyAttempt twice. Bind stale confirmation to that requested identity/snapshot and invalidate it immediately if identity changes. App uses existing useDismissMessage and its own notify-returned id to retire ONLY its previous failure message/action and snapshot; never dismiss an unrelated current message. Cancel reveals/writes nothing.

Mount one new `ManualBlueprintDialog` under App's existing dialogs, independent of Results tabs. Approved props:
`{ failure: BlueprintCopyFailure; onClose: () => void }`; mounted only while recovery is requested. App's failure
callback uses existing `notify({severity:'error', text:"Could not copy the blueprint. Select the string to copy it yourself.",
action:{label:'Select blueprint string',onClick:...}})`. Errors persist by the existing message default. The action opens
the dialog with the captured failure, not live current output. Dialog title "Blueprint string to copy", read-only
labelled multiline field containing exactly that snapshot, initial focus/selection, a visible Select string button
for touch/keyboard and a Close button. Show captured below-target warning; for captured stale output say it is an old
clock and show existing generated-for text. The prior stale confirmation must occur before either write or recovery;
Cancel never reveals the hidden old string. No second clipboard attempt or claim of successful copy on Select.
Always identify it as the blueprint from the failed copy attempt; it must never imply that a changed live selection
or replacement build is the source of this captured string. Return focus through the established MUI dialog behavior;
if original Copy was unmounted, use a connected workflow
control/heading fallback rather than focusing a detached node. Existing `Messages` body-level live region handles modal hiding.
Manual selection has no pinning side effect; current-best pinning remains contingent on a successful clipboard write.
