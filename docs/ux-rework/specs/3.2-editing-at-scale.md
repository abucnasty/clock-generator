## Why it is wrong today

**B17, the List and the Diagram edit an inserter with two copies of the same form.** Since Phase 1 and 2.11 some of B17
is fixed: the belt lane is settable in the List (`InsertersForm.tsx:347-353`, 2.11's `NearLaneSelect`), the machine type
says "Assembling machine" in both (`MACHINE_TYPE_LABELS`, 1.12), and a cleared Stack Size falls back to 16 in both
(`InsertersForm.tsx:448`, `InserterConfigPanel.tsx:174`). What is left is the cause: two components that drift.
- Labels differ: the row says "Source" and "Destination" (`InsertersForm.tsx:287, 385`); the dialog says "Source — Tile
  1", "Destination — Tile 3" and a strip "Inserter 1 — Tile 2" around Stack Size (`InserterConfigPanel.tsx:154, 165-179,
  192`). Shot `phase1-end/w1440/14-diagram-inserter-edit-dialog-1440.png` against `w1440/10-logistic-configure-list-1440-part1of2.png`.
- The pickers' options differ: the List lists an infinity chest's filters as its sublabel and says "No item filter"
  (`InsertersForm.tsx:97-117`); the dialog says "No filter" and gives an infinity chest none (`InserterConfigPanel.tsx:82-87`).
- The automatic filters are computed twice: a local `getInferredFilters` in the List (`InsertersForm.tsx:129-192`) and
  `inferInserterItems` in the dialog (`InserterConfigPanel.tsx:94-97`). The filter handlers are copied too
  (`InsertersForm.tsx:194-224`, `InserterConfigPanel.tsx:99-112`), and so is the 16 fallback.

**N5 (Phase 1 end B#5, ledger "1.8 → 3.2"), two commit models in the Diagram's dialogs.** The inserter dialog is a draft:
nothing reaches the build before Save (`InserterConfigPanel.tsx:250-253, 331-338`, sticky Cancel/Save at `:392-417`,
discard prompt at `EntityEditDialog.tsx:575-593, 693-701`). The machine, belt, chest and drill dialogs apply every
keystroke live, with no Save and no Undo (`EntityEditDialog.tsx:98, 133, 143, 156` for the machine; the sections get the
live `onUpdate*` at `:636-687`). Shot `phase1-end/w1440/13-diagram-entity-edit-dialog-1440.png` (Machine 1: no footer)
against `14` (Inserter 1: Cancel and Save).

**B22 and N43, editing at scale is slow.**
- No Duplicate anywhere; no multi-select or bulk edit. Changing stack size 16 → 12 on 15 inserters
  (`intermediates/low-density-structure/low-density-structure.json`) is 15 separate edits.
- Add Inserter appends at the bottom (`edits.ts:157-172`) and nothing moves focus or scrolls
  (`InsertersForm.tsx:235`, `onAdd={addInserter}` straight through at `App.tsx:598`). The same for the other four kinds
  (`App.tsx:585, 612, 623, 662`). `useFocusAfterRemove.ts` handles removal only.
- **Tab stops.** The logistic Configure page is 64 stops (`phase1-end/a11y/INDEX.md:133`). Inserter 1 alone is 13
  (`phase1-end/a11y/w1440/tab-order-configure.txt` lines 19-31): the drag handle, Source, Destination, Stack Size, two
  filled slots each with its own remove button, three empty slots, the rule chip and Delete. On p2 the lane select adds
  one more on a belt-fed row. The spinners are already out of the order.

**N4 (Phase 1 end B#4), a drag renumbers silently.** A delete says "Deleted Inserter 2. Inserter 3 is now 2." and offers
Undo (`undoSnapshot.ts:134-169`, wrapped in `undoable` at `App.tsx:377-392`). A drag renumbers every entity of the kind
(`edits.ts:519-543`), but `onReorder` goes straight to the edit (`App.tsx:588, 601, 615, 627, 665`): no message, no
Undo. Last run's "Inserter 5" is now another row and nothing says so. The 1.3 capture even asserts it
(`capture-messages-undo.mjs:1129`, "no false offer: a reorder").

**WCAG 2.5.7 (ledger "1.11 → 3.2").** Reordering needs a drag; the only alternative is dnd-kit's keyboard sensor on the
handle (`SortableList.tsx:35-38`), which is not a single-pointer path.

**A latent bug the reorder Undo would hit.** `SortableList` re-syncs its local order only when the set of keys changes
(`SortableList.tsx:49-54`). An order changed from outside (an Undo of a reorder, or a Move up) keeps dnd-kit's old order,
so the next drag moves the wrong row.

**B26, filters.**
- Removing one automatic filter silently turns the other inferred filters into explicit ones, which then stop following
  the source and destination (`InsertersForm.tsx:209-213`, the same at `InserterConfigPanel.tsx:108`). Nothing on screen
  says so.
- Choosing an item in an automatic slot starts from an empty list (`InsertersForm.tsx:196-197`), so picking slot 3 stores
  `[ , , item]`, which serialises with two `null`s.
- The filter picker lists every item in the game (`FilterSlotSelector.tsx:212-218`, `options={itemNames}`), not what the
  source can give first.

## Pick: one editor that takes a value and reports changes (B17)

**`InserterEditor` renders the inserter's fields from `value` and calls `onChange(updates)`. It holds no state. The List
row passes the live inserter and `updateInserter`; the dialog passes its draft and a draft setter.** Only the layout
differs (`layout: 'row' | 'stacked'`). The labels, the order of the fields, the option lists, the automatic filters and
the fallbacks come from one place.

| | One controlled editor (picked) | One editor with its own draft and a `live` flag | Keep two, share helpers |
|---|---|---|---|
| Same fields and labels | By construction | By construction | Only as long as both are kept in step (B17's cause) |
| List stays live, Dialog stays a draft | Yes: the caller decides | Yes, but the editor owns commit logic it does not need in the row | Yes |
| Bulk edit (PR B) reuses it | Its parts (`inserterOptions`, `inserterFilters`) yes | Same | Partly |

Field order in both: **Source, Nearest lane of the belt (only when the source is a belt with two lanes), Destination,
Stack Size, Filters.** The dialog's "Tile 1/2/3" strip goes: the order already reads source, inserter, destination, and
the tile words are not in the glossary.

## Pick: every Diagram dialog is a draft with Save (N5; owner Q3, recommended answer (a))

The machine, belt, chest and drill dialogs work like the inserter one: they edit a draft, the sticky footer shows
"Unsaved changes", Cancel and Save, and closing with unsaved changes asks "Discard changes to {Machine 1}?" (1.8's
`DiscardChangesDialog`). Save applies the changed fields in one go and closes. The List stays live, as it is today. One
model per surface: a modal is a draft, the List is live. It is the model 1.8 chose and needs no new Undo surface. Under
(b), see "Owner decision needed: Q3".

- A chest's type switch in the dialog changes the draft (a buffer chest becomes an empty infinity chest in the draft).
  On Save, when the type changed, the dialog calls `onSwitchChestType(index, type)` first (it offers Undo with
  `describeChestSwitch`'s "Chest 1 changed to Infinity Chest.", as today), then `onUpdateChest(index, rest)` with the
  draft's other changed fields.
- The machine dialog's Machine Facts read the draft, so a new crafting speed shows its max rate before Save.
- The Delete button in the title stays and deletes at once (with Undo), dropping any draft.

## Pick: B26, say it and offer the way back; source items first

- **Keep the conversion, say it.** "Remove that one slot and keep the rest AUTO" cannot be stored: `filters` is either
  absent (automatic) or a list. So a change to an automatic slot (remove, or choose another item) makes the shown list
  explicit, **starting from the automatic list** (no holes), and the editor then shows **"Set by hand"** with a text
  button **"Use automatic filters"**, which removes `filters`. The change is announced (copy table). The note and button
  show only while `filters` is set and the automatic list is not empty. Vetoable: the plan names only the picker half of B26.
- **Source items first.** The filter picker gets the source's items as a first group, "From {Belt 1}", then "All items".
  Search filters inside each group, so the groups stay together (MUI's `groupBy` needs contiguous groups). With no
  source items there are no groups. Only the inserter filter picker; the chest pickers have no source.

## Pick: Duplicate appends at the end (B22)

**Duplicate adds a copy as the last row of its kind, with the next number, and focuses it**, the way Add does.

| | Append (picked) | Insert after the original |
|---|---|---|
| Renumbers other rows | Never | Every later row of the kind, which then needs its own message and Undo |
| Works whatever Q2 decides | Yes | Ties Duplicate to the renumber message |
| Copy next to its original | No (Move up, or a drag, puts it there, with a message) | Yes |

A copy keeps every field: source and destination with the lane, stack size, filters, the enable rule and its
`_forced_always` flag (the copy moves the same items, so "Exclude from LCM" covers it the same way). A machine's,
belt's, chest's or drill's copy keeps all of its own fields; no inserter is copied with a machine. Duplicate is not
destructive, so it offers no Undo (Delete on the copy has one); it is announced.

## Pick: reorder gets a message and Undo; Move up and Move down in a row menu (N4, WCAG 2.5.7; owner Q2, recommended answer (a))

- A drag, Move up and Move down all go through `undoable.reorder*` in `App.tsx`, which calls
  `offerUndo((form) => describeReorder(form, kind, from, to))` just before the edit, as removes do. The message: "Moved
  Inserter 5 to 2. Inserters 2–4 are now 3–5." Dropping a row where it was says nothing and offers nothing (null).
- **A row actions menu** ("More actions for Inserter 3", a grey `MoreVert` icon button between the rule chip and Delete;
  in rows without a chip, before Delete) holds **Duplicate, Move up, Move down**. Move up is disabled on the first row and
  Move down on the last. This is the keyboard and single-pointer path for reordering (WCAG 2.1.1, 2.5.7).
- **The drag handle becomes pointer-only:** `tabIndex={-1}`, `aria-hidden="true"`, and `SortableList` drops dnd-kit's
  `KeyboardSensor`. dnd-kit's announcements return nothing, so a drop is read once, through the message in the polite
  region. `reorderAnnouncements` goes from `a11yLabels.ts` (knip).
- After Move up, focus stays on the moved row's menu button (MUI returns focus to the anchor, and the row keeps its DOM
  node because it is keyed by `_uuid`). After an Undo, `useUndo` returns focus to `offeredFrom` as it does for deletes.
- `SortableList` re-syncs its local order whenever the incoming order differs (not only when the key set does). After a
  drag the incoming order equals the local one, so the drop animation is untouched.
- The offer ends as every Undo offer does, including when a check or generation starts (1.5 F).

## Pick: fewer tab stops, not a grid (B22)

B22's best case is one stop per row with arrow keys between cells (the ARIA grid pattern). Not picked: every cell holds a
combobox or a select whose arrow keys already mean something, so a grid needs a cell-edit mode on top, which is a large,
risky change for the List that newcomers use. Picked, per row: the drag handle out (Move up/down replace its keyboard
use), the filter remove buttons out (Delete on a focused slot already removes it, `FilterSlotSelector.tsx:97-100`; the
slot gets `aria-keyshortcuts="Delete"`), and one row menu in.

**Inserter row stops (select mode off) = Source + Destination + Stack Size + 1 if the lane select shows + one per set
filter slot + 1 for the "+" slot (2.7 B draws one) + rule chip + row menu + Delete.** Logistic science: Inserters 1 and 2
(belt with two lanes, one filter) 9 each, Inserter 3 8. Today on p2: 13, 13, 12 (14, 14, 12 with five slots and the lane
select; 2.7 B alone brings them to 10, 10, 9). Machine, belt, chest and drill rows lose the handle and gain the menu: no
row gets a stop more.

## Pick: select mode and a bulk bar for inserters (B22)

- **A "Select" toggle button** (`aria-pressed`) in the Inserters section header, beside "Add inserter". Off by default,
  so a newcomer sees no checkboxes (newcomer-first). On: every inserter row starts with a checkbox "Select Inserter 3".
  Space toggles; Shift+click selects the range from the last clicked row. "Select" off clears the selection.
- **The selection is a set of `_uuid`s**, so it survives renumbers, moves and Undo. It is pruned to the rows that exist
  on every render, so Import, Paste from Factorio and Reset clear it.
- **The bulk bar** shows while at least one row is selected, at the top of the Inserters section (in the DOM before the
  rows, so Shift+Tab reaches it), `position: sticky` just under the page header, so it stays in view while the player
  scrolls 15 rows. It holds: "{n} inserters selected", **Select all**, **Clear selection**, a **Stack Size** field with
  **Set**, **Filters…**, **Enable rule…**. All are outlined grey or text (2.7: green filled stays the next step).
  - **Set** applies the field's value to every selected row.
  - **Filters…** opens a popover with a slot editor on a draft list (the same `FilterSlotSelector`), the picker's first
    group being the union of the selected rows' source items ("From the selected inserters' sources"), and **Apply**,
    **Use automatic filters** and **Cancel**.
  - **Enable rule…** opens the existing `EnableControlModal` with `entityLabel` "Inserters 1–3", the shared rule as
    `currentOverride` when every selected row has the same one (else none), `availableItems` the union of their items,
    and `sourceType`/`sinkType` only when all selected rows share them. Save sets the rule on each row.
  - Each apply is one edit, `edits.updateInserters(uuids, updates)`, and offers Undo with a message naming the rows
    ("Set Stack Size to 12 on Inserters 2, 5–7."). Undo puts every row back.
- **Focus not obscured.** While the bar shows, the page's `scroll-padding-top` grows by its height, so Tab and Shift+Tab
  never leave a focused row under it (WCAG 2.4.11). `useStickyHeaderHeight` writes `calc({header}px + 8px +
  var(--sticky-under-header, 0px))`; the bar sets `--sticky-under-header` from its measured height and removes it on
  unmount.
- When the bar goes (Clear selection, the last selected row deleted, Select off) while focus was in it, focus moves to the
  Select toggle.
- Not here: bulk delete, bulk for drills, selection across kinds. Each is a follow-up if wanted.

## Pick: a new row is focused and in view (B22)

Add (any kind) and Duplicate both append, so one rule covers both: when a card's row count grows through its own Add or
Duplicate, focus moves to the new last row's first control (marked `data-row-first`: an inserter's Source, a machine's
Recipe, a belt's Belt type, a chest's first field, a drill's Type), and `focus()` scrolls it into view below the header
(the header hook's `scroll-padding-top`). The change is announced ("Added Inserter 16."). Not for rows added by an import,
a paste or the Diagram. If 2.7 B added a focus-after-add for its chest and drill "+ Add" rows, this replaces it with the
general one in `useFocusAfterRemove.ts`.

## Change (what the player sees)

- The List row and the Diagram's inserter dialog show the same fields, in the same order, with the same words.
- Every Diagram dialog has Cancel and Save; nothing reaches the build before Save, and closing with changes asks first.
- The filter picker starts with what the source gives. Changing an automatic filter says "Set by hand" and offers
  "Use automatic filters".
- Each row has a "⋮" menu with Duplicate, Move up and Move down. A move or a drag says what was renumbered, with Undo.
- Add and Duplicate put the keyboard in the new row, on screen.
- Inserters can be selected and edited together: stack size, filters and enable rule, each with Undo.
- Fewer Tab stops per row.

## Owner decision needed: Q2, drag reorder

**Question.** A drag renumbers every row of its kind (the owner chose consistent renumbering in 1.9). Today it does so with
no message and no Undo, unlike a delete. What should it do?

  keyboard and single-pointer path (WCAG 2.5.7).
- **(b) Drop drag reorder.** Rows stay in the order they were added; numbers change only on a delete (with Undo).

**Recommendation: (a).** It is small (one `offerUndo` per reorder, as removes have), keeps a way to put rows in the order
