## What is wrong today (A10)

- **The question that most decides the pick is hidden.** "Belts do not move" is a switch inside the collapsed
  "Advanced Overrides (Optional)" accordion (`OverridesForm.tsx:105-126`), with a ~90-word tooltip. It is
  `overrides.non_moving_belts` (`clock-generator/src/config/schema.ts:460`, off by default).
- **What it decides** (`rank.ts` `rankingOf`, `alternatives.ts`, `plan-run.ts` `clockOfPlan`): by default every clock is
  made for a moving belt, so each window of an inserter that picks up from a belt stays open a few ticks longer (belt
  pickup slack), and a clock made without the slack is only picked when no clock with it holds the target rate. With the
  switch on, every clock is made without the slack and the one with the fewest wake-ups wins. On logistic science that
  is the difference between the pick with 177 wake-ups a minute and a stable clock with 0 (review shot 20).
- **Results never says which assumption the pick used.** 1.6 puts "on a moving belt" / "with belts that stand still" in
  the recommendation sentence and a "This run" line in a closed disclosure, but nothing offers to change it.
- **The slack only exists for an inserter that picks up from a belt** (`beltPickupSlackTicks` in `clock.ts` looks for an
  inserter whose source is a belt). With no such inserter the question means nothing.

## Change

- **The question, in the Belts section.** When at least one inserter takes from a belt of the build, the Belts card
  (List view) opens with "Your input belts are:" and a two-option radio group: **Moving** (the default) and **Backed up
  and standing still**, each with one line saying what it does (copy below). It maps to `overrides.non_moving_belts`:
  Moving stores nothing (the key is removed, as the switch does today), Standing stores `true`.
- **Gone from Advanced Overrides.** The "Belts do not move" switch and its tooltip are removed. The other overrides stay.
- **Also in the Diagram view.** The Belts card is not drawn there, and the switch is leaving Advanced, so the same
  question is drawn in its own small card under the diagram. Without it, a player who works in the Diagram could no
  longer reach the setting.
- **Results states the assumption, with an action.** Above the Potential Clocks panel (or inside 2.5's summary card, see
  "If 2.5 has landed") a line says what the clocks assume, with a text button:
  - made for moving belts: "These clocks assume your input belts are moving." + **My belts stand still. Generate again**
  - made for standing belts: "These clocks assume your input belts are backed up and standing still." + **My belts
    move. Generate again**
  - The button sets the answer on the build, then runs Generate on it (through the Generate button's own handler, so
    2.3's check-first applies once it has landed). While a generation runs the button is not clickable but stays in the
    tab order. The line shows only when the question was asked for that generation.
- **A hint of what switching may bring** (optional, the orchestrator can veto): on a moving-belt result, when the best
  clock for standing belts has fewer wake-ups than the pick, one more sentence: "On belts that stand still, this build
  may do with 0 wake-ups a minute instead of 177." It is computed from the clocks already on screen (the clocks made
  without the slack are in the list, ranked "not for your belt"), so it needs no engine change; "may" because the
  regenerated clocks can differ slightly (fuel hand room, see `withFuelHandRoomWhereNeeded`). It is the A9/A10 reason the
  0-wake-up clock was not picked.
- **Not changing:** the engine, the config schema and file format (`non_moving_belts` stays the stored key; saved and
  shared configs load as before), 1.6's recommendation sentence (it already says "on a moving belt" / "with belts that
  stand still"), the Belt column of the clock table, the engine's own clock names and descriptions (engine text is left
  for 2.5), the `search_for_fewer_wake_ups` switch (still under Advanced), and the Undo snackbar (a radio change is not
  destructive).

### When to ask (the rule)

Ask when `inserters.some(i => i.source.type === 'belt' && belts.some(b => b.id === i.source.id))`: a belt of the build
feeds an inserter. Not when the build has belts but none is picked up from (belts only filled by inserters, direct
insertion, chests only). The answer is read from the same build either way:
`overrides.non_moving_belts === true` is Standing; absent or `false` is Moving. When the question is not asked its
stored value is left alone, and since no inserter takes from a belt it changes no clock.

### `utils/beltQuestion.ts` (new, pure, no React)
Types only from `./configForm/formData` and `../worker/types`; the one runtime import is `recommendedIndexOf` from
`./recommendedClock` (1.6). Export only what the page or the tests use (knip fails on unused exports).
- `type BeltAnswer = 'moving' | 'standing'`.
- `interface BeltQuestion { ask: boolean; answer: BeltAnswer }`.
- `beltQuestionOf(build: { inserters: ReadonlyArray<{ source: { type: string; id: number } }>; belts: ReadonlyArray<{ id: number }>; overrides?: { non_moving_belts?: boolean } }): BeltQuestion`.
  The structural input takes both the form (`ConfigFormData`) and the engine `Config`, since the page asks of the form
  and `generatedForOf` asks of the config a generation ran with.
- `nonMovingBeltsFor(answer: BeltAnswer): true | undefined`: what to store. Never `false`.
- `otherAnswer(answer: BeltAnswer): BeltAnswer`.
- `beltResultsLine(answer: BeltAnswer): { text: string; actionLabel: string; switchTo: BeltAnswer }`.
- `standingBeltsHint(alternatives: Pick<ClockAlternativeView, 'ranking'>[], recommendedIndex: number | null, used: BeltAnswer): string | null`.
  Null unless `used` is `'moving'`, `recommendedIndex` is not null and the list is not empty. It recomputes the pick with
  `ranking.matches_belt_choice` set to `true` on every clock (`recommendedIndexOf` over copies), which is the rule a
  standing-belts run applies, then returns the hint only if that clock `meets_target_rate`, both clocks' wake-ups are
  non-null, and the standing clock's is smaller when compared the way `rank.ts` does (`Math.round(x * 1000)`). Numbers
  print as `Math.round`, like the table.
- `BELT_COPY`: every string in the table above.

## Tests

- `beltQuestionOf` (the when-to-ask mapping):
  - empty build: `ask` false;
  - a belt-sourced inserter whose belt exists: `ask` true;

  - two belt-fed inserters, or one of several inserters: true;

    is `'moving'`; the answer is reported even when `ask` is false;

- `nonMovingBeltsFor`: `'moving'` is `undefined` (not `false`), `'standing'` is `true`.

- `standingBeltsHint`: builds clocks with a small `clock(id, ranking)` helper like 1.6's tests:
  - the default case (a moving pick with 177 wake-ups, a stable clock with `matches_belt_choice: false` and 0): the exact

  - `used: 'standing'` gives null; `recommendedIndex` null or an empty list gives null;
  - the standing-belt clock has the same or more wake-ups: null (compared to a thousandth);
  - the best standing clock does not meet the target rate: null; a wake-up count of `null` on either: null;
  - numbers print rounded (176.6 prints 177).

## Risks and checkpoints

- **No owner checkpoint is tripped.** No new dependency (MUI `RadioGroup`, `Radio`, `FormControlLabel`, `Button` are
  used elsewhere), no engine, CI, release or `.claude` change, and the plan's text is followed (the question, the
  default, the removal from Advanced, the Results statement with the action). Additions beyond its wording, each
  vetoable: the Diagram-view copy of the question, the optional wake-ups hint, the `README`/`GOALS` wording fix, and the
  "Not sure? Leave it on Moving" line.
- **More than 5 files, so by the ORCHESTRATOR rule this moves up to `opus`.** The edits are small and the logic is one
  pure module with tests, so `sonnet` as the header says is probably enough, but the "set the override then generate"
  effect in `App.tsx`, the `GeneratedFor` change and the merge with 2.3, 2.5 and 1.6's files are the places a weaker
  model could slip. The orchestrator's call.
- **Where the hint is wrong.** The clocks made without the slack in a moving-belt run are the same clocks a
  standing-belts run starts from, but a standing-belts run can also add room for a hand of fuel
  (`withFuelHandRoomWhereNeeded`) and drops the "non-moving belt" duplicate. The hint therefore says "may". If the
  orchestrator would rather not promise a number, veto the hint: delete `standingBeltsHint` and its prop.
- **An answer that does nothing.** An inserter that takes from a belt but is always enabled (an enable rule of Always on,
  or a forced one from "Exclude from LCM") gets no window, so no slack, and the answer changes nothing for it. The
  question is still asked because the form cannot know the windows. The Results line then says "assume" rather than
