# 1.2 Keep the header usable at every width
Findings: A7, B25, C1  ·  Implementer model: sonnet  ·  Branch: feat/ux-rework-p1-header

Owner decision this serves ("Widths"): full support for desktop and half-width down to 720px. Below 720px only
Configure, Results and the main actions (Generate, Copy) have to stay reachable. This item is that guarantee for the
header. The rest of the half-width layout is 2.9.

## Why it breaks today

- `App.tsx:284-304` draws a `position="fixed"` `AppBar` with one `Toolbar`: logo, the title "Factorio Clock Generator",
  and `ConfigImportExport` (two outlined buttons plus the ⋮ icon). At 390px the buttons do not fit, so the bar wraps to
  about 96px (C1).
- `App.tsx:305-306` is a `<Toolbar />` spacer that assumes the fixed bar is 56px (xs) or 64px (sm and up) tall.
- `WorkflowBar.tsx:70-80` is a `Paper` pinned with `position: 'sticky'` and `top: { xs: 56, sm: 64 }`. When the app bar
  wraps, the workflow bar's first row slides under it, and the Configure/Results toggle (and Validate/Generate before
  validation) cannot be clicked. From Results the player cannot get back to Configure (A7, B25, C1; shots 28, 30, 31,
  39).
- The workflow bar itself also wraps at 390px (`WorkflowBar.tsx:81` has `flexWrap: 'wrap'`). That is fine, as long as
  the bar grows and nothing is pinned to a guessed height.

## Decision: render the workflow bar inside the app bar, and make the app bar sticky, not fixed

Recommended: put `WorkflowBar` inside the `AppBar` as a second dense `Toolbar`, and change the AppBar from
`position="fixed"` to `position="sticky"`. Delete the spacer.

Reasons:

1. With `fixed`, a taller bar needs a matching spacer, so the same guess moves from `top: 56/64` to the spacer. With
   `sticky` the bar is in the page flow: it takes its real height, pushes the content down, and stays at the top while
   scrolling. No spacer, no JS, no first-paint jump, and it survives text zoom, a wrapped workflow bar and the bar
   appearing only after `isInitialized`.
2. Both rows share one stacking context, so the toggle can never be covered by the title row (C1's proposed fix).
3. The alternative (keep the bar a separate sticky `Paper` and measure the app bar with a `ResizeObserver` to set
   `top`) works, but needs state, can lag a frame behind a resize, and leaves two things that must agree.

Layout facts checked: the root `Box` (`App.tsx:283`) has no `overflow`, and `index.css` sets none on `body` or `#root`,
so `sticky` will stick to the viewport. The fullscreen diagram `Dialog` (z-index 1300) sits above the app bar (1100).
The footer is `sticky` at the bottom with the same z-index and is not changed here (1.5).

## Change

- At 900px and wider (MUI `md`) the app bar looks as it does today: logo, "Factorio Clock Generator", Import Config,
  Export Config, ⋮. The workflow bar sits directly under it as part of the same header, and the whole header stays
  pinned while the page scrolls.
- Below 900px, Import Config and Export Config leave the bar and become items in the ⋮ menu (same labels, same icons,
  same behaviour). The app bar holds only logo, title and ⋮, on one line.
- Below 600px (MUI `sm`) the title reads "Clock Generator".
- The workflow bar is never covered. At 1440, 960, 720 and 390px the Configure/Results toggle, Generate and, once there
  is a blueprint, Copy blueprint are visible and clickable, and no part of the header overlaps another part or the page
  content.
- At 390px the workflow bar may take two or three rows. To keep it from taking more than it needs, its gap shrinks
  and the selected-clock label (`WorkflowBar.tsx:97-101`) is hidden below 600px.
- "Validate" scrolls the Validation panel to just below the header at every width, including when the header is tall.
- The "Copied. {rate warning}" toast still shows when a below-target blueprint is copied. It must not land on top of
  the title or ⋮ (see "Snackbars" below).

## Snackbars and dialogs

- **Import and Export dialogs.** `Dialog` already renders through a portal, so the "Confirm Import from Factorio" dialog
  is unaffected by the AppBar containing it. It and the file input and snackbar are siblings of the buttons, not
  children of the `Menu`, so moving the buttons into the menu changes nothing for them. The implementer proves it by
  running Import Config and Export Config from the menu at 390px (see Acceptance).
- **ConfigImportExport's snackbar** (`ConfigImportExport.tsx:378-387`, bottom centre) is unchanged. It is still inside
  the AppBar's stacking context, so the sticky footer still covers part of it. That is finding A14 and is 1.5's job,
  not this item's. Changing `fixed` to `sticky` on the AppBar does not change how a `position: fixed` snackbar is
  placed.
- **WorkflowBar's "Copied. {rate warning}" snackbar** (`WorkflowBar.tsx:113-122`, top centre) is the one this item
  changes. Today it sits inside a z-index 1099 `Paper`, below the z-index 1100 app bar, so it is mostly hidden behind
  it. Once the workflow bar is inside the AppBar it would be drawn over the title and ⋮ for 10 seconds. Wrapping it in
  `Portal` renders it in `document.body` above the footer and the app bar (z-index 1400), and anchoring it at the bottom
  centre keeps it off the header. 1.5 will move both snackbars to one portal at the app root, anchored below the
  workflow bar, and will replace this stop-gap. 1.2 must not build that shared portal.
- **Ordering with 1.5.** 1.2 and 1.5 both edit `WorkflowBar.tsx` and `ConfigImportExport.tsx`, and 1.1 and 1.4 edit
  `WorkflowBar.tsx` and `App.tsx`. Merge 1.1 and 1.2 in plan order and do not run any two of 1.1, 1.2, 1.4 and 1.5 in
  parallel (the orchestrator's "no file in common" rule).

This is a layout-only change, and `clock-generator-ui` has no component-test setup: `package.json` has `vitest` but no
`jsdom` or `@testing-library`, `vite.config.ts` has no `test` block (so tests run in Node), and the 6 existing tests

  the one that can catch an overlap.

## Risks and checkpoints

- **No owner checkpoint is tripped**: no new dependency (`useMediaQuery`, `useTheme`, `Portal`, `Toolbar` and `Divider`
  are in `@mui/material` already installed), no CI, release or settings change, no glossary or copy (labels unchanged;
  "Clock Generator" is the title shortening that A7 and C1 ask for), no id change. Nothing here contradicts an owner
  decision.
- **For the orchestrator to confirm, not an owner question:**
  - Recommending `sticky` instead of the plan's two options is a variant of "render it inside the AppBar".
  - Hiding the selected-clock label below 600px drops a status line on phones. The same name is on Results in the
    Potential Clocks table. Say so if you would rather keep it.
  - The stop-gap `Portal` plus bottom anchor on the "Copied." snackbar overlaps 1.5. 1.5's implementer should delete
    it when they build the shared portal.
- **Vertical space on a phone.** At 390px the header may be about 56px plus two or three workflow rows (roughly 120 to
  170px of an 844px screen), and it is pinned. That is accepted: below 720px only reachability is guaranteed. A
  collapsing header is a Phase 2 matter (2.9), not this item.
- **Focus and keyboard.** Menu items hidden with CSS would break `Menu` arrow-key navigation, so use the `narrow`
  conditional, not `display: none`. After Import Config opens the native picker from the menu, MUI restores focus to the
  ⋮ button when it closes, which is the desired behaviour.
- **User activation.** Calling `fileInputRef.current?.click()` after an `await` or a timer is blocked by browsers. Keep
  the menu handlers synchronous (see Files).
- **Resize while the menu is open.** Crossing 900px while the menu is open re-renders the items. It does not break
  anything (the `Menu` stays anchored to the ⋮ button). Not worth handling.
- **Scroll targets elsewhere.** `DebugPanel.tsx:43` scrolls inside its own log box and is unaffected. Only
  `ValidationPanel.tsx:36` is a header-height guess in the code base (searched `sticky`, `scrollIntoView`,
  `scrollMargin`, `top:`).
- **Merge conflicts.** See "Ordering with 1.5" above. Do not start 1.2 in parallel with 1.1, 1.4 or 1.5.
