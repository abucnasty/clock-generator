# The record

One small JSON file per blast job (`<group>-<name>.json`, the blast's job key): the clock the generator selects for the build and every other clock it
weighed. It is committed and generated by `scripts/blast/blast.sh`, never edited by hand. CI regenerates it and compares it field by field; a
difference fails with a table of job, field, before and after.

It holds what `blast.sh` computes for the job and nothing else: no seconds, no path, no machine. A job is one of the blast's seven groups
(`config`, `pickup`, `overhood`, `front`, `blocked`, `containers`, `variants`): the sample configs as they are, the fixtures, and the variants (a sample with the options a game recording or a test sets on it: belts backed up, an ingredient left out of the window cycle; `tests/game/builds/variant-jobs.ts` lists each with what qualifies it).

## Fields (format `clock-record-2`)

A field's name and meaning do not change; a new field or a changed meaning is a new format number (`clock-record-3`) and rewrites every file. `clock-record-1` named the window cycle time `period`; `clock-record-2` names it `window_cycle_ticks`, and `record.py worse` still reads a base record in `clock-record-1`.

| Field | Meaning |
| --- | --- |
| `format` | `clock-record-2` |
| `job`, `group`, `name` | the blast's job key (`config-ACCUMULATOR_640`), its group and its name |
| `config_sha256` | the hash of the job's config as the blast loads it: it says whether a moved result comes with a moved config |
| `job_results_sha256` | the digest of what belongs to the job and to no single clock: why it is not stable, the selected index, the clocks' ids |
| `selected` | the id of the selected clock (one of `alternatives`) |
| `selected_windows` | the recommended clock's windows: for each inserter or drill, `start-end` pairs in ticks of the window cycle (`0-10,54-64`: the opening edge and the closing edge of each window); empty when the machine has none |
| `alternatives` | every clock, in the generator's order, one per line. Only the recommended clock's windows are written out; every other clock carries the hash of its windows (`windows_sha256`), since written out they would be four times the size of everything else (1.4 MB for 33 jobs) |
| `error` | instead of the fields from `job_results_sha256` on, when the config failed to generate: the error |

A clock in `alternatives`:

| Field | Meaning |
| --- | --- |
| `id` | the clock's id, unique in the job |
| `verdict` | the generator's verdict: `stable`, `unstable` or `no recovery` |
| `holds` | whether the clock holds the target |
| `rate` | items a second it makes |
| `supply` | the belt's kind the clock was weighed with: `moving` or `backed_up`; null where the build has none |
| `window_cycle_ticks` | the window cycle time in ticks |
| `wake_ups` | inserter wakeups a minute, to three decimals; null where the clock has none |
| `descriptions_cut` | how many descriptions Factorio's 500-byte limit cut (0 in all but one clock of the first record) |
| `clock_sha256` | the hash of the exported clock's identity (the blueprint without its text, and the schedule): the hash a game recording is tied to |
| `windows_sha256` | the hash of all this clock's windows (the selected one's are in `selected_windows`) |
| `text_sha256` | the hash of the exported blueprint with its text, which moves with any description |
| `results_sha256` | the digest of what the clock hash leaves out: label, description, insights, verdict, assessment, the simulation's histories, the clock-only run, the fuel view |

## Clock ids

A clock's `id` is derived from the strategy and the settings of the clock (`takt_batches_observed`, `round_robin_polling_per_hand`,
`takt_batches_swings_6`, `coordinated_sources`). The blast writes the slot that made each clock into its job file as `maker` (the id it had
before the ids were derived); the record does not hold it, so its format does not change. `record check` reads an id of the committed
record that is a maker of the run, and not an id of it, as the id the run gave that maker's clock, so a pure rename of the ids is no
difference. A pin of a game test (`selection.id`) is of the record's ids: its clock is the one with the pin's `clock_sha256`.

## Regenerating it

```bash
# all seven groups, every job (the record covers all 86), then write the files
BLAST_GROUPS=config,pickup,overhood,front,blocked,containers,variants bash scripts/blast/blast.sh run .. <out>
bash scripts/blast/blast.sh record write <out>          # or the cache entry's key, as `blast.sh list` prints it
bash scripts/blast/blast.sh record check <out>          # the table of differences against the committed files; exit 1 on any
```

CI runs the jobs in eight shards and joins them (`blast.sh run <worktree> <out> --shard i/8`, then `python3 scripts/blast/shard.py merge <whole> <shard folders>`;
`shard.py plan` prints the split), then runs `record check` on the joined folder.

A run that is cached (the key of the engine and the job list) writes the record in seconds. After a rename of jobs, `record check --map <renames.txt>`
takes the blast's rename map (`old-job-key new-job-key` a line) and compares a renamed job with its new name.

## The properties

What must be true of the result of every job, whatever the build, is checked on every clock of every job by one module,
[`tests/game/builds/record-properties.ts`](../tests/game/builds/record-properties.ts). It runs in the blast, on the live results (the simulation's
histories are too big to keep), and writes what it found into the job file as `properties` (not into the record): the clocks each
property applied to, and the problems. `blast.sh record check` fails on any problem with a table of job, property, clock and the
values. The six properties:

| Property | It says |
| --- | --- |
| `entity-routes-total` | every inserter and drill of a clock has exactly one route: a reason it stays always on exactly when it has no window and no clock of its own, and the clock's reasons are exactly those |
| `decider-build-order` | the order the check gives the window deciders is the order the exported blueprint builds them in |
| `stable-holds-and-survives-loss` | a clock gets the disturbance trials when it is not unstable; it is stable only when it has recovery after every disturbance trial; a clock that meets the setpoint is stable |
| `counters-add-up` | the per-inserter counters add up to the wakeups, and the clock-level figures agree with the clock |
| `fuel-never-dry` | no machine that burns fuel runs out of it in the fuel consumption view |
| `strategy-and-signals` | the strategy's output swings are the count the clock was made at, counted as output swings or as hands brought in, a construction named for the families made from batched swings only; signals a minute counted where wake-ups are, none from a clock with no window decider |

A property states what a result must satisfy; the record pins the values. A property that fails on a job is a finding about that job's
result, and is not loosened to pass: a job that cannot satisfy one for a reason of its own goes in `EXCEPTIONS` of the module, with the
reason, and the pull request says so. A job file made before the module, or carried by a selective run from one, has no `properties` (or
those of another version of the module): `record check` fails on it, and `blast.sh run --full` makes it again (`--allow-unchecked` lists
such jobs and goes on).

## MOVES.md

A pull request that changes any record file commits the new files and adds an entry to [MOVES.md](MOVES.md) naming each moved job and why.
A recommended clock that got worse than in the base fails the check unless its job is named in the lines the pull request adds (CONTRIBUTING.md,
"The record of the blast jobs", defines worse from the fields above).
