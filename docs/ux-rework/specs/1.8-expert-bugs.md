## What is wrong today

- **B5.** In the Validation panel's Transfer Plan, clicking an ingredient chip to "Excluded" runs
  `updateIgnoredIngredients` (`utils/configForm/edits.ts:449-509`). For every inserter whose items are all excluded it
  writes `enable_control: { mode: 'ALWAYS' }` (lines 465-473) over whatever was there, including a hand-built CLOCKED or
  CONDITIONAL rule. Clicking it back to "Included" removes the whole `enable_control` of any inserter whose items were all
  excluded and whose mode is ALWAYS (lines 474-484), so it also deletes an ALWAYS the player set on purpose (the sample
  `intermediates/advanced-circuit/advanced-circuit-230.json` has exactly that: coal excluded, inserter 9 set to ALWAYS by
  hand). The code cannot tell a forced ALWAYS from a chosen one. `App.tsx:255-260` (`handleExcludeChange`) and
  `TransferPlanPanel.tsx:47-53` (`toggleExclude`) only call it and need no change.
- **B16.** `ConfigFlowDiagram.tsx:258-277` renders `<ReactFlow>` without `deleteKeyCode`. `@xyflow/react` 12.10.2 defaults it
  to `'Backspace'` (`node_modules/@xyflow/react/dist/esm/index.mjs`, in the `ReactFlow` destructure: `deleteKeyCode =
  'Backspace'`), and `onEdgesDelete={handleEdgesDelete}` (line 272; handler at 197-214) deletes the whole inserter at
  either end of the selected edge, with no confirm and no undo.
- **B6.** The rule editor lives in two hosts.
  - `EnableControlModal.tsx:363-415` (opened from the List's gear in `InsertersForm.tsx:473-573` and from
    `DrillsForm.tsx:282-310`): `Dialog onClose={onClose}` (line 379) closes on a backdrop click and on Esc, and the
    X (line 395) closes too, all throwing away the form state held inside `EnableControlFormContent` (lines 98-103).
  - `InserterConfigPanel.tsx:256-372`, the Diagram's inserter dialog (`EntityEditDialog.tsx:628`): two tabs with two commit
    models. The **Config** tab (`InserterEditSection`, lines 43-238) writes every change straight to the config through
    `onUpdate`. The **Overrides** tab (`EnableControlFormContent`, lines 357-367) holds its edits in local state until
    its own Save, and the tab bodies are rendered with `activeTab === 0 && ...` / `activeTab === 1 && ...` (lines
    344-368), so switching to Config **unmounts it and silently drops the draft**. Esc, a backdrop click and the X
    (`EntityEditDialog.tsx:575-580, 591`) also drop it.

## Decisions

### 1. Where "the ALWAYS was forced" is recorded: a UI-only field on the inserter, `_forced_always`

Add `_forced_always?: true` to `InserterFormData` (`utils/configForm/formData.ts:35-45`), next to `_uuid`, with the same kind
of comment ("UI-only, never part of the exported config"). `updateIgnoredIngredients` sets it when it forces an ALWAYS and
is the only thing that sets it. It means "this inserter's ALWAYS was put there by Exclude from LCM, so Include may take it
away again".

Why this and not the alternatives:

| Option | Verdict |
|---|---|
| A list of forced inserter ids on the form (like `next_ids`) | Rejected. Ids are not stable: reorder reassigns them (`reorderWithIdReassignment`, edits.ts:33-48) and 1.9 renumbers on delete, so the list would go stale or need remapping in every edit. A field on the inserter travels with it through reorder, delete and renumber for free (`{ ...item, id }` spreads keep it). |
| A marker inside `enable_control` (`{ mode: 'ALWAYS', forced: true }`) | Rejected. It would clear itself when the modal replaces the object (nice), but it sits inside the engine's config-shaped `EnableControlOverrideConfig`, so it needs a deep strip to stay out of the export, the `configKey` (1.1) and the engine; and "Copy from another inserter" (`EnableControlModal.tsx:162-174`, `InserterConfigPanel.tsx:300-311`) would copy it onto a different inserter. |
| Something in `overrides` (for example a per-inserter list) | Rejected. `overrides` is passed to the engine whole by `formDataToConfig`. |
| Infer "forced" as ALWAYS plus all items ignored | Rejected. That is the bug: it cannot tell a deliberate ALWAYS from a forced one. |

How it behaves through every path that handles the form:

| Path | What happens to `_forced_always` | Where |
|---|---|---|
| localStorage save | **Kept.** The save replacer (`usePersistedConfigForm.ts:129-138`) drops only the key `_uuid`. | no change except the extraction below |
| Reload | **Kept.** `readSavedConfig` (lines 59-89) returns the parsed object as is; a form saved before this item simply has no flag, which reads as "not forced". No migration. | none |
| Engine check of the saved form (`worker/simulation.worker.ts:231-234`, `savedConfigProblem`) | Passes. `InserterConfigSchema` is a plain `z.object` (schema.ts:308), which strips unknown keys; `_uuid` and `next_ids` already pass through the same check. | none |
| Export Config, Validate, Generate, `configKey` (`App.tsx:192`) | **Stripped** by `formDataToConfig` (`configMapping.ts:123-136`). Nothing UI-only reaches the Config or the engine, and toggling the flag does not change `configKey`, so it cannot trigger 1.1's staleness banner by itself. | configMapping.ts |
| Import Config / Paste from Factorio / Reset | **Gone.** `configToFormData` (configMapping.ts:44-117) and the paste path (`App.tsx:297`) build fresh inserters. A file cannot say "forced". Consequence, accepted: after importing an exported build whose ALWAYS came from Exclude, that ALWAYS counts as the player's own and Include no longer removes it. This is the safe side of the bug (nothing is deleted), and a change from today. | none |
| Edit that replaces the rule (the modal's or the dialog's Save, which call `updateInserter` with an `overrides` key) | **Cleared.** The player has taken ownership of the rule. | `updateInserter`, edits.ts:167-174 |
| Edit that does not touch `overrides` (stack size, filters, ends) | Kept. | same |
| Reorder / delete / the renumbering in 1.9 / 1.3's undo snapshots | Travels with the inserter, because it is a field of the inserter. | none |

### 2. New `updateIgnoredIngredients` rules (`edits.ts:449-509`)

Per inserter that has a transfer-plan entry with at least one transfer (unchanged guard, lines 457-460):

1. **All its items are now excluded** (`allNowIgnored`):
   - mode is absent or `AUTO`: write `enable_control: { mode: 'ALWAYS' }` and `_forced_always: true`, keeping other
     `overrides` fields (as lines 467-472 do).
   - any other mode (ALWAYS set by the player, NEVER, CLOCKED, CONDITIONAL): **return the inserter unchanged**, same
     object, no flag added. An already forced inserter stays forced.
2. **Not all excluded, and `_forced_always` is set:**
   - mode is `ALWAYS`: remove `enable_control` (drop `overrides` if nothing else is left, as lines 477-483 do) and drop
     the flag from the inserter (the key must be absent, not `undefined`).
   - any other mode (a defensive case, since `updateInserter` clears the flag when the rule is replaced): keep the rule,
     drop only the flag.
3. Otherwise the inserter is unchanged.

The old `allPrevIgnored` check and the `prevIgnored` variable (lines 454, 463, 474) are replaced by the flag; delete them.
The `newOverrides` / `ignored_lcm_ingredients` part (lines 489-508) is untouched. The explicit-`{ mode: 'AUTO' }` case
counts as AUTO.

### 3. Backspace on an edge: delete the shortcut, and the code behind it

`<ReactFlow ... deleteKeyCode={null} />`. In 12.10.2 the prop is `deleteKeyCode?: KeyCode | null`
(`types/component-props.d.ts:275`); `null` means no key deletes anything (`useKeyPress(null)` watches no keys), whereas
omitting it uses `'Backspace'`. Delete is not bound by default, so nodes, edges and multi-selections can no longer be
deleted from the keyboard. The diagram has no other path to `onEdgesDelete`, so remove the dead code instead of leaving
it: `handleEdgesDelete` (lines 197-214), the `onEdgesDelete` prop (line 272), the `onDeleteInserter` entry in
`FlowContentProps` (line 71), in `FlowContent`'s destructure (line 89) and in the `<FlowContent>` call (line 426). Do
**not** touch `EntityEditDialog`'s `onDeleteInserter` (the dialog's Delete button still deletes; undo for it is 1.3).

### 4. One commit model for the inserter dialog: Save and Cancel, for both tabs

B6 offers "apply live everywhere with undo, or Save/Cancel everywhere". Chosen: **Save/Cancel everywhere**.

- Live-everywhere needs undo. The owner ruled out an undo history (PLAN "Safety net": Undo snackbars only), so a rule
  changed or wiped live (a CONDITIONAL tree replaced by clicking the ALWAYS radio) could not be taken back. A rule is
  also a compound thing that is wrong half-built (an empty rule set, an inverted range), and live writes would save it,
  change `configKey` (1.1's stale banner) and re-run the dagre layout behind the dialog on every keystroke.
- The rule editor already commits on Save everywhere it appears, including the List's `EnableControlModal`. Making the
  Config tab a draft too is what makes the dialog behave as one thing.
- Cost, accepted: in the Diagram dialog the Config tab no longer updates the diagram until Save. 3.2 will replace this
  panel with one editor shared with the List; the draft and footer built here are what it keeps.

The List's rows are unaffected: their inline fields stay live (they are single values, with no dialog), and the rule modal
is its own Save/Cancel dialog.

Behaviour, for both hosts of the rule editor:

- **No close on a backdrop click** in `EnableControlModal` (the rule modal). A fullscreen modal has no backdrop.
- **Esc, or the X, with unsaved changes** asks "Discard changes to {entityLabel}'s rule?" (for example "Discard changes to
  Inserter 3's rule?"; drills read "Drill 2's rule?"), with **Keep editing** (focused) and **Discard**. With no unsaved
  changes they close at once. The **Cancel** button is an explicit discard and closes without asking.
- **"Unsaved changes" means** the rule form would save something different from what it was opened with. It is computed by
  building the override the form would save and comparing it with the one built from the form's initial state (not with the
  stored override), so opening the form and touching nothing is never "dirty", and an untouched imported rule with an
  inverted range that Save would drop is not either.
- **Inserter dialog** (`EntityEditDialog` + `InserterConfigPanel`): both tabs stay mounted (hide the inactive one), so
  switching tabs loses nothing. The Config tab edits a local copy of the inserter (draft). A footer under the tabs has
  **Cancel** and **Save** (Save disabled until something changed, plus the text "Unsaved changes" beside it while there is).
  Save sends one `onUpdate(entityIndex, updates)` with only the changed fields among `source`, `sink`, `stack_size`,
  `filters`, plus `overrides` **only if the rule changed**, then closes the dialog. Esc, the X, a backdrop click with
  unsaved changes ask "Discard changes to {title}?" (title is `EntityEditDialog`'s `Inserter {id}`). With none they close at
  once. The dialog's Delete button deletes without asking (the entity is going away).
- The rule form inside the panel hides its own Cancel, Save and Clear Override buttons (the footer replaces them; picking
  AUTO clears the rule).

## Change

- Excluding an ingredient from the LCM never replaces a rule you wrote (CLOCKED, CONDITIONAL, NEVER or your own ALWAYS), and
  including it again removes only an ALWAYS that Exclude itself put there. This survives a reload.
- In the diagram, selecting a line and pressing Backspace (or Delete) does nothing. An inserter can no longer disappear
  from the keyboard.
- The enable-control modal ignores clicks outside it. Esc or X after you changed something asks "Discard changes to
  Inserter 3's rule?"; Esc with nothing changed closes it.
- In the diagram's inserter dialog, Config and Overrides are one form with Cancel and Save. Moving between the tabs keeps
  what you typed, and closing with unsaved changes asks first.
- The Transfer Plan's tooltip and note say that inserters with their own enable rule keep it.

## Tests

`clock-generator-ui` has vitest only and tests run in Node. No jsdom, no testing-library. UI behaviour is checked by the
screenshots below.

`utils/configForm/edits.test.ts` (extend `describe('overrides')`, lines 279-300; a `plan(...)` helper builds the
`SerializableTransferPlan` cast the existing test uses; build the inserters with the file's `inserter()` helper and
`edits.updateInserter`):
- Forces AUTO and absent overrides: ALWAYS plus `_forced_always: true` (the existing test, extended).
- Reverts only a forced ALWAYS: Include removes `enable_control`, removes the flag key (`'_forced_always' in ins` is
  false), and removes `overrides` when nothing else is left.
- Keeps other overrides when reverting (`animation` stays, `enable_control` goes).
- `it.each` CLOCKED, CONDITIONAL, NEVER: all items excluded leaves the inserter as the same object and without the flag;
  Include leaves it as the same object.
- A hand-set ALWAYS (no flag): excluded, then included, still ALWAYS.
- An explicit `{ mode: 'AUTO' }` counts as AUTO (forced, then reverted).
- Two items: excluding one does not force; excluding both forces; including one reverts.
- Idempotent: running it again with the same items leaves a forced inserter forced.
- Defensive: flag set with a non-ALWAYS mode, then not all excluded: the rule stays and the flag goes.
- `updateInserter` with `{ overrides: ... }` on a forced inserter drops the flag; with `{ stack_size: 12 }` keeps it.
- `reorderInserters` keeps the flag on the moved inserter (it travels with the inserter, not the id).

`utils/configForm/configMapping.test.ts` (extend `describe('formDataToConfig')`): a form with a flagged inserter gives a
config whose JSON has no `_forced_always` and whose inserter keeps its `ALWAYS` rule; `configToFormData` never sets the flag
(no inserter has the key).

`hooks/usePersistedConfigForm.test.ts`: `readSavedConfig(serializeConfig(form))` keeps `_forced_always` on the flagged
inserter, and `serializeConfig` still leaves out `_uuid`.

`utils/enableControlDraft.test.ts`:
- `buildEnableControlOverride` matches the old `handleSave` for each mode, including: AUTO and a stored `{ mode: 'AUTO' }`
  give `undefined`; CLOCKED drops ranges with `end <= start` and omits `period_duration_ticks` for `''`, `'0'`, `'-5'`;
  CONDITIONAL has `latch` only when enabled with a release condition.
- `enableControlDraftChanged` is false for an untouched draft of every mode, including a stored CLOCKED rule with an
  inverted range; true after changing the mode, a range end, the rule set, or the latch; false after changing a range while
  the mode is ALWAYS (hidden state is not saved); false after changing a value and changing it back.
