# Stability: disturbances and enable windows

This page was split out of GOALS.md on 2026-10-15; GOALS.md holds the goals.

## Disturbances

A clock must always recover. When any item of a build stops arriving for a while, or its output stops being taken, the machines run dry or fill up, and when the item comes back the build has to return to its target rate under the same clock by itself. Nobody should have to restart a build because one input ran out.

A clock that does this is stable, and one that does not is not. This is what "stable" has meant in this project: a stable clock is one that has recovery after every disturbance trial. A clock that only makes its setpoint from a clean start, with every machine full of ingredients and emptied of products, does not meet goal 1.

Builds are classified the same way. Some builds have no recovery after a disturbance whatever the clock, such as a loop of machines that does not start again once it has run dry. That is a limit of the build, and it is fine to say so and to give such a build the clocks it can have, as long as they are named for what they are.

Decided on 2026-10-10, after a clock for the advanced circuit build that makes its 704 a window cycle from a clean start made 608 and 624 in the game: one of its two plants held products when the clock started, and never caught up.

### How a clock is started

The default trial models the staged scaffold start: full input supplies, empty machines, buffers and inserters' hands, and clock phase 0 with no earlier run. The simulator's belts and infinity chests are supplies that are always full. A machine that makes its own ingredient (pentapod eggs) receives a one-time kick start: `overrides.kick_start_items` sets the amount (default 200). The machine takes at most what the game puts into it from outside an inserter, the larger of the item's stack and its automated insertion limit, + 64 (84 pentapod eggs and 114 iron bacteria of the samples, recorded in Factorio 2.1.24). Model warm-up follows, up to 10 window cycles with an earlier stop when the state repeats, before output is judged; longer checks assess the settled output where available. This does not promise the target in the first window cycle or convergence from an arbitrary live build state. The output cycle is still planned on a separate prepared build filled until its output is blocked (the prepare step). Where the belts move, the whole output swings a cycle can have are counted on that build with its belts backed up: a cold moving belt brings the first hands slower, and on the express moving half-tile pickups the plant got half the hands before its output blocked (2.75 hands against 5.5), which planned 2 output swings, a window cycle time of part ticks no moving clock can be made for, where observed windows hold at 3 (#269, 2026-10-20). Fractional swings keep the build's own count: it is their swings per cycle, not a cap.

The belts move where an input lane (a lane of a belt that an inserter takes from) is not a dead end. A belt that states one lane has only that lane: the generator does not read a lane end for its other side ([lane ends](belt-pickup/lane-ends.md#a-belt-with-one-lane-stated)).

Before, a clock started on that filled build with its output machines emptied, and no scaffold has that. A clock could hold from it and not from the scaffold's: the advanced circuit clock tightened by hand holds 704 a window cycle from the filled build and, from the staged start, falls short of it from some start phases (544 from the start phase 88), as the game's plant fell to 608 and 624.

The measured empty-hand intervals show a stable local order when several inserters take a product from one machine, the first up to its hand and the next what is left ([simulator](simulator.md), "Two inserters that take from one machine"). Which one it puts first is not known from a config, which carries no build order, so a clock holds and recovers only if it does under each order of them (decided 2026-10-25). The orders are settled by arithmetic on the clock's windows: only takers of one product that are enabled in the same tick can be served one before the other (an inserter on no window is enabled all the time). Where at most two are, the clock is run again with them the other way round (`ascending` beside the default `descending` config ids); where more are, under each rotation of the descending order, so that each comes first once and last once (two orders would leave the middle ones never first nor last); the groups of one build are turned together, with additional checks changing one contested source at a time while the others keep the default order. Joint changes of several sources are not exhausted. These are declared order samples, not a proof over every combination. The unshifted clock and its long run are run under each order, and every loss; the sampled clock offsets and lane phases stay under the default order, each kind of start varied on its own. Takers that are never enabled in the same tick take turns, and their clock is checked once, as one without competing takers is. A clock that holds under one order only is unstable, and the result says so ("the order inserters take from one machine"); one that gets back after a loss under one order only does not recover. The order of a run is `competing_takers_order` (`descending`, `ascending`, a rotation or a seed). The measured empty-hand intervals have a stable order; takers that both hold part of a hand were served in a varying order in one recording, often with the earlier sleep preceding the next pickup. The default simulator still uses a fixed order for each run. A clock is kept only if it holds under every declared order sample, so a clock the game runs well can be rejected for an order the game does not use for part hands.

Why the takers of one machine are there decides how they are best clocked (decided 2026-10-25). Where one machine feeds two or more machines of the same recipe, arithmetic asks first whether its output slot can give every taker its hands in one window together: what it holds at its block and makes over the window against the hands they draw. Where it can, the takers may share a window, and the clock is still checked under the declared order samples. Where it cannot, they take turns, each turn sized so that its machine gets what it needs over the cycle: then no order can tell, and nothing is left to the order the game happens to have. Even hands and grouped hands, in a chain of machines too, make the turns: the takers' windows open a share of the window cycle apart, in the order of the machines they fill, where what the machine made since their last window (up to its output block) and makes in the window is less than one hand of each, and the turns fit the window cycle without meeting. One supercapacitor plant that makes 11.69 a window cycle for two science plants with hands of 16 gets its two takers 20 ticks apart in a window cycle time of 40.

### Start dependence

By default every clock is selected and judged from the cold start alone, one run for each, and the generator says that start dependence was not checked (`start_dependence_note` of the result, and a line in the output of the scripts). A clock can reach its target from the cold start and settle elsewhere from another start: the same windows made 3,072 packs a window cycle from one start and 2,560 from another on the utility-science-480-lds-foundry-chain sample.

`overrides.check_start_dependence` in the config asks for it to be checked (the scripts in `clock-generator/scripts` take `START_DEPENDENCE=1`; the UI has no setting for it). Every clock is then also run, as its long run is, from:
- the cold start with the clock standing 30, 300, 700 and 1,000 ticks into its window cycle at the first tick (`cold+N`; the cold start itself is the 0; a clock whose window cycle time is not a whole number of ticks is tried unshifted only),
- the cold start with the competing inserters served in ascending config ids (`ascending`),
- the cold start with the competing inserters of each machine served in a random order, drawn from a fixed seed for the whole run, twice (`random-1`, `random-2`),
- the cold start with the clock's window deciders built in reverse order (`deciders-reversed`).

Every other run takes the deciders in the order the clock's blueprint builds them, as a build placed in one go has them. Where the window of an inserter opens with the window of the inserter that takes its machine's products, on a machine at its block, the order decides whether it takes its first items in the tick of the take or a tick later: the game updates the inserter of the last built decider first ([simulator](simulator.md), "When a waiting inserter acts"). A build put down by robots can have its deciders in any order; the reversed start turns every such pair the other way round.

The ordinary clock checks include 12 clock offsets and independent moving-lane phases. A start reaches the target when the clock holds its expected output in every window cycle of the judged part of the long run (for the cold start: all the checks of the generator). A clock that fails one of the checks that are not about the start (the one-window-cycle check, the sampled offsets or lane phases) fails from every start, even if each long run keeps up, so it is unstable and not start-dependent. The verdict of the clock from the starts:
- **stable**: it reaches its target from every start;
- **start-dependent**: it reaches it from some start and not from another, judged on the same checks;
- **unstable**: it reaches it from none, which is the verdict it would get with the check off.

A start-dependent clock is listed as unstable in the one word of the clock (`verdict`) and named by `assessment.start_dependence.verdict`; it is not selected as holding. The result says where it reaches the target and, for each start that settles elsewhere, the rate and the cycle it repeats in (items per window cycle, in the order they come), as one line: "start-dependent: reaches 480/s from cold, cold+300; settles at 2880 a window cycle (128.6/s, cycle 2784/2944/2912) from ascending." The numbers of every start are in `assessment.start_dependence.starts`.

The requested override alone is not evidence that a check completed. A null `assessment.start_dependence` can mean not requested or unavailable; the UI preserves the request and generation completion separately and counts actual returned starts. Fractional window cycle times omit shifted-phase samples. Holding from the modeled cold start, numerical rate, sampled-start verdict and evaluated recovery are separate facts: a start-dependent clock can hold its requested rate and have usable disturbance trial results while its overall verdict is unstable.

### The rate of a clock that fails its first check

The first check measures one window cycle, the eleventh after a cold start. A build whose state does not repeat with its clock moves different amounts in the window cycles that follow, so that one window cycle can be far from what the clock makes: on the processing unit circuit export sample the 1-swing clock moves 480 to 608 items in a window cycle of 528 ticks, 608 in the window cycle measured and 546 on average, and the game makes 546 (62.0 a second where the one window cycle said 69.09). A clock that fails its first check is therefore listed, ranked and described by the mean items a window cycle over the judged part of its long run, the figure a clock that fails the long run already gets, and its check says which it is (`as_built.output_basis`: `long-run mean`, or `one period` where the window cycle is too long for a long run). The check, the clocks that are made and every verdict are unchanged. The long run is made where the primary clock does not hold, since the rates rank the selection only where no clock holds. On the sample the clock with the highest rate by the mean is the 3-swing one (65.19 a second), which makes 66.4 in the game; the 1-swing clock the one window cycle favoured makes 62.0.

### How a clock is tried for it

Ordinary moving pickups are checked with independent phases on their two lanes, for both settled output and
loss recovery. An interruption can shift one lane relative to the other even when a shared clock shift passes.
The checks advance each lane through one stack-spacing cycle at its belt speed: 2 phase positions on turbo,
8 on express, 4 on fast and 8 on normal. Both matching lanes are combined for one pickup at a time; other
pickups keep their default phases. This bounded check does not enumerate joint phases across a conveyor
network or combine every lane phase with every clock offset. Backed-up pickups retain their finite
stationary-stock initialization. These are verification starts, not new config settings or a change to the
pickup timing rule.

The generator tries every clock that holds its expected output, in the simulator. A loss is one item that stops arriving from the belts and infinity chests of the build, or one output that is no longer taken away. Each loss is cut at four places in the clock window cycle, and at each it lasts a quarter, a half, three quarters and all of the time the build takes to stop. The build has stopped when nothing was moved, crafted or burned for a whole window cycle; a loss ends after 200 window cycles at the latest. When the item is back the build has 40 window cycles to be at exactly its expected output again, and has to stay there: where the state of the build at a window cycle's end repeats one it had at an earlier window cycle's end, what it did since it does for good and the trial ends there; where none repeats, its last 8 window cycles have to be at its expected output. A trial that was at its expected output in the 8 window cycles before those last 8 and falls short only in them runs on, until 40 window cycles at its expected output follow its last short one or its state repeats, 200 window cycles after the item is back at most, and is judged on them. Agricultural science's batched swings is back from the second window cycle after a loss of nutrients and then falls one to three hands short once, 33 to 37 window cycles after it; the game shows such a dip too, once in three losses, and is at its rate for 158 and 160 window cycles after the others (recorded 2026-10-24). Of the samples' trials that were not back at 40 window cycles, run on to 200, none that had 36 window cycles or more at its expected output fell short again; a trial short every few window cycles (a clock that does not hold its output from that start) is not one that runs on, nor is one whose output is counted in bins longer than the 40 window cycles (a subtick clock that repeats in 83 window cycles). A trial that is back in its 40 window cycles is judged as before. Agricultural science's recommended clock, batched swings since this rule (2,673.8 wakeups a minute, where the 2-swing clock selected before has 3,089.8), takes 37 window cycles to be back for good after its slowest trial. The trials are the same for every build and every clock, and are defined in `clock-generator/src/crafting/disturbance-trial.ts`. A clock is tried no further than its first failure. The 16 trials of a loss stop at the first that does not go back to its rate, and the losses of a clock (the supplies in the order the inserters meet them, then the outputs, the product's first) stop at the first loss after which it does not go back to its rate at the modeled lane phase; the losses after it are not tried, and the verdict lists them as `disturbance_trial.not_tried`. A loss that a moving-belt clock misses only from another lane phase does not stop the rest, so that cause stays apart from the others. A clock that goes back to its rate after every loss runs every trial, and its verdict is the same as when all were tried. On the blast's 44 jobs that have a clock which does not go back to its rate, the loss runs take half the simulated ticks (498 M to 252 M) and those jobs generate in 68% of the time (750.6 s to 509.8 s; the iron gear wheel build at 9.97 a second (no longer a sample) 105.1 s to 19.1 s as it is, 100.8 s to 13.1 s with backed-up belts); 79 losses of 45 verdicts are not tried, 69 of which fail on a clock that is tried on all of them, and the 10 others (metallurgic science's coal and product, for one) are the ones the verdict no longer says it gets back from. No selection and no verdict changed. Stopping inside a loss alone takes 28% of the loss ticks and stopping at the first failing loss alone 18% (a census of 788 clocks); the order of the losses moves the two together between 30.4% and 32.1%, and the order above is 0.5 points under the best possible one, so it is not searched for.

The output is counted in bins of a window cycle from the tick the item is back, which is not where the clock counts 1. Where the bins of a repeat are not each at the expected output, the repeat is counted again by the window cycles of the clock. A window cycle of the clock starts at the tick the clock counts 1. A hand that drops a tick before the edge of a bin or a tick after it is then in the correct window cycle. The trial is back if each window cycle of the repeat on the clock is at the expected output, by the same rules as a bin (`judgedOnTheClock`). The bins before the repeat are the bins it took to be back. A clock whose window cycle is not a whole number of ticks is counted in the whole ticks after which it repeats. Its count starts again at that point. The run with nothing cut checks what the clock holds, and so do the runs from the other lane phases. They are judged in their bins only. A backlog put into a container at once (a result that comes by chance, below) is a loss of the trials too: its repeat is counted on the clock in the same way, and it has to be back from the first bin. The export belts are judged in the bins only. A trial that is back on the clock and gives an export belt less than its consumers take in its bins is not back.

A build whose items spoil is tried with losses shorter than three quarters of the shortest spoil time of the items its machines take, make and burn (the game data's spoil times): 3 min 45 s on agricultural science (nutrients), 45 s on iron bacteria cultivation (iron bacteria), 3 min on the jelly builds and 2 min 15 s on biochamber fuel (yumako mash). A loss that runs its course comes back at the place in the window cycle it was cut at, as on any build, or at the limit where that comes first; the losses that end part of the way are shares of the time the build took to stop, or of the limit. On iron bacteria cultivation that cuts its longest trials from 57.6 s (3,456 ticks) to 45 s; no clock of any sample moves. In the game a longer loss spoils what the build holds, and no clock brings it back: iron bacteria cultivation did not go back to its rate after 57.6 s without bioflux, nor agricultural science after 400 s without nutrients or bioflux, or with its output not taken; both got back after losses of three quarters of the spoil time and more (45 s, 272 s; recorded 2026-10-24). The limit is below the spoil time since the items a loss leaves in the machines are older than the loss, and an item that comes back takes a while to reach them. The web app says the limit where it shows recovery.

A clock that holds its expected output and does not go back to its rate after a loss is not stable. It is listed as a clock with no recovery, with the losses that break it, and it is only selected when no clock of the build survives. On the samples the selection changed for two builds: agricultural science, whose recommended clock did not go back to its rate after a loss of nutrients, and military science, where from the staged start no clock is stable: two (the selected one is among them) hold their output and are broken by a loss, and the others fall short of it from some starts, because the machine that makes the grenades can stop with its output full and too little iron left to craft again, and then makes half of its grenades and packs in a window cycle. The metallurgic science sample (`record/config-METALLURGIC_SCIENCE_45.json`) has one stable clock, its recommended clock, `derived-subtick`: it holds 45 a second with backed-up belts, and a stable clock has recovery after every disturbance trial, a stop of the tungsten ore supply among them. The seven other clocks are `unstable` and hold the setpoint on none, and no clock has the verdict `no recovery`. The record has one verdict for each clock, not one for each disturbance trial.

A clock the trials could not be run on is not known to go back to its rate. The trials count the output by the window cycle, so a clock whose window cycle time is not a whole number of ticks needs the whole ticks it repeats in, its subtick clock; one with none (a fraction of a scale above 1,000) cannot be tried. Such a clock keeps the verdict of what it holds, and the result says why it was not tried (`assessment.disturbance_trial_not_tried`; the web app shows it under "Recovers: Unavailable"). It ranks below every clock that holds the setpoint and was tried and goes back to its rate, and above every clock that does not meet the setpoint, those that hold it and do not go back to its rate included; while it is the best on offer the searches still run (`ClockRanking.recovery_untried`, `clock-generator/src/crafting/rank.ts`). Before 0.20.0 it was taken as stable, and on the car's Sidecar paste at its suggested maximum, 80.78/s, an untried clock beat every clock that was tried.

A window cycle time that is not a whole number of ticks is exported with a subtick clock where one exists; with no subtick clock, rounded down to whole ticks, as its blueprint counts it. Before 0.26.0 a clock with a subtick clock was also offered rounded; that rounded clock was never selected on any sample or fixture. A rounded clock is listed as the clock it is, at the rate it runs the build at, and labelled with how much it runs fast ("clock rounded to 2888 ticks, runs 0.02% fast"). It meets goal 1 when it runs at most 0.1% faster than the target and no faster than the machines that make the target item can make together, and is then tried as a clock of whole ticks on its own window cycle time: the clock-only check with its start phases, moving lane phases and long run, the disturbance trials, and the other starts when they are asked for (`roundedClockTrial`, `clock-generator/src/crafting/trial.ts`). It ranks below every clock that meets the setpoint exactly and was tried, and above every other (`ClockRanking.runs_fast`, `rank.ts`); while it is the best on offer the searches still run for an exact one. A rounded clock further off keeps the verdict of the exact window cycle time and does not meet the setpoint. The case is the iron gear wheel build at 9.97 a second (no longer a sample): its batched clock's window cycle time is 2,888.666 ticks (2880000/997, whose subtick clock does not fit a 32-bit signal), its blueprint counts 2,888 and runs 0.02% fast, and in the game it held 480 gears a window cycle and got back from two cuts of the iron ore and a blocked output (#332); on its own window cycle time the simulator finds it getting back from every loss too, where every subtick clock of the exact rate does not. On the car's Sidecar paste at its suggested maximum, 80.78/s, no rounded clock meets goal 1: the one of 5 output swings, 356.524 ticks, runs 0.15% fast, and the batched one, 0.08% fast, above what the furnaces make. Before 0.20.0 a clock with no subtick clock was listed at its exact window cycle time and rate, and a rounded clock was never taken to meet the setpoint.

When the recommended clock does not meet goal 1, the result says why (`why_not_stable`; the web app shows it on the result card), in one of four causes read off what the clocks already carry (`clock-generator/src/crafting/why-not-stable.ts`). **Output chest full:** the run that failed the clock ended with a chest its output goes into full, and no inserter of the build takes from it (`full_output_chests` of the as-built check: the chest, its item, what it held and the output inserters that drop into it); it is told before the others, with the chest named as the web form names it. A chest that fills only after the simulated run (the warm-up, the first window cycle and the ten-minute long run) gives a stable verdict while the form still warns. **Moving lane phases:** the clock is made for a moving belt, holds from the modeled start, and falls short only from a start where a lane reaches a pickup in another phase, either at the start (`as_built.failed_pickup_phases`) or after every loss that stops it going back to its rate (`disturbance_trial.broken_at_other_lane_phases`, the losses it gets back from at the modeled phase and not at another). **No recovery:** it holds the target and does not go back to its rate after the losses it names; where the build's tightest machine would take more than the 40 window cycles to make up one window cycle of crafting at its spare ticks, that is said too. **Nothing holds:** the nearest clock's rate against the target, and the alternatives that could not be made, with the generator's reasons (`not_made`; the output chest message lists them too). Coordinated Sources is among them where the generator makes no clock of it, or makes the same clock as one made before it, with the parts it took no windows from and why ([Coordinated Sources](clock-candidates.md#coordinated-sources)). A clock that misses a loss from the modeled start and another only from other lane phases is told as no recovery, with both.

The saved 336-tick Thaeln clock, made with the coal out of the window cycle time (`overrides.ignored_lcm_ingredients`), shows the edge of a bin. After a partial loss of coal, its trial settles into a repeat whose bins read
`792,744,792,744`. Counted on the clock, each window cycle of that repeat holds 768, the expected output. So the clock is
back after that loss, and it is stable. The requirement stays exact in each window cycle, counted on the clock. On
automation science, one clock (takt batches, 1 output swing) makes 48 in one window cycle of the clock and 16 in another.
It must make 32. Over 15 window cycles that is the expected output, but a repeat that does this is not back.

Where the copies of a build share a lane, the trials are made again on the copies together, with the supply stopped at the entry of each shared lane (see "The disturbance trials on the copies" below).

One kind of build is left out of this. Where a build has a deadlock risk (see "Two inserters that bring the same item"), its clocks are tried and their verdicts shown, and the verdict does not decide which is selected.

This can cost wakeups: goal 1 comes first. The clock selected for agricultural science then had 3,950 a minute where the one before had 2,543. Since the rules of issue 152 (2026-10-14, "When a waiting inserter acts") batched swings gets back from every loss on that build and is selected again, at 3,651. Its trials of a loss of nutrients then fell a hand short in a late window cycle, and the 2-swing clock was selected, until such a trial ran on (above): batched swings is selected again, at 2,673.8.

Fluids are not cut, as the simulator leaves them out. The harness has no setting that cuts a supply, but it runs Lua it is given, and the belt-pickup clock tests in `clock-generator/tests/game/builds` use this to cut supplies in the game: twice, at fixed window cycles of the run, an ingredient is taken off every belt of the build (a different one each time where the build has two), the output is blocked once between those cuts, and the output of every window cycle before and after is counted. A chest-fed build at belt stack sizes 1–4 has its output alone blocked, for 24 window cycles. The game fills the output belt before the output stops, where the trials hold the output inserter at once; that moves output within the blocked window cycles and the few after the release, and changes no verdict (see the [simulator](simulator.md#a-stack-inserter-dropping-onto-a-moving-lane)). Those builds have one machine each, and these cuts are not the trials above: the trials have not been run in the game, and no sample build has had a supply cut there.

The trials do not catch the clock that led to this rule. The advanced circuit clock with windows of 4 ticks gets back from all 48 of its trials in the simulator, and made 608 and 624 of 704 in the game. That is a known gap. From the staged start the check of 12 start phases does fail that clock, at the start phase 88 (544 of 704), so the clock is no longer taken for one that meets goal 1; the disturbance trials are only run on clocks that hold, and still do not see it. The trials are not to be changed until they fail that one clock: a check that is tuned to a build is no longer a check for any build.

### Export belts

A belt lane with a consumption rate (`consumption_per_second`, "Consumed /s" in the form) is emptied by consumers outside the config, so the inserters that fill it have to put that rate on it. A clock is stable only if each export belt gets that rate (`clock-generator/src/crafting/export-delivery.ts`). The lanes of one belt that carry the same item are one demand, the sum of their rates, filled by all the inserters that put the item on the belt: two lanes of 40 a second need 80 a second from the inserters together, not 40 from each (before 0.22.0 each lane was compared with what all the inserters moved, so a belt that got half passed). It is judged where the output is:
- in the window cycle of the first check, to within an item;
- in each judged bin of the long run (and so from every start of the start-dependence check), to within a hand of the largest inserter that fills it, and over the judged part as a whole to within a hand, or, for a run proven to repeat, to within an item.

Only a shortfall counts. The simulator does not throttle an export belt (the free-running circuit export build puts 141 a second on its belt where the game, whose consumers take 80, lets 80 through), so a clock that puts more on it than the consumers take is not held against; one that takes what the build needs for its own target fails the target on its own. A clock that fails here is listed unstable, `assessment.holds` is false, and the shortfall is in `stability_check.as_built.export_shortfalls` (belt, item, what the consumers take, what it got, the inserters that fill it) and told on the result card ("export belt short", `why_not_stable`). The disturbance trials and the exhaustive start phases (`CLOCK_PROOF_PHASES=1`) hold the exports to it too, in the bins they judge the output on and from the runs they already make: a clock that is back at its expected output after a loss and gives an export belt less than its consumers take has not recovered.

### A build whose results come by chance

A recycler's results come by chance, so no window cycle of its clock in the game is exactly like the next. The simulator makes them at their expected amounts ([simulator.md](simulator.md#a-machine-that-places-its-results-itself)), so its run repeats and is judged as any other: the clock holds when that run makes the target every window cycle from every start, and has recovery when that run goes back to it after each loss. On top of that, every window that carries a result that comes by chance has room for what a window cycle gives of it over its expected amount in all but 1 in 740 window cycles, the binomial's own quantile; the clock reports that room and what the machine's crafting has to spare (`random_margins` of the result). Where what it gives comes back into it, the clock is tried with the backlog of it the container takes up in all but 1 in 740 window cycles (`CraftingMargin.backlog`: the variance a window cycle of what comes back times ln 740.7 over twice the spare crafts less what they give back; 67 ore on the exact-speed ore voider) put into that container at once, at each of the four places of a loss: the clock has to hold its output in every window cycle through it, or it does not count as stable ("iron ore comes over its mean"). In the game a batched clock of the ore voider lost a hand of ore in 5 of 1,900 window cycles after runs of returns over the mean, its taker emptying the car into the recycler past its insertion limit; the trial costs it the same hand. In the game such a clock holds when its mean over a long run is within the binomial's range of the target (3 standard deviations of a window cycle's amount over the square root of the window cycles) and no container it places into stays full; it has recovery when the backlog in that container drains, at the room a window cycle, back to its normal level. Where the results come too rarely for whole hands in a window cycle, each set of takers has one window a window cycle sized by that share and by the backlog a lost output leaves ([simulator.md](simulator.md#results-that-come-by-small-chances)): the simulator runs it for 20 window cycles and judges, beside the target, that every result went into the container and was taken out as it came; the loss of a supply is tried as for any clock. A result's output is not run until the build stops (with copper cable not taken away the silo takes 4,000 of them, 200 window cycles of 96 s): its recovery is the arithmetic's, the backlog drained at the window's margin (what the window takes a window cycle over the expected count) within the 32 window cycles a trial gives, and each trial confirms it. The output is not taken away for 4 window cycles (fewer where the window's worst backlog comes sooner), and the build is run for twice the window cycles the margin drains what that left, with the 8 a recovery holds, between 16 and 64; it has recovered when it is back at its output and the results' count in the container is back within a window cycle's worth at the level and a hand (`resultLossTrialOf`).

### Copies that share a lane

Where the copies of a build take from one lane, each clock that holds on one copy is run again with every copy on that lane ([simulator](simulator.md#copies-that-take-from-one-lane)). The verdict of that run has two checks (`clock-generator/src/crafting/shared-lane-verdict.ts`):

1. **The takers.** Each inserter of each copy that takes from a shared lane is compared with the same inserter in a run of one copy alone, over the whole window cycles of the second half of the run. An inserter that puts down fewer of the lane's items than in the run of one copy is short.
2. **The machines and the output inserters.** A shortfall is a loss only where a machine or an output inserter of a copy is behind its target in the same run, over the same window cycles: a machine by more than one craft, an output inserter by more than one hand. A machine's target is the crafts that one copy needs from it for the setpoint. An output inserter's target is the items of the product that it puts down in the output cycle. Where no machine and no output inserter is behind, the shortfall is stock that moved between the two runs, and the clock holds.

Where the config states its output belt, each copy's output inserter puts its stacks onto it. A copy can have a side belt that is full at its join onto the output belt. Then it holds its hand, its machines fill up, and its takers take less from the lane. Where such a copy held a hand in the judged window cycles, the run of the copies is made once more. In that run, each output inserter drops on a tile of its own. The loss names a machine or an output inserter of the copy. If it is further behind with the output belt by more than one craft or hand, the output belt is the cause. Then the loss says that the side belt of the copy is full at its join (`join_full`), with the hands that were held. It does not say that the lane gives the copy too few items. The description of the clock says "It is not stable on its output belt." If the output belt is not the cause, the loss names the lane as before. One more sentence gives the held hands (`side_belt_waits`).

A part copy is the fraction of `setpoint.copies` after the whole copies: 3.5 copies are three whole copies and one part copy. On each shared lane, the part copy holds that fraction of a copy's takers, rounded up, with the machines that they feed and what those machines need. So a machine of a part copy can have fewer takers than the same machine of a whole copy, and it makes only what its takers take. If it is held to the target of a whole copy, it is always behind, and each shortfall of a taker on the lane is a loss.

So a machine of a part copy is held to the target of a whole copy times the share of the machine's takers' transfers that the part copy holds. A transfer is one hand that an inserter moves in the output cycle. A machine that no inserter takes from, or whose takers move nothing, keeps the target of a whole copy. The machines of a whole copy keep their targets.

An example: in a whole copy, a machine has four takers, and each moves one hand in the output cycle. In the judged window cycles, the machine must make 100 crafts. The part copy holds two of the four takers, so it holds 2 of 4 hands, and its machine is held to 50 crafts. If it makes 50, it is not behind. If it makes 45, it is 5 crafts behind, and a taker's shortfall on the lane is a loss.

- A machine of a part copy that makes less than its share by more than one craft is behind, and the loss stands.
- An output inserter of a part copy is held to its own target, the same as an output inserter of a whole copy.

Not shown: no part copy has been recorded in the game. The rule comes from the model only.

#### When the shared lanes cannot be checked

The check puts the copies one after another along each lane that they share, `copy_offset` apart in the direction in which the items of the lane move. A belt can state a `flow_direction` across the copy spacing: for example, the copies stand along x and the belt moves its items south. Then the copies stand at the same place on the lane, and the check cannot put them on it. The generator refuses such a config before it makes a clock. The message names the belt, its flow direction and the axis of the copies. To correct the config, state the direction in which the items move along the row of copies, or remove the flow direction from the belt (`clock-generator/src/crafting/shared-lane-lanes.ts`).

The check can stop with an error for another reason. Then the clock does not pass the check: it gets a shared-lane loss that says that the lanes could not be checked, with the message of the error, and its verdict is unstable. The result shows this loss in the description of the clock ("It is not counted as stable. The lanes its copies share could not be checked: ...") and in `assessment.shared_lane_losses`. When it is the recommended clock, the note that tells why no clock is stable gives the same reason. The disturbance trials on the copies are not made for such a clock. An error of the generator itself stops the generation.

#### The disturbance trials on the copies

The disturbance trials of one copy (see "How a clock is tried for it") are made again on the copies together. They are made for a clock that gets back from every loss on one copy and has no loss on the shared lanes. The run is the run of the copies that the check above makes, from the same cold start, with the same losses, places and lengths as on one copy (`clock-generator/src/crafting/shared-lane-trial.ts`).

- **A supply stop.** The entry of each shared lane that carries the item is closed. The lane gets no more items, and the takers of the copies empty it from the entry downstream. The belt of the lane does not withhold the item, so a hand stops only when its reach of the lane is empty. Every other belt and infinity chest withholds the item, as on one copy. When the item comes back, the entry opens and the lane fills again from the entry.
- **An output blockage.** The product is refused in the chests and on the belts of every copy, as on one copy. Where the config states its output belt, the infinite end of the output belt is shut instead: the belt lane is blocked from draining to the belt it joins. Every lane upstream backs up from there, and a hand is held only when its side belt is full ([simulator](simulator.md#the-output-belt-of-the-copies)). The chests the product goes into refuse it as on one copy. When the blockage ends, the infinite end opens again.

After each trial, each copy is judged on its own, by the rules of one copy. Its output has to be the expected output of one copy alone in every window cycle: from the window cycle at which the state of the run repeats, the lanes included, or in its last 8 window cycles where no state repeats. Where the state repeats, each copy's repeat is counted on the clock as on one copy. A trial that a copy is not back from runs on until the lanes settle: until the state of the run repeats, at most 200 window cycles after the item is back. Where no state repeats by then, the last 40 window cycles are judged. A copy that is not back makes the clock one with no recovery. The result names the loss, the shared lanes, the copies from the entry that are not back and the items a window cycle that each of them ends at (`disturbance_trial.on_copies`). The trials stop at the first loss after which a copy is not back.

The run with nothing cut is judged first, in the same way, but in its bins only. Where a copy is not at the expected output in every window cycle of it, the trials on the copies are not made, and `on_copies.not_tried` says why. A part copy that holds only some of the output inserters is not judged (`on_copies.copies_not_judged`). The other lane phases and the other orders of the takers are tried on one copy only. A build whose copies share no lane is not run on copies. `overrides.disturbance_trials_on_copies: false` makes the trials on one copy only.

The trials on one copy and the check of the shared lanes found no loss for this clock. The trials on the copies find that copy 3 ends at 304, 272 and 304 a window cycle after the accumulator stops, where one copy makes 352, and the other copies at 352.

A trial on the copies starts with all the lanes full and supplied at the entry. A build in the game does not start in that condition. Thus the stops that keep a copy short in the trials can be different from those in the game. #### What the result says was checked

The result lists each lane of the build one time (`lanes`): its item, its **lane role**, its **lane end** and where the end comes from (`end_given_by`: the lane, the `backed_up_belts` switch, an export lane, or the role), its sharing, its supply rate and its capacity. A build of one copy has this list too.

Each clock of a build of copies has `checked_lanes` (`clock-generator/src/crafting/checked-lanes.ts`). It has one row for each lane that the copies share and that has an item and a role. A lane that is per copy has no row. A row gives what the copies take from the lane or drop onto it together, in items a second, and a state:

- **Holds.** The run of the copies finds no loss on the lane. At the output belt, the row gives the copies whose side belt held hands at their join, and in how many swings. On a clock that is not stable on a shared lane, the label is "Not the cause".
- **Short.** A copy misses swings on the lane. The row gives each copy, with its swings missed of the swings that it makes alone. Two takers of one copy on the lane are added together.
- **Join full.** The output belt is the cause: the side belt of a copy is full at its join. The row gives the swings missed of the swings that the target needs.
- **Takes less.** The copy takes less from the lane because its join is full. Where the run without the output belt shows the copy short on the lane too, the row says so.
- **Rate fits.** An output belt that is a plain belt in `belts` is not run. The sum of the drops of the copies is not more than what the lane carries.
- **Not checked.** The check does not run the lane, for the reason that the row gives: for example, the build drops items onto the belt.
- **Not run with the copies.** The clock does not hold its output on one copy, so the copies are not run. No row of such a clock holds.

The short rows and the rows of a full join come first. The line of a clock says if the copies were run together. It says if every copy gets its items, and if a copy misses swings at the output belt. On plain output belts, it says that only the sum of the drops is checked. It names the chest that the output goes into.

A clock that is not stable on a shared lane has the parts of its cause, each a sentence with its numbers:

- The headline: the swings that each copy misses.
- The cause, only where the run of the copies shows it. The run records each tick in which the hand of a taker holds items and takes none. It records if the reach of the lane of the held item is empty. It also records if the output of the machine of the taker is full. A window cycle in which a copy makes fewer swings than alone counts as many missed swings. An empty reach is the gap of the copy before where a taker of that copy took the item earlier. The time between is the ticks that an item takes from that copy to this copy. The cause gives the count of each, and of the swings that show both. At a full join, the cause is the full side belt.
- The reason (`reason`), as a code with its counts. Where at least one missed swing shows the gap of the copy before, the code is `belt_gaps`, with the swings missed and the count of them that show the gap. At a full join, the code is `join_full`, with the output swings missed and the output swings that the target needs. Another loss on a lane has no reason. The result gives no sentence for a code. The web app shows a text for the code next to **Underproduces**.
- The reason from the spacing, only where the run shows the gap of the copy before: the tiles between the copies, the ticks that an item takes over them, and the window cycle. It does not decide a verdict.
- Where and how much: each taker of each copy by its items, with its swings missed.
- One copy alone: what the same inserter makes in the run of one copy alone.
- What changes it: the most copies on the shared lanes whose own run holds, found by bisection. Also another clock of the result that holds with all the copies.

In 5 of them, the output of its assembling machine is full, and 2 show both. With 8 copies on the lanes, every copy makes every swing.

### What a stable verdict proves

A clock called stable is proven only where its check reports `long_run_proven` or `start_phases_proven` (#258), and then only under the simulator's mechanics. Everywhere else the verdict rests on a sample. The lane phases, the loss grid and the start-dependence starts described above are samples too.

**Sampled, not proven:**
- The default start phases are a sample; every phase is checked only with `CLOCK_PROOF_PHASES=1`.
- Long runs that never repeat, such as agricultural science and metallurgic science's fractional window cycle time.
- The orders of competing takers: two orders where at most two are enabled together, the rotations where more are; their combinations across machines are not tried.

## Active Inserter Windows

An active inserter window is defined as a period where an inserter receives a signal from a decider combinator telling it to be enabled. During that window it has the ability to actively do work and transfer materials from a source to a sink.


### Active Inserter Windows Definition of Good

A good clock output reduces an active inserter window to run just in time to transfer the items the machine needs to keep on crafting to meet the target production rate. This means that many times the inserter will transfer multiple times back to back to meet the transfer goal. Reducing the duration of an active window can lead to instability. The measure for a good active inserter window is when the inserter can pick up the items it needs in the least number of ticks. The output from a machine has also another special consideration which is that it should attempt to pick up the full stack size whenever possible. If it cannot do this, it should minimize the amount of time sitting idle over the machine, picking up the output one craft at a time.


## Hands in groups

Where the windows a plan observes do not hold, windows made from the plan's hands and the sources of the build take their place, if they hold (`src/crafting/candidates/round-robin-polling.ts`, called from `generateClockForConfig`; it is no clock of its own and no search). It began as the clock built by hand for the grenade build (`intermediates/grenade`), turned into a rule, and it has the order of a chain of machines and whole hands for the utility science 480 build (`science/utility/utility-480-lds-foundry-chain`). It applies to a build whose inserters take from a machine, a chest or a belt and put into a machine, whose machines hand their products on to a belt or a chest, and whose drills drop into machines. Elsewhere it declines and the planned windows stay (the planning log says why).

1. **One run of hands.** An inserter that moves `h` hands a window cycle into a machine gets one window that opens at the tick its first hand starts and is long enough to start every hand the machine can take, `S` of them, and one more tick for the combinator: `(S - 1) x cycle + 2` ticks. Where it takes from a belt, the window has room for one more hand too. `S` is `h + 1`: `h x cycle + 1` is the shortest window that starts the last hand (grenade build: 41 ticks; 36 to 40 move nothing), and one more tick is the margin. The hands must follow each other under the limit (`computeMaxSwingsPerSubCycle`). The same windows are also made with `S = h` (the surplus guard) for an inserter whose machine would take more than one hand over (a surplus hand it keeps), which are not on a belt: the utility science 480 build's plastic into the foundries, four hands in 26 ticks (a window for a fifth start does not hold there).
2. **Rule F: fractions of a hand.** In a chain, an inserter that fills a machine and moves a fraction of a hand a cycle (the coal inserter's 15/8) is planned at the next whole number of hands, so its count is whole in one cycle; the machine's limit refuses the surplus and it moves the fraction on average. The window cycle is the cycles in which the inserters that take the output out move whole hands, and the plan is made again for them (`overrides.lcm`, unless the config sets it): one cycle on the utility science 480 build, 168 ticks, in place of the eight (1,344) the coal asks for.
3. **Groups for a source that cannot serve everyone.** A source machine holds its output block and makes its product at a rate, so the takers of one source cannot all draw their hands together. The machines they fill are split into the fewest groups for which each group's draw (`takers x h x hand`) fits what the source holds plus what it makes in a window, and the groups open their windows evenly over the window cycle. Where more than one dealing of the machines to the groups serves every source, and the output inserters have places on a shared belt, the dealing whose output hands land on each other least is taken (`dropTieBreak` in `src/config/drop-spacing.ts`: the machines in the order of their ids, or in the order of the belt, dealt round robin or in blocks; the first with the fewest pairs wins, so the order of ids on a tie); it is arithmetic on the places and ticks, with no run of the build. On the grenade build it puts the two machines of one row of the belt in one group (inserters 1 and 2, then 7 and 8), as the hand-made clock does. The grenade build's foundry holds 100 plates and makes 3.74 a tick: four takers draw 320 plates in 42 ticks against 257 there, two draw 160. One group gives 49 of 64 in the simulator, two give 64. In a chain of machines the test is not made (it would ask for three groups on the utility science 480 build, where one holds in the simulator and in the game); an inserter that puts a machine's product into a chest that machines are filled from is left out of it. Hands in bursts in place of groups (the grenade build's four iron inserters in a 2-2-1 split, with pauses for the foundry to refill) also hold and have recovery there, but at 192.9 wakeups a minute against 118.9 for two groups, and are not exact on the full build in the game; the rule makes groups only. The blueprint shows the groups: the combinators of a group stand together in the order of its turn (the output swings, the inputs, the drills), two empty tiles between groups, and the first of each group says its turn. Only the positions, the order of the green wire along the row and the text change; the entities keep the order of their ids, which is the order they are built in (the game updates the inserters enabled in one tick in the reverse of it).
4. **Output.** One hand a window cycle in a window of one tick at the start of the machine's group; an output of more hands in `h x cycle + 1` ticks (the utility science 480 build: three hands in 37; 25 to 36 move too little). The machine's input windows open at or after the output, never before it (the grenade build holds from 0 to 38 ticks after it and fails 2 before): 2 ticks after the output's last hand starts.
5. **Drills.** A window of the planned length, at least two ticks (a window of one tick drops nothing), opening with the machine's inputs.
6. **A chain of machines.** The rule applies outside a chain only to what the grenade build is: sources that are machines or chests, one item, whole hands, one output hand. In a chain (a machine or a chest that something takes from is itself filled) the inserters may take from belts and from machines that are filled, an inserter that puts a machine's product into a chest that others take from counts as a taker of that machine, and the windows go in the order of the chain from the output machines: the output window, then, as its last hand starts, the inputs of the output machines from belts, chests and machines nothing fills, then those from machines that are filled, each when the previous stage's window ends; an inserter that fills a source machine opens after the one that takes from it, so the machine is emptied before it is filled: staged, 16 ticks after it, or compact, 1 tick after it (the utility science 480 build: the plastic has to open within 3 ticks of the low density structure, so only compact holds there). The order is read off the config's dependency graph, with no item names. On the utility science 480 build: output 0-36, units and frames 26-53, low density structure 54-71, plastic 55-80, coal 56-83.
7. **A margin.** The clock is offered only if it holds, and still holds when every group of windows (the inserters and drills that share windows) is moved a tick either way with the others where they are (one run of the build each, `holdsWithMargin`). A clock that holds at one placement and not next to it is left out (working rule 3). Cell 09's clock holds when its output group is moved -4 to +14 ticks, units -14 to +18, low density structure -5 to +1, plastic -1 to +6, coal -30 to +4. With "Backed-up belts" on, the utility science 480 build's windows have no belt slack and a group does not hold a tick off, so no grouped clock is offered there.
8. **An inserter busy the whole cycle.** An inserter whose hands, rounded up, take the window cycle time (`(S - 1) x cycle + 2` plus the offset is the window cycle time or more: three hands of 8 ticks in a cycle of 24 on the circuit export build) is busy all the time, and a window would only leave gaps between hands that follow each other, so it gets none and stays enabled. It still counts in the order of the chain, where the others are placed as if it had its window. Before, such a window refused the whole way of making windows, and the ways with fewer starts (item 1) were the only ones left.
9. **From every start phase, then the ranking.** The margin of item 7 runs the build from the cold start only. The windows are made in all four ways (staged or compact, each with or without the surplus guard of item 1; ways that make the same windows are one), and of the ways that hold with their margin and from every start phase of the clock-only check the clock is the one the selection would rank first: one that gets back from every disturbance trial, then the fewest wakeups a minute, then the fewest windows, the first way on a tie. The losses are tried in that order until a clock gets back; a generation keeps the verdicts, so the clock kept does not try them again. A way that has the margin but not the start phases is kept only if none holds. Each way is the only one that holds on some sample: staged on the advanced circuit build at 90 a second (no longer a sample), staged with the guard on the utility science 480 build with its belts backed up (112 ticks), compact on the circuit export build (24 ticks: staged has a margin there and fails from one start phase), compact with the guard on the utility science 480 build. On the productivity module chain staged, staged with the guard and compact hold, at 843.8, 575.6 and 1,103.1 wakeups a minute: staged with the guard is the clock, where before the first that held (staged) was.

10. **Shared windows.** The same windows are also made with the inserters that take into their machines and open on the same tick sharing one window, the longest any of them needs (`shared_windows` of the generation options). Inserters of one window share one decider, so the clock has fewer decider combinators; an inserter that needs fewer hands than the window stays enabled longer than it must, which can add wakeups (the productivity module chain: 12 deciders and 575.6 wakeups a minute with separate windows, 6 and 1,254.4 shared). The shared clock is listed beside the separate one as `<alternative>-shared`, except for the other output swing counts and fractional swings (since 0.26.0: on no sample or fixture was theirs selected), only where it holds from every start, passes the margin of item 7 and gets back from every disturbance trial; the usual ranking picks between them. Military science selects it: its separate windows have no recovery. The list of clocks has a Deciders column, and the clock with the fewest is named Fewest deciders only when it has strictly fewer than the recommended one.
