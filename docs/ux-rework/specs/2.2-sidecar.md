## What I found (read this before the Change section)

1. **The "select the text and focus the box" half of "easier copy" already exists.** `gui.create_copy_popup`
   (`scripts/gui.lua:154-162`) already calls `textbox.select_all()` and `textbox.focus()`. The popup text
   (`locale.cfg`, `copy-instructions`) still tells the player to press Ctrl+A first, which is stale. Whether the call
   really takes effect in 2.1 (it runs inside the `on_gui_click` handler of the Copy JSON button, on a `read_only`
   text-box) is **unverified**; only the owner can check it in game. So this item (a) fixes the text, (b) adds a
   "Select all" button as a guaranteed fallback, and (c) names a fix to apply only if the owner's check fails.
2. **There is no clipboard API.** The Factorio runtime docs for 2.1.21 list, for `LuaGuiElement`, only `select_all()`
   ("Selects all the text in this textbox", textfield or text-box only), `select(start_index, end_index)` and
   `focus()` ("Focuses this GUI element if possible"). I found no clipboard member in the class pages I read
   (<https://lua-api.factorio.com/latest/classes/LuaGuiElement.html>, 2.1.21; the second half of that page is
   navigation only), and a forum thread says the Lua API has no clipboard access
   (<https://forums.factorio.com/viewtopic.php?p=454202>, 2019, so not proof for 2.1). I did not read every page of the
   reference. **So no one-click copy is specced.** The implementer greps the docs index once for "clipboard" and
   "copy" before closing this out, and reports the result. If something turns up, stop and tell the orchestrator: it
   is an addition, not a swap.
3. **"Recipe" in Target Output is really the main product's item name.** `trial.ts:166` compares
   `machine.output.item_name` (the recipe's main product) with `config.target_output.recipe`, and the shipped
   Gleba sample targets `rocket-fuel` while its machine runs `rocket-fuel-from-jelly`
   (`gleba/jellynut-processing/jellynut-processing-rocket-fuel.json`). The export therefore has to name the **main
   product**, not the recipe. A recipe name that differs from its product (foundry `casting-iron` makes `iron-plate`)
   would otherwise produce a target the engine can't match.
4. **The number the engine wants is a ceiling-to-aim-below.** `items_per_second` is the total over all copies
   (`target-production-rate.ts`). A clock exists to make a machine idle part of the time, so a target equal to the
   machines' maximum leaves a clock nothing to switch off. The shipped samples target 5 to 10 percent below the maximum
   (logistic science: 240/s against a maximum of about 252/s). The plan still says "its max rate", so that is what is
   exported, but **2.1 must word the pre-filled number as "up to X/s: lower it to what you need"**, not as a
   recommendation. Raised as a checkpoint concern below.
5. **There is no Lua runtime on this machine and no Lua test suite in `clock-generator-sidecar/`.** The Lua can be
   exercised only in game. The engine side is fully testable, and that is where the one rule that must stay identical in
   two languages (the final-product rule) is made testable: the engine has its own implementation of it, used for
   exports from older mods, and the Lua mirrors it.
6. **The mod portal's long description is not carried by the upload API.** `.github/workflows/publish-sidecar.yml`
   uploads only the zip. The upload API documents only `init_upload` and `finish_upload`
   (<https://wiki.factorio.com/Mod_upload_API>). The portal page for 0.7.0 today shows only the `info.json`
   `description` as its summary and has no long description. So the long description is **pasted by hand by the
   owner** on the mod's portal page ("Edit"), and the repo keeps the text.

## Change

What the player sees and does differently:

- **The export carries a suggested target.** After pressing Copy JSON the text has an extra top-level key,
  `suggested_target`, naming the product that leaves the selection and what the selected machines make of it together
  at their maximum. A selection with no such product (no machines, or machines that feed each other in a circle) leaves
  the key out.
- **The window shows it too.** Under "N entities selected" a line reads, for example, "Suggested target:
  [icon] Transport belt at up to 3.00 per second". The owner can check the number before pasting anywhere.
- **The copy popup points to the site.** Its text says the JSON is already selected, to press Ctrl+C, and to open
  clock-generator-self.vercel.app and click "Paste from Factorio" there.
- **Easier copy.** The JSON stays selected and focused when the popup opens (already coded, now verified in game and the
  text fixed), and a **Select all** button selects it again if the player clicked away.
- **The mod names the site where players meet it.** `info.json` `description` (the portal summary and the in-game mod
  list) and `homepage` name and link the site. The long portal description is written (in `PORTAL.md`) for the owner to
  paste.
- **The site accepts the new key and is unaffected by its absence.** Pasting an export with `suggested_target` yields a
  validated suggested target; pasting an older export yields one worked out from its machines (same rule); pasting
  anything else yields none. The paste dialog does not show it yet: 2.1 reads it (see "The field, for 2.1").

## The field, for 2.1

The export gains one optional top-level key. Its shape is exactly the config's `target_output`:

```json
{
  "sidecar_version": "0.8.0",
  "suggested_target": { "recipe": "transport-belt", "items_per_second": 3, "copies": 1 },
  "machines": [ ... ], "drills": { ... }, "inserters": [ ... ], "belts": [ ... ], "chests": [ ... ]
}
```

- `recipe`: the **item name of the main product** (a string such as `"transport-belt"`, `"rocket-fuel"`,
  `"iron-plate"`), which is what `target_output.recipe` holds. Not necessarily the name of the machine's recipe.
- `items_per_second`: a positive number. The total the selected machines of that recipe make at their maximum, with
  their speed and productivity as exported. A ceiling: see finding 4.
- `copies`: always `1` from the mod. Whoever selected a block of repeated copies selected one.
- The key is **absent**, not `null`, when the mod found no final product.

What 2.1 receives on the site side, with no parsing of its own:

```ts
// clock-generator-ui/src/worker/types.ts, on PastedEntities
suggested_target: Option<SuggestedTarget>;

// clock-generator/src/config/suggested-target.ts, exported from 'clock-generator/browser'
interface SuggestedTarget {
    target: TargetProductionRateConfig;   // { recipe, items_per_second, copies }, validated by the config schema
    source: "mod" | "inferred";           // "mod": the export carried it; "inferred": worked out from the machines
}
```

`Option` is the repo's `Option` (`{ _tag: "None" } | { _tag: "Some", value }`), as for `guidance`. The state reaches
`ConfigImportExport.tsx` as `pendingImport.suggested_target`. **2.1 does not parse JSON and does not re-implement the
inference**: it only reads this and decides how to show it. It should treat the pre-fill as applicable only when the
player keeps "Machines" ticked in the import dialog (the target describes those machines).

## The final-product rule (one rule, two implementations)

Same wording in `suggested-target.ts` (reference, tested) and `scripts/suggested-target.lua` (mirror). Both work on the
exported machines only (not drills, not belts or inserters), so they agree even though the Lua also sees the game.

1. Group the machines by recipe name. A recipe that is unknown, or has no item product (a pure fluid recipe), is
   skipped.
2. `main(r)` is the recipe's **main product**: the non-fluid product with the largest expected amount per craft
   (amount, or the middle of `amount_min` and `amount_max`, times its probability); the first wins a tie. This is
   `recipe-metadata.ts:fromRecipe`.
3. Recipe `r` is **intermediate** if some other recipe `r2 != r` in the group has an ingredient named `main(r)`
   (items and fluids). By-products are ignored: a by-product being consumed does not make a recipe intermediate. A
   recipe that consumes its own product (the pentapod egg) is not made intermediate by itself.
4. The **final** recipes are those that are not intermediate. If none is (a circle), there is no suggestion.
5. If several are final, take the one whose machines make the most of their main product per second in total; on an
   exact tie, the one whose main product's name sorts first (names are ASCII lowercase with dashes, so Lua's `<` and
   JS's `<` agree, and it does not depend on the order the game lists the selected entities in).
6. `recipe` = `main(r)`; `items_per_second` = the sum, over the machines with that recipe, of
   `crafting_speed / energy * ((amount - ignored) * (1 + productivity / 100) + ignored)`, where `amount` is the main
   product's amount per craft and `ignored` is its `ignored_by_productivity` (0 when absent). This is
   `machine.ts:createMachine` (lines ~124-155) word for word, including that it does **not** weigh the main
   product's probability: the number must equal the "Output rate" the site's machine facts show for that machine.
   (`productivity` is the percent the mod already exports, research included, capped at 300.) `copies` = 1.

Worked examples (assembling machine 2, speed 0.75, no modules, no productivity research):

| Selection | Final | Number |
|---|---|---|
| one machine on `iron-gear-wheel` (0.5 s, 1 gear) | `iron-gear-wheel` | 0.75 / 0.5 * 1 = 1.5 |
| gear machine feeding a machine on `transport-belt` (0.5 s, 2 belts, takes 1 gear) | `transport-belt` | 0.75 / 0.5 * 2 = 3 |
| one gear machine and one `copper-cable` machine (0.5 s, 2 cables), unconnected | `copper-cable` | 3 beats 1.5 |
| foundry on `casting-iron` | `iron-plate` (not `casting-iron`) | foundry speed / recipe time * amount |
| only inserters and chests | none | key left out |

## Files

### Engine

1. **`clock-generator/src/config/suggested-target.ts`** (new). Exports:
   - `interface SuggestedTarget` (above).
   - `parseSuggestedTarget(raw: unknown): Option<TargetProductionRateConfig>`: `TargetProductionRateConfigSchema`
     with the `recipe` required to be non-empty, run with `safeParse`. **Anything invalid gives `None`; it never throws
     and never blocks the paste**: the key is a hint. Unknown extra keys inside it are ignored (zod's default).
   - `inferSuggestedTarget(machines: readonly MachineConfiguration[]): Option<TargetProductionRateConfig>`: the rule
     above. Uses `FactorioDataService.findRecipeOrThrow` (catch: an unknown recipe is skipped), `RecipeMetadata`
     (`fromRecipeName(...).output` gives `main(r)`, `.raw.ingredients` the ingredients; note `findRecipeOrThrow`
     drops fluid ingredients and fluid results, so fluid names never match, which is fine since a fluid cannot be the
     main product) and `Machine.computeMachineFacts({ recipe, productivity, crafting_speed, type,
     energy_consumption_bonus, fuel })` for each machine, summing `output_rate_per_second`. Do not copy the formula;
     the facts function is the one the site already shows. A machine whose facts throw is skipped.
   - `suggestedTargetOf(raw: unknown, machines: readonly MachineConfiguration[]): Option<SuggestedTarget>`: the mod's
     field if `parseSuggestedTarget` accepts it (`source: "mod"`), else the inference (`source: "inferred"`), else
     `None`.

## PORTAL.md (the long description, for the owner to paste on the portal page)

```markdown
Copy a Factorio build as text for the **Clock Generator** website: <https://clock-generator-self.vercel.app>

The website works out a circuit clock for your inserters, so the build makes the rate you want while its inserters wake
up as seldom as possible, and gives you a blueprint of the clock to place.

## How to use it

1. Press Alt+E (or click the shortcut button) to pick up the selection tool.
2. Drag over the machines, inserters, belts and chests of one build.
3. Click **Copy JSON**. The text is already selected: press Ctrl+C.
4. Open <https://clock-generator-self.vercel.app> and click **Paste from Factorio**.

## What it copies

- machines and furnaces: recipe, crafting speed (with modules, beacons and research) and productivity
- biochambers with their energy consumption bonus, and mining drills with their speed bonus
- inserters: what each takes from and drops into, its stack size and filters
- belts and the items on each lane, and chests
- a suggested target: the product that leaves your selection and how much of it the machines make at most per second

Inserters whose pickup or drop the mod cannot read are listed in the window and left out of the text.

## Notes

- Needs Factorio 2.1.
- Source and bug reports: <https://github.com/abucnasty/clock-generator>
```

The implementer checks every claim against the code (for example that chests and drills are exported, which they are
in `export.lua`) and the portal's markdown dialect (plain markdown: headings, lists, links, bold).

## Tests

No Lua tests exist in `clock-generator-sidecar/` and none can run here (no Lua runtime; the headless harness does not
render GUIs); the Lua is covered by the owner's in-game steps. The engine side, in
`clock-generator/src/config/suggested-target.test.ts` (unit project, game data is loaded by the setup file, as in
`sidecar-version.test.ts`):

1. `parseSuggestedTarget`: a valid `{recipe, items_per_second, copies}` gives `Some` with the same values; each of these
   gives `None` and does not throw: `undefined`, `null`, a string, `{}`, `recipe: ""`, `items_per_second: 0`, `-1`,
   `"3"`, `NaN`, `copies: 0`, `copies: 1.5`; an extra key inside the object is ignored.
2. `inferSuggestedTarget`, with expected values taken from `Machine.computeMachineFacts(...).output_rate_per_second`
   (never from a hard-coded float):
   - one `iron-gear-wheel` machine; two machines of one recipe sum;
   - `iron-gear-wheel` + `transport-belt` gives `transport-belt` (gear is intermediate);
   - an unconnected `iron-gear-wheel` machine and a `copper-cable` machine give the one with the higher rate, and with
     the speeds chosen so the rates are exactly equal, the one whose product name sorts first;
   - a recipe whose name differs from its main product (`rocket-fuel-from-jelly` gives `rocket-fuel`, as the Gleba
     sample does);
   - productivity above 0 and a recipe with `ignored_by_productivity` (the pentapod egg) match the facts function;
   - the shipped samples: for `logistic-science`, `agriculture-science`, `advanced-circuit`, `processing-units-belt-export`
     and `jellynut-processing-rocket-fuel` configs, load the JSON from `resources/config-samples/`, run
     `inferSuggestedTarget(config.machines)` and expect its `recipe` to equal the sample's own `target_output.recipe`
     (this is the guard that the rule agrees with the hand-written targets; `items_per_second` is only expected to be
     at or above the sample's);
   - empty list gives `None`; an unknown recipe name is skipped and does not throw; two recipes that consume each
     other's products (build the case from real recipes if one exists in the data, else drop this case) give `None`.
3. `suggestedTargetOf`: the mod's field wins over the machines (`source: "mod"`, even when it names something the
   inference would not); an invalid field falls back to the inference (`source: "inferred"`); no field and no usable
   machines gives `None`.
4. **Old and new export shapes**, as inline objects shaped like real exports: a 0.7.0 export (has `sidecar_version`,

   one. For each, every machine passes `MachineConfigurationSchema`, `checkSidecarImport(sidecar_version, machines)`

   the `LATEST_SIDECAR_VERSION`), and `suggestedTargetOf` returns `Some`, with `source` `"inferred"` for the first three
   and `"mod"` for the last.
5. The existing `sidecar-version.test.ts` is **not edited** and must still pass (it proves no version moved).

## Risks and checkpoints

- **Checkpoint: the sidecar (2.2).** This item trips the one in `ORCHESTRATOR.md`: the owner runs the steps above before
  the phase merges. The orchestrator must not merge the child PR on CI alone if the owner's check is meant to gate it;
  per the plan's wording ("the agent lists the steps for them to try in the phase PR") the gate is the phase PR.
- **Untestable Lua.** The final-product rule and the rate formula are written twice. A mistake in the Lua passes every
  automated check. Mitigations: the Lua is small and deterministic; the shipped-sample test pins the TypeScript rule; the
  owner's steps 4, 8, 9, 10 pin the Lua to worked numbers; the engine's `source: "mod"` is trusted as given, so a wrong
  mod number reaches the form. That risk is accepted because the site shows the number as editable (2.1).
- **Testing 0.7.0-labelled code.** The owner tries the mod as `0.7.0` (no bump in a phase). The final PR changes only
  version strings and changelog text on top of it. The final PR's checklist should include one more in-game open of the
  built 0.8.0 zip (steps 4 to 6 only).
- **Machine-max target (concern for 2.1).** See finding 4: pre-filling the maximum makes a clock that never sleeps. 2.1's
  copy must say "up to X/s" and tell the player to lower it.

  phase and child PRs publish nothing. Nothing to do; stated so no one is surprised.
- **Old zip in the folder.** `clock-generator-sidecar/clock-generator-sidecar_0.2.0.zip` is an ignored (`*.zip`)
