# 0.24.0: lighter engine, built from components

This is the plan for release 0.24.0: what it is for, its packages in order and what it leaves for later. It is kept while the release is in flight and dropped when 0.24.0 is released. Live status is on the Real Boy board, https://github.com/users/abucnasty/projects/2, item "0.24.0 · Lighter engine, built from components"; this page does not follow every merge. The milestones and follow-ups it names are in [ROADMAP.md](../ROADMAP.md).

## What the release is for

Generating a large build takes a lot of memory, and the engine that simulates it is spread over rules that each name the entity they apply to. 0.24.0 does two things about that, and prepares the ground for the planner of [0.25.0](0.25.0.md).

First, memory. The state transitions of a run are kept in typed columns, one sealed history shared by everything that keeps the run, in place of an object for each transition. What the generator keeps of its runs is trimmed where measurement shows it pays, and the allocation churn of the hottest paths is cut. With the lighter engine, more blast jobs, generation-test workers and spot checks run at once.

Second, composition (#423). Each entity of a build is an archetype chosen by the game's prototype class, never by its name: crafting machine, mining drill, inserter, transport belt or container. An archetype is a fixed set of components (storage, ingress, energy, crafting, yield, placement, mining, hand, belt lane, control and wake-ups). A component owns its state and its behaviour in each tick, and its traits are read from the game's prototype spec. One phase table keeps today's order of a tick. The planner gets its facts from the same traits, as plain data. The refactor comes first and is checked in one verification phase at the end; behaviour changes wait for it.

On top of the facts, the release builds the graph of a build (machines, belt lanes, chests and sinks as nodes; inserters and direct placement as edges; a loop of machines as one node; every terminal output an edge into one shared sink) and a feasibility pass that refuses by arithmetic what cannot be clocked, before any simulation. The traversal planner that plans on the graph is [0.25.0](0.25.0.md).

Done means:

- Memory: the peak memory of every spot-check job is lower than on master, with no job slower; the blast and the generation suite run with more jobs at once than today, with no throttling and no out-of-memory stop.
- Composition: every entity the engine models is composed of components keyed by prototype class, with traits from the prototype spec; no rule is keyed by a name; each per-entity branch that goes is listed with what replaced it.
- Graph: every sample builds its graph from the planner facts.
- Feasibility: what cannot be clocked is refused before simulation, naming the node and the arithmetic; the number of simulated candidates per sample is counted and is no higher than on master.
- No regression: every sample's selected clock is equal or better in the blast against 0.23.0 (verdict, rate, then wake-ups), and any move is explained. Fewer wake-ups may follow but are not the measure.

It advances milestone M4 (stability on real cells).

The goals keep their order ([GOALS.md](../../GOALS.md)): goal 1, the clock meets its target exactly and recovers; goal 2, the fewest wake-ups. Model corrections are reported apart from search-only changes, and search-only changes keep every result identical. The time spent searching at generation does not grow ([working rules](../working-rules.md), rule 6).

Engine and UI are 0.24.0, each with one unreleased changelog entry.

## Packages, in order

Packages are named `0.24/<code>`. One engine change merges at a time; the design pass and the mechanics checks run beside them because they put no load on the engine.

### 1. Memory

**`0.24/memory`**, memory reduction, measured by spot checks. The known slow configurations and every science configuration are generated one at a time on the release and on master, and their time and peak memory compared; the times of a blast are not used, since they are noise. Times are for comparison with each other and depend on the machine. The count of simulated candidates for each job is stated beside them. On the processing-unit sample with a belt export 755 MB is the run memo (raw transition histories, 416 MB of it reason text) and 989 MB the alternatives (two serialized copies of the histories); 0.23.0 shares the text of equal reasons (#433), which lowers its peak memory from 3.10 to 2.65 GiB. In order:

- Transitions in typed columns. Per entity, the tick, the from and to status and the reason, about 10 bytes a transition against 64 to 72. The history is sealed once when the recorded run ends and shared by the memo, every trial and every alternative. The UI receives the columns with a table of reason texts, and the insights, timelines and hover texts read the same as before. Saved results are dropped when the schema version changes.
- The memo keeps no simulation context, only if the context measures above about 50 MB on the processing-unit sample after the columns.
- The memo is bounded by bytes, only if a live memo stays above 300 MB on any spot-check job.
- Allocation churn, one change per allocator: the transfer tracker's snapshots during warm-up and the stock recorder's per-tick work. The other allocators found in the profile of agricultural science (37 GB allocated in 40 seconds) become part of the refactor's per-tick rules, so they are not tuned before it removes them.

Every step keeps the results identical: a full blast with no move and a comparison of the insights, descriptions and histories of all config jobs with master. Done when every spot-check job takes less peak memory than on master and is no slower, with the figures per job.

**`0.24/parallel-runs`**, more parallel test runs, after the verification phase of `0.24/refactor`. The blast's job count is set from the measured peaks of the refactored engine, the guard cap is sized from them, per-job heap flags are used where they pay, and the generation suite is timed again. Done when the blast and the suite run more jobs at once than today with no throttling.

### 2. Two rules, as built

**`0.24/loop-windows`**, wake windows for the inserters of a loop. The inserters that pass items between the machines of a loop, such as the egg inserters between the egg biochambers of agricultural science and the bacteria inserters of iron bacteria cultivation, get wake windows where the clock still holds and recovers with them. 0.23.0 leaves these inserters always on ([wake-ups.md](../wake-ups.md)). Built on an earlier state of the 0.23.0 work, the rule takes agricultural science from 1,258 to 881 wake-ups a minute from the cold start and iron bacteria cultivation from 3,535 to 516, at a generation time of 1.6 to 1.9 times. Done when it is rebased onto the release, the selection of the loop builds is checked in the blast, the scaffold pins of agricultural science are recorded again if its selected clock moves (0.23.0 judges under every order the game may serve), and the texts a player reads are decided. Its rules later become the behaviour of the loop node.

**`0.24/start-mean`**, clocks of a loop compared by their mean wake-ups. On a build with a loop of machines the wake-ups depend on where the clock is when the build starts: a clock settles into another steady state from another start point. The clocks of such a build are compared by their average over 12 start points, and the result shows the average beside the count from the cold start. Built on the same earlier state, it adds 40 to 58% to generation on the four loop builds. Done when it is rebased onto `0.24/loop-windows` and the release, the stacked generation time of both is stated, and the texts a player reads are decided.

### 3. Design, components and the refactor

**`0.24/design`**, a design pass, with no engine code, beside `0.24/memory`. It writes down: the graph model; the facts a component gives and the traits that bound them (throughput bound, hand size, timing, blocks, behaviour); how each of today's strategies maps onto a branch or a shared node of the graph, which become rules, which stay as fallbacks and which go; how the periods of branches compose (one main counter, branch periods that divide it, deciders merged across branches); which refusals move to the feasibility pass; and what it deletes, in files and lines. It is checked against every sample with the stored results of the blast, on paper, and it is reviewed before the planner facts are written.

**`0.24/refactor`**, the composition refactor (#423), on its own branch cut after the two rules above are in. Archetypes by prototype class and components that own their state and their behaviour in each tick, as the section above says; the traits are read from the game's prototype spec, and the input types are generated from its prototype API. One phase table keeps the order of today's tick and its same-tick rules. The mode machines, transition evaluators, pickup and drop logic and status plugins become component methods. The clock's enable controls stay as the planner builds them, held by a control component. A hand picks up and drops through ports, and a placer (a machine or a drill that puts its result in front of it) places through the same ports, so that a new kind of target is a new port. Status strings in histories, the UI, the recorder and the comparison stay as they are.

The refactor is a series of small commits, each passing the unit tests, the type check, the lint, the check for unused code and a replay check: every sample's stored selected clock is run through the simulator with no search, and what every entity holds and shows is compared per period with the base. The full blast, the generation tests and the game checks wait for the verification phase.

The planner facts (each component's traits as plain, serializable nodes and edges) are written right after the traits are built, and the graph and the feasibility pass are built beside the rest of the refactor. They merge after it.

Done when every entity is composed as stated under Done means, and the verification phase passes.

**Verification, once.** After the last commit of the refactor: the full blast, the comparison of insights, descriptions and histories, the generation tests on CI, the game smoke test, the spot checks and the UI checks. A move is traced by bisecting over checkpoints (after the traits, and at several points of the refactor). Then the refactor merges.

**`0.24/graph`**, the graph builder. From a config it builds the nodes, the edges, the loops condensed into one node each and the terminal edges, from the planner facts. Done when every sample builds its graph (a snapshot per sample is kept in the tests) and the blast is unchanged.

**`0.24/feasibility`**, a pass over the graph by true-maximum capacities. A pass linear in nodes and edges checks necessary conditions only: each node's capacity against its share of the rate, and the smallest cut between the sources and the terminal edges against the required rate. A capacity is the entity's true maximum, never a planned figure: an inserter always on with its real hand size and swing, a machine at its speed and productivity, a belt lane at its throughput. A refusal here must be sound, so a check that is only usually true belongs to ranking or planning, not to refusal. The structural traps that are refused one by one today (grouped takers of several results that can deadlock, a silo recipe that traps results, a recycler fed several items) move here, and the text of "why not stable" can name the node and the arithmetic. Done when every refusal that was made before is made, earlier and with its reason, and any new refusal is explained and checked against the simulator.

### 4. Mechanics checks

**`0.24/mechanics-checks`**, the rules of the game that the planner's facts rest on and the game has not checked ([rules-of-the-game.md](../rules-of-the-game.md)). Ten of the rules are of high priority. Each gets one short check in the game, and three of them need a new scaffold. Two more checks go with them. The first is a native record of the inputs of the original electromagnetic science scaffold (#100): the electronic and advanced circuits and the supercapacitors, counted in the game as they move. The second is the order in which the game serves inserters that take from one machine when both hold part of a hand ([simulator.md](../simulator.md#two-inserters-that-take-from-one-machine)): part-hand contests are recorded on more builds, and then the rule "slept first, served first" is modelled if the records show it, which may restore clocks that the check under every order rejects today. Done when each rule is checked in the game and its result is in the docs, the planner facts of `0.24/refactor` follow them, and the input records are in the game test of #100.

### 5. Behaviour fixes after the verification

Changes of behaviour are kept out of the refactor, so that its results can be compared exactly. Each is its own change with its own blast, in this order:

- The bulk inserter's full hand from `wait_for_full_hand` (#452). The engine applies the stack inserter's rule to the bulk inserter.
- The known quirks of the simulator that the refactor keeps exactly: a machine drop without a check of its limit; a drill's status that is never written; a machine's copy that loses its window-opening take decider; and the two fallbacks of a belt drop to a lane.

## Decisions before it starts

- `0.24/design`: the review of the design, before the planner facts are written.
- `0.24/refactor`: whether the inserter part of the refactor ships in this release or in the next, decided at the midpoint of the refactor with its figures.
- `0.24/mechanics-checks`: each new scaffold is reviewed before it is used.
- `0.24/feasibility`: the texts of the refusals.
- Whether the blast runs in CI, sharded on GitHub runners as the generation tests are, so that it runs off the developer's machine; decided once `0.24/parallel-runs` shows how many blast jobs fit on one machine.
