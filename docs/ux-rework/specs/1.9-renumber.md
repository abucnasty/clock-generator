## Change
- **Delete renumbers.** Removing a machine, inserter, belt, chest or drill renumbers the remaining entities of that kind 1, 2, 3 … by row and
  moves every reference to them along. A link to the entity that was deleted becomes empty ("not chosen"), as it does today.
- **Reorder and delete share one code path** (`renumberKind` + `followRenumber`, below), so they cannot disagree again.
- **The row chip shows the entity's own label**, from its id: "Inserter 3", "Machine 2", "Belt 1", "Chest 1", "Drill 2" (today "#3").
- **One label format in every view the form builds**: `Kind N`, from one function (`entityLabel`). The engine already writes "Inserter 3",
  "Machine 3 (recipe)", "Drill 3 (item)", "Belt 1" in the timelines, transfer history, Insights and Fuel, so those match once the form's
  own views do. The "#" forms (`Inserter #3`, `Drill #2`, `#3`) go.
- **Old saved forms still load.** `next_ids` is dropped when a saved form is read; the ids it has stay as saved.
- Results made before a renumber are not touched here: 1.1's banner already says they are for an older build (the renumber changes the
  config key).

## Design (in `utils/configForm/edits.ts`)
Keep every exported function name and signature (`useConfigForm.ts:124-160` wraps them). Replace the retire machinery with one renumbering path.

1. **`renumberKind<T extends { id: number }>(items: T[]): { items: T[]; idMap: Map<number, number> }`.** Gives item `i` the id `i + 1` with
   `{ ...item, id: i + 1 }` (spread, so `_uuid`, `_forced_always` and any other field stay). `idMap` holds **every kept entity**, old id to new
   id, including the unchanged ones. If two entities share an id (an invalid imported file), the first wins in the map.
2. **`reorderWithIdReassignment`** (`:32-48`) keeps its job (move, then renumber) by calling `renumberKind`; it returns the same `{ items, idMap }`.
3. **`followRenumber(prev: ConfigFormData, kind: EntityKind, idMap: Map<number, number>): ConfigFormData`** (replaces the three copies of the
   `remap` blocks in `reorderMachines/Belts/Chests` and the machine-only branch of `removeMachine`):
   - `kind === 'machines'`: map `source`/`sink` ends with `type: 'machine'` and every drill `target.id`;
   - `kind === 'belts'`: ends with `type: 'belt'`; `kind === 'chests'`: ends with `type: 'chest'`;
   - `kind === 'inserters'` or `'drills'`: nothing refers to them; return `prev`.
   - Mapping rule, one for delete and reorder: `idMap.get(id) ?? UNSET_ID`. A reference to the deleted entity is not in the map, so it
     unsets itself; `UNSET_ID` (0) stays 0. **This also unsets a reference to an id no entity had** (a form that was already inconsistent).
     Today reorder leaves that id as is, and after a renumber it could silently point at a different entity. Spread the end (`{ ...end, id }`)
     so `near_lane` stays on a kept belt; an unset end is exactly `{ type, id: 0 }` (no `near_lane`), as the existing belt test expects.
4. **The five removes** (`removeMachine :113`, `removeInserter :176`, `removeBelt :216`, `removeChest :290`, `removeDrill :368`): take the
   entity out, `renumberKind` the rest, put the list back, then `followRenumber`. An index that is out of range (or `removeDrill` without
   drills) returns `prev` unchanged. No `next_ids`.
5. **The four reorders** (`reorderMachines :515`, `reorderInserters :530`, `reorderBelts :535`, `reorderChests :547`, `reorderDrills :559`; only machines, belts and chests have references to follow)
   call `followRenumber` instead of their own copies. Their results are unchanged for a consistent form (the existing reorder tests pass
   untouched).
6. **Delete** `retireId` (`:26-30`), `unsetInserterEndsAt` (`:53-65`, now covered by the `?? UNSET_ID` rule; keep `UNSET_ID`), and every
   `next_ids:` line. `nextId` (`:21-24`) becomes `Math.max(1, ...items.map((item) => item.id + 1))` and stays exported (`inserterFix.ts:3`).
7. **Not changed:** `addX`, `mergeX`, `replaceX` (a paste/import supplies its own ids), `switchChestType`, `updateX`. Importing a config or
   pasting from Factorio does **not** renumber (see Decisions).
