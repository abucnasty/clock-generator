## What is wrong today

- **A6 (blocker), B21, C10.** When the build is not ready, Validate is disabled with no tooltip
  (`WorkflowBar.tsx:133-140`), and Generate's tooltip says "Validate the configuration first" (`:141`) even when Validate
  is disabled too, so the two buttons point at each other. Nothing says what is wrong. The only explanation is the
  `MissingInserterAlert` (`App.tsx:404-407`, `:434-437`), which exists only on Configure, and Import does not switch to
  Configure (`ConfigImportExport` calls `onImport` and stays on Results). On a broken build seen from Results there is no
  clue at all (shots 04, 33, 34).
- **The reasons are hover-only.** Generate's tooltip sits on a `<span>` wrapper (`:143`) and the disabled button is not
  focusable, so a keyboard, touch or screen-reader user gets nothing (C10).
- **Where the rules live.** `canGenerate` (`App.tsx:267-278`) is a block of conditions with no text. The engine's
  `validateInserterCoverage` (`clock-generator/src/config/inserter-coverage-validator.ts`, returned through
  `useInserterValidation`, `hooks/useInserterValidation.ts:14-37`, as `InserterCoverageIssue[]`, shape in
  `clock-generator/src/config/errors.ts:141-155`) gives `{ kind: 'missing_input_inserter' | 'missing_output_inserter',
  machine_id, recipe, item_name, fix_options }`. `useInserterValidation` returns **null until the first check has come
  back**, and `canGenerate` waits for that (`checkedCoverageIssues?.length === 0`).

## Change

- **One pure function lists what blocks the build.** It reads the same conditions as `canGenerate`, in this order, and
  gives each problem a sentence and a place to go (the table below). `canGenerate` is rewritten to use it, so the button
  and its explanation cannot disagree.
- **The disabled buttons say why, in three places that agree:**
  - A tooltip on disabled Validate and disabled Generate (mouse hover).
  - **Visible text** in the workflow bar, on its own row under the buttons: the first problem as a text button, in the
    error colour. This is what keyboard, touch and screen-reader users get. Both disabled buttons are linked to it with
    `aria-describedby`.
  - The Validation panel's own grey-out note ("Fill in the target, the machines and an inserter for every ingredient
    and output first.") is replaced by the same sentence.
- **Clicking the text (or the chip) goes to the problem.** It switches to Configure (and to the List, for the two
  problems that are only editable there) and moves keyboard focus to the field or row, scrolled into view.
- **An "N problems" chip** (red, "1 problem" when there is one) in the workflow bar on **both** views. It is a button that
  does the same as the visible text for the first problem.
- **The Validate step is explained too.** When the build has no problems but Generate is still off, the visible text says
  why: "Validate the build first" (nothing checked yet), "The build changed since the last check. Validate again", or
  "The last check failed. See Validation for why" (this last one goes to the error in the Validation panel). These are
  next steps, not problems: they are not counted in the chip and Validate stays enabled.
- **After Import Config, Paste from Factorio (when something is replaced) and Reset, the page switches to Configure.** The
  player lands where the chip and the text are. It does not steal focus or scroll: the coverage check answers a moment
  later.
- **Not changing:** Copy, the stale banner (1.1), the header layout (1.2), the `MissingInserterAlert` buttons, the
  Validation panel's Validate button, the diagram.

### The problems, in order, and where each one goes

Order matches the conditions in `canGenerate` (so the first problem is the first condition that fails today), then the
coverage issues in the order the engine returns them.

| # | Fails when (`config` is the form data) | Text (named constants, one module) | Focus target (`FocusTarget`) | Element it focuses |
|---|---|---|---|---|
| 1 | `target_output.recipe` is empty | `Set the recipe in Target Output` | `target-recipe` | the Recipe input of `TargetOutputForm`, id `target-recipe` (**add**) |
| 2 | `target_output.items_per_second <= 0` | `Set Items per Second in Target Output to more than 0` | `target-rate` | the Items per Second input, id `target-items-per-second` (**add**) |
| 3 | `target_output.copies <= 0` | `Set Copies in Target Output to 1 or more` | `target-copies` | the Copies input, id `target-copies` (**add**) |
| 4 | `machines.length === 0` | `Add a machine` | `add-machine` | the "Add Machine" button, id `add-machine` (**add**). List only |
| 5 | one problem **per machine** with an empty `recipe` | `Set the recipe of Machine {id}` | `machine-recipe` + `machineId` | that row's Recipe input, id `machine-recipe-{id}` (**add**). List only |
| 6 | one problem **per coverage issue**, `kind: 'missing_input_inserter'` | `Machine {machine_id} has no inserter bringing in {item_name}` | `coverage-issue` + the issue's `kind`, `machine_id`, `item_name` | the issue's row in `MissingInserterAlert`, id `coverage-issue-{kind}-{machine_id}-{item_name}` (**add**, `tabIndex={-1}`) |
| 7 | the same, `kind: 'missing_output_inserter'` | `Machine {machine_id} has no inserter taking {item_name} out` | same | same |

Notes on the table:

- **Why focus the issue's row, not its first fix button.** Each row has "Add to Belt 1", "Add New Belt", "Use Infinity
  Chest" buttons that change the build. Focusing one would put a build-changing action one Enter away. The row gets
  `tabIndex={-1}`, so it takes focus and a screen reader reads "Machine 1 (…): missing output inserter for …"; Tab then
  reaches the fix buttons. The alert exists in both the List and the Diagram view (`App.tsx:404-407` and `:434-437`), so
  coverage problems never need the List.
- **Why #4 and #5 need the List.** Their fields exist only in `MachinesForm`; the diagram edits machines in a dialog. The
  owner's decision is that the List is the main editor, so `goToProblem` sets `configView` to `'list'` for these two and
  leaves the Diagram alone for every other problem.
- **#1-#3 are not hidden in the diagram.** `TargetOutputForm` is rendered above the List/Diagram toggle
  (`App.tsx:350-358`) in both views.
- **Item and machine names.** Items print as their ids ("logistic-science-pack"), as the plan's example does and as
  `MissingInserterAlert` does. The in-game names come with 2.8. Machines print as `Machine {id}`, the same label the
  alert uses; 1.9 makes id equal position.
- **`copies <= 0` cannot be reached from the form today** (the field falls back to 1), but it is a `canGenerate`
  condition, so it stays a problem.
- **Machines with an empty recipe produce no coverage issue** (the engine skips them), so #5 and #6-#7 never double up.
- **Not a problem:** the check still pending (`useInserterValidation` returned null), a generation running, or a Validate
  running. See "Why a button is off" below.

### Why a button is off: `blockedActionsOf`

The workflow bar needs one `Problem | null` per button. Rules, top to bottom, first match wins:

| Inputs | Validate | Generate |
|---|---|---|
| a generation is running (`isRunning`) | none (label reads "Generating...") | none |
| there are problems | the first problem | the first problem |
| the coverage check has not answered yet (`coverageChecked: false`) | `Checking the build…` (no target) | same |
| `validationStatus` is `running` | none (label reads "Validating...") | none |
| `validationStatus` is `none` | none (enabled) | `Validate the build first` (no target) |
| `validationStatus` is `out-of-date` | none | `The build changed since the last check. Validate again` (no target) |
| `validationStatus` is `invalid` | none | `The last check failed. See Validation for why`, target `validation-error` |
| `validationStatus` is `valid` | none | none |

Text that has no target is shown as plain grey text, not a button. `isRunning` is first because both buttons are off for
that and say so on their own label.
