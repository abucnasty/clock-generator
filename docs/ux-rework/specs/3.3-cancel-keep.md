## Why it is wrong today

- **A run can't be stopped (B18, N42).** There is no cancel anywhere: `useSimulationWorker` exposes no stop
  (`hooks/useSimulationWorker.ts:24-83`), and the header's progress row is only the bar and its text
  (`components/WorkflowBar.tsx:315-319`). A deeper search ("can take several times longer", `utils/deeperSearch.ts:15`)
  holds the page until it ends.
- **Even the existing "drop" doesn't stop the work.** `clearResults` (Import, Paste, Reset) only forgets the run
  (`useSimulationWorker.ts:415-418`: "the running generation's later answers no longer match it"). Every worker keeps
  computing its task, so the next Generate queues behind dead work (spec 1.1, Risks: "Real cancelling belongs to the Phase
  3 … item"). An engine error in one task does the same to the others (`:299-306`).
- **Copy shows mid-run, and the pick moves under it (B18).** The bar renders Copy as soon as the first clock arrives
  (`WorkflowBar.tsx:182`, `{blueprintString && (`), with the plain "Copy blueprint" label (`App.tsx:514`,
  `copyBlueprintLabelOf` has no running case, `utils/rateWarning.ts:65-76`). Each later clock re-runs the selection
  (`useSimulationWorker.ts:197-202`), so the clock a player copied can stop being the selected one with nothing said.
- **Regenerating drops the pick (B11, B#9).** `runSimulation` resets the selection and forgets the player's pick
  (`useSimulationWorker.ts:385`, `:389` `userSelectionRef.current = null`), so after a tweak and Generate the clock being
  compared is gone; Search deeper and the belt "Generate again" do the same (`App.tsx:357-368, 459-469`).
- **Nothing survives a reload (B11).** Clocks, selection, pick rule and searches all live in hook state
  (`useSimulationWorker.ts:147-177`); only the form is saved (`hooks/usePersistedConfigForm.ts:138-145`). A reload costs a
  full Generate.
- **Undo of an import brings back the build, not its clocks (B#12, N44).** Import, Paste and Reset clear the results
  (`App.tsx:452-455`); their Undo restores only the form, and says so (`App.tsx:393-402` passes `resultsCleared`;
  `utils/undoSnapshot.ts:14` "Build restored. The clocks you had generated were cleared; click Generate…", `:94-105`).
- **The stale banner can't say what changed (B#3, N12).** It names only the recipe and rate
  (`utils/resultsStaleness.ts:46-54`), which still match after any other edit, has no time and no button
  (`components/StaleResultsBanner.tsx`), and is an MUI `Alert` with the default `role="alert"` (ledger: "the stale
  banner's role=alert … consider dropping the live role"). The Copy-old dialog says the same (`StaleCopyDialog.tsx:32-35`).
- **A worker crash sticks (ledger, 1.1 and 2.3).** `onerror` (`useSimulationWorker.ts:328-348`) records a crashed check as
  `invalid` (`:333-336`), so the next Generate goes to that error instead of retrying (`utils/checkThenGenerate.ts:81-83`,
  `invalid` → `go-to-check-error`); only Check only or an edit retries. The crashed worker is never terminated or
  replaced: it stays in `workersRef` and gets the next plan.
- **A new worker would mis-handle early requests.** The worker handles `initialize` asynchronously (`await import(…)`,
  `worker/simulation.worker.ts:27-42, 302-308`); a `plan` or `validate` that arrives first runs with `clockGenerator`
  undefined. Today nothing posts early (the page waits for the pool), but replacing a worker mid-session would.

## Picks

### Pick 1: what Cancel stops, mid-check and mid-generation

**Cancel replaces the workers doing work that is being thrown away (terminate, then start a fresh one in the same place);
the others keep running idle. What stays on screen follows one rule, `afterCancel`.**

| | Terminate and replace the busy workers (picked) | Drop the run, let workers finish (today's `clearResults`) | Cooperative flag (`SharedArrayBuffer` + `Atomics`) |
|---|---|---|---|
| Stops at once | Yes | No: a deeper search keeps every core busy for minutes | Yes, at the engine's next check |
| Next Generate | Starts at once (requests wait in the new worker until it has loaded the data, ~0.2–0.5 s; the 1.5 MB game data text is already fetched, `worker/engineClient.ts:10-26`) | Queues behind the dead tasks | At once |
| Cost | A small gate in the worker (`worker/requestGate.ts`) | None | COOP/COEP headers in `vercel.json` (deploy config: an owner checkpoint) and engine hooks in every long loop |

**Mid-check** (Generate's check stage; only Generate's check shows Cancel, see below):
- the check is dropped: its promise resolves `dropped` (`PendingChecks.dropAll`), a late answer matches no request (the
  request id is bumped, as `clearResults` does at `:432`), so Generate stops silently (`afterCheck` → `stop`);
- the check state goes back to what it was before the check started (a passed check for this build stays passed, its swing
  plan stays in Advanced), not to `none`;
- worker 0 (the one that plans and checks) is replaced; nothing else changes: no results were touched, the view stays.

**Check only gets no Cancel.** Its checks take 20–40 ms (`capture/lib.mjs:42-44`), it never moves the page (2.3), and a
progress row that appears and goes in a blink would shift the header twice. The plan's "Cancel beside the progress"
holds: Check only has no progress row. Generate's check stage shows the row because
the row stays for the generation after it.

**Mid-generation** (planning or tasks): every worker running a task, and worker 0 while it plans, is replaced. Then
`afterCancel({ runKey, clocksMade, previous })`, first match wins:

| # | When | Results show | Announced |
|---|---|---|---|
| 1 | The results on screen before this Generate were for the same build (`previous.key === runKey`) and complete (not stopped) | Those results again, with their pick (a cancelled Search deeper or regenerate loses nothing) | "Stopped. Your earlier clocks are back." |
| 2 | At least one clock arrived | The clocks made so far, marked **stopped**, selection as it was | "Stopped. The clocks made so far are kept." |
| 3 | Something was on screen before | That, as it was (stale or not; the banner follows from its key) | "Stopped. Your earlier clocks are back." |
| 4 | Otherwise | "Nothing generated yet" | "Stopped. No clocks were made." |

A stopped run's Results show one line (`RunNotes`): "You stopped this run early, so not every clock was tried. Generate
again to try them all." Copy is normal then (the run is over; the clocks are real clocks for this build).

**Build replaced mid-run** (Import, Paste, Reset): the same stop (workers replaced, `afterCancel` computed), then the
result is set aside for Undo (Pick 4) and the screen is cleared as 1.1 built.

**Errors and crashes stop the run the same way.** An engine `error` from one task replaces the other busy workers. A
worker `onerror` once started replaces that worker; a check it was running ends `invalid` with `crashed: true`, and
**Generate retries a crashed check** instead of going to its error (closes both ledger follow-ups).

### Pick 2: what "Copy current best" means

**While a generation runs, Copy stays (as today) but reads "Copy current best"; copying pins the copied clock as the
player's pick.** It is never the filled button while running (2.7's `nextStepOf` names Generate while `isRunning`).

- Label precedence: stale ("Copy old clock…") > running ("Copy current best", with 1.14's suffix when the best so far is
  below target: "Copy current best (192/s, below target)") > 1.14's labels. Tooltip while running: "More clocks are still
  being made. This copies the best one so far."
- It copies the selected clock's blueprint, the one the card and the bar's "Selected clock" name.
- **Copying pins that clock** (as a click on its row does), so a better clock arriving later doesn't silently replace the
  selection the player copied; the card then offers 1.6/2.5's "Back to recommended". Announced: "Copied the best clock so
  far: {label}. It stays selected."
- Why not hold Copy back until the end: a deeper search can run for minutes, and Cancel then Copy would be the only way to
  get a working clock out early; the pin removes B18's real risk (the copied clock silently stops being the selected one).

### Pick 3: the storage key, size limits and eviction

**IndexedDB, native API, no dependency.** Database `clock-generator-results`, version 1, its own (3.4 keeps builds in
`localStorage` for the `storage` event; a separate database means no shared upgrade path and no chain edge). Two object
stores, both `keyPath: 'key'`:
- `entries`: one small row per kept generation, read whole (`getAll`) when the page opens and mirrored in memory, so every
  "is there a record for this key" is synchronous;
- `records`: the generation itself, read one at a time.

**Key = the config key the clocks were made for**, `generatedFor.key` (`configKeyOf` of the form's export,
`utils/resultsStaleness.ts:28-30`; for a one-run Search deeper it is the form's key, not the engine's,
`utils/deeperSearch.ts:43-57`). The full string, not a hash: it is exact, needs no `crypto.subtle` (unavailable on a plain
`http://` LAN address), and a config is a few KB. A newer complete generation for the same key replaces the older one; a
**stopped** generation never replaces a complete one for the same key (`shouldReplace`).

**What a record holds:** `generatedFor` (now with `generatedAt`), `alternatives` (the `ClockAlternativeView[]` as shown),
`pickRule`, `skippedSearches`, `searchedDeeper`, `stopped`, `lean`. Not the log, not the check result, not the view or
tab. The entry holds `schema`, `appVersion`, `savedAt`, `shownAt`, `bytes`, `stopped` and the pick (`{ id, label } |
null`).

**Size limits** (constants in `utils/resultsCache.ts`, estimated, not measured, so they cost nothing at save time):

| Limit | Value | What happens |
|---|---|---|
| `RECORD_BYTES_CAP` | 16 MB | Over it, the record is saved **lean**: the four developer histories (`transferHistory`, `stateTransitionHistory` emptied to `{ total_duration_ticks, entities: [] }`; `clockOnly…` set to `null`). Still over: not saved (kept in memory for this session only). |
| `TOTAL_BYTES_CAP` | 64 MB | After a save, the least recently shown entries are evicted until the total fits. |
| `MAX_KEPT` | 10 | After a save, the least recently shown beyond 10 are evicted. |
| Quota error | | On `QuotaExceededError`, evict the least recently shown one and retry, until only the new record would be left; then give up quietly (`console.warn` once). |

Eviction never removes the record being saved or the one on screen. `estimateKeptBytes` counts 2 bytes per blueprint
character, 100 bytes per transfer, transition and Factorio-state entry in the histories, and 2 KB per clock; the
implementer logs the estimate next to `new Blob([JSON.stringify(record)]).size` once for LOGISTIC and the largest sample
that generates, and adjusts the factor if they differ by more than 2x (in `EVIDENCE.md`).

**Discarded on open:** entries whose `schema` is not `RESULTS_SCHEMA_VERSION` (bump it when `ClockAlternativeView`
changes shape; 2.5 A adds install facts to it) or whose `appVersion` is not `__APP_VERSION__` (a release may make
different clocks; showing old ones as fresh would be wrong).

**When IndexedDB is missing or fails** (no `indexedDB`, `open` errors, or is `blocked` for 3 s): an in-memory store with
the same interface. Undo, build switches and restores work for the session; a reload keeps nothing. No message: nothing
the player can act on. The connection closes on `versionchange`, so another tab can upgrade.

### Pick 4: restoring the results and the pick

**One function, `restoreResultsFor(key, mode)`, decides what comes back; it runs on load and whenever Results is empty.**

`keyToShow({ currentKey, mode, entries, dropped })`, first match wins:
1. a kept entry for `currentKey` → that record, fresh;
2. the record set aside by the last build replacement (`dropped`), if `dropped.formKey === currentKey` → that record as it
   was on screen (fresh or stale by its own key): this is **Undo of Import, Paste or Reset bringing the clocks back**
   (N44), including a stopped run, and it needs no IndexedDB;
3. `mode === 'load'`: the entry shown most recently (`shownAt`) → that record, **stale** (the banner, "Copy old clock…");
   this is "the build changed, then the page was reloaded": the screen is as it was;
4. nothing.

When it runs:
- **On load:** once the saved form is loaded and the store is open; the page's loading state waits for it (it is ready
  well before the workers in practice; the store's 3 s guard bounds it). Not announced.
- **When Results is empty** (no clocks, not running) and the build's key changes: an Undo of a replacement, opening a
  build file whose clocks are kept, editing back to a kept build after a Reset. Mode `replace` (rules 1–2). Announced:
  "Your clocks for this build are back. Selected clock: {label}." A restore that resolves after a Generate, an edit or
  another restore started is dropped (a `latest` token).
- Results that are on screen are never swapped for others by an edit (stale ones keep their banner).

**The pick** (`{ id, label }` of the clock the player chose; null = follow the recommendation):
- **Kept across a regeneration** (Generate, Search deeper, the belt "Generate again", an edit then Generate) when a clock
  with that id is made: the selection follows it as rows arrive (the existing `userSelectionRef` path,
  `useSimulationWorker.ts:199-202`).
- **Not made this time:** when the run ends without it, the recommended clock is selected, the pick is cleared, and
  `RunNotes` says "{label}, the clock you picked, wasn't made this time, so the recommended clock is selected." (also
  announced, in place of the plain "Finished generating." message).
- Cleared by Import, Paste and Reset (another build); restored with a record; "Back to recommended" clears it.
- Saved: with the record at the end of a run, and on every pick change after (`entries` only, a small write).

## Change

- While a generation runs, the header's progress row has **Cancel** (grey text) at its end; Generate's check stage shows
  the row too ("Checking your build…") with Cancel. Cancel stops at once and the next Generate starts at once.
- Keyboard: when a run starts and the focus fell to the page (the pressed button turned off), it moves to Cancel. After
  Cancel, focus goes to Generate. When a run ends with focus on Cancel, focus goes to the bar's Copy (or Generate).
- While running, Copy reads **"Copy current best"**; copying it keeps that clock selected.
- After a stop, Results keeps what Pick 1's table says, with a one-line note when the run was cut short.
- Your clock pick survives Generate when that clock is made again; if it isn't, Results says so.
- **Reload shows what was on screen:** the clocks, the pick, the stopped note, and the stale banner if the build had
  changed. Undo of Import, Paste or Reset brings back the clocks too.
- The stale banner (and the Copy-old dialog) say when the clocks were made and list up to three changes ("Since then you
  changed Items per second (240 → 200), Inserter 3 and 2 more."), and the banner has a **Generate again** button.
- A crashed check is retried by Generate; a crashed or failed run stops its other workers.

## Risks and checkpoints

- **No owner checkpoint is tripped as specified.** No new dependency: IndexedDB is a browser API, and its adapter is thin.
  **Owner question (optional):** unit-testing the adapter itself would need `fake-indexeddb` as a devDependency, which is a
  checkpoint. Recommendation: don't; the memory store tests the logic, and the reload criteria test the adapter in Chrome.
- **Storage use.** Up to 64 MB (estimated) per browser for kept clocks, evicted least recently shown first; no UI to clear
  it beyond eviction (Reset doesn't wipe it). Safari deletes site storage after 7 days without a visit; that only loses
  the cache. The orchestrator may want the owner to confirm the budget; recommended as written.
- **Beyond the plan's four bullets:** the banner's change list, time and button (N12), Undo bringing clocks back (N44),
  crash retry and stopping workers on error (ledger), and pinning on "Copy current best". The first two are the Phase 1 end
  retro's PLAN changes for 3.3; the rest are small and the orchestrator can veto. **Split if review gets heavy:** PR A
  "cancel" (Pick 1, 2, crash; files 1–4, 7–12, 27–30) and PR B "keep" (Picks 3, 4, banner; the rest), B stacked on A.
- **Behaviour change to 1.1:** Import of a build whose clocks are kept by key now shows them (fresh, so never a stale
  blueprint). 1.1's capture imports builds never generated, so it still sees "Nothing generated yet".
- **Big records on the main thread.** IndexedDB clones the record when it is put and read; a large build's histories can
  take tens of ms. Saves happen once per run end; pick changes write only the small entry.
- **Version skew.** A `ClockAlternativeView` change without a `RESULTS_SCHEMA_VERSION` bump would restore records missing
  fields; 2.5 A adds install facts. The constant's comment and the code review cover it. App version is 0.9.x for the
  whole rework, so only the schema guards within it.
- **Lean records** have no developer timelines; after 2.5 B they sit behind Developer tools, which will show empty
  timelines for such a record. Acceptable for an expert view (light fixes only); the implementer adds nothing there.
- **Terminate races.** Messages from a terminated worker may still be delivered; the run id and request id checks ignore
  them, as `clearResults` relies on today.
- **Cancel during Search deeper with a different build on screen** (rare: edit back to a kept build, Generate, Cancel)
  shows the previous screen, not the kept record for the run's key; `afterCancel` uses only what was on screen.
- **Cross-item API with 3.4** (`resultsCleared` removed from `offerUndo`): see Must follow; the orchestrator writes it
  into both specs before either is implemented.
- **Multi-tab:** two tabs share the database; the last save for a key wins; harmless. 3.4 owns cross-tab warnings.
- **Glossary:** new strings use clock, build, check, Generate; "Copy current best" is the plan's own wording. No new term.
- **Follow-up enabled, not built:** 1.7's "found N fewer wake-ups" after a deeper search can now compare with
  `Generation.previous`; leave it in the ledger.
