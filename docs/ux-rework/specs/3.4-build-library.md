## Why it is wrong today

- **One slot for every build.** The whole form is saved under one key, `STORAGE_KEY = 'clock-generator-config'`
  (`hooks/usePersistedConfigForm.ts:16`), by `saveConfigToStorage` (`:139-145`), on every change (`:197-202`). A player
  with several builds has to keep the others as files.
- **Two tabs overwrite each other without a word.** Both tabs write that one key on every keystroke (`:197-202`). The last
  write wins, and nothing in `src` listens for the `storage` event (no `addEventListener('storage'` anywhere). A tab
  opened on a second build wipes out the first one the moment either tab is edited.
- **Reset deletes the only copy.** `resetConfig` removes the key (`:204-207`). Undo brings the build back while it is
  offered (1.3), but nothing else keeps it.
- **Saved files have machine names.** Export downloads `clock-config-${recipe}-${Date.now()}.json`
  (`components/ConfigImportExport.tsx:91`), for example `clock-config-logistic-science-pack-1739871234567.json`. B20 cites
  this: a folder of these is unreadable.
- **No way to share a build except a file.** The ⋮ menu (`ConfigImportExport.tsx:356-402`) has Paste, Import, Export and
  Reset. Nothing reads `location.hash` (no match in `src`). To show a build on Discord or Reddit, a player attaches a
  JSON file.
- **Undo assumes one build.** Undo writes its snapshot into whatever form is shown (`hooks/useUndo.ts:104-112`,
  `setConfig(outcome.form)`). It withdraws the offer only when the form differs by value (`utils/undoSnapshot.ts:63-71`).
  Once builds can be switched, an offer that outlived a switch would write build A's old form into build B. This item has
  to end the offer on a switch (see "Undo and switching").

## Change

- **Your builds.** A switcher in the app bar, right after the title, shows the current build's name. It opens a menu:
  the builds, most recently opened first, then New build, Duplicate build, Rename build… and Delete build. Every build is
  saved on its own, so editing one never touches another.
- **Nothing to migrate by hand.** On the first load after this ships, the existing single save becomes the first build,
  untouched. A player who never opens the switcher sees no difference.
- **A tab keeps its own build.** Two tabs can each work on a different build. When another tab edits *the same* build, a
  warning says so and offers to load that tab's version.
- **Copy share link** in the ⋮ menu copies a link that carries the build, compressed into the part after `#`. Opening it
  asks first ("Open a shared build?"). The shared build is added as a new build, or takes the place of an empty one, and
  the message offers Undo.
- **Save build file** names the file after the build (`logistic-science-pack.json`).
- Delete build offers Undo. Switching, New build and Duplicate build lose nothing, so they are announced but offer no
  Undo, and they end any Undo offer that was open.

## Pick: library storage shape and migration of the single slot

**Picked: an index key plus one key per build, in `localStorage`; the first build keeps the old key.**

| Key | Where | Holds |
|---|---|---|
| `clock-generator-builds` | localStorage | The index: `{ "version": 1, "builds": [{ "id", "name", "recipe", "createdAt", "openedAt" }] }` |
| `clock-generator-config` | localStorage | The form of the build with id `default` (today's slot, same text and format as now) |
| `clock-generator-build:<uuid>` | localStorage | The form of every other build, in the same format (`serializeConfig`) |
| `<that build's key>.backup` | localStorage | A build that could not be loaded, as `clock-generator-config.backup` is today |
| `clock-generator-tab-build` | sessionStorage | This tab's build id, so a reload keeps the tab on its build |

- `name` is `null` for "named after its target recipe" (see naming below), or the player's name. `recipe` is a copy of
  the build's target recipe, kept so the menu can show names without reading every build. `createdAt` and `openedAt` are
  epoch ms. `openedAt` sorts the menu and picks the build a new tab opens.
- **Migration is an index write, not a copy.** The build with id `default` lives under `clock-generator-config`. When
  the index is missing, `openLibrary` writes an index with one build, `default`, whose `recipe` it reads from the saved
  text if it can (`''` otherwise). The saved text itself is not read into anything new, rewritten or removed. So:
  - nothing can be lost: if the index write fails (storage full or blocked), the next load tries again, and the build
    still loads from the same key as before;
  - the existing load path keeps working: the engine's `saved-config` check, `readSavedConfig`'s migrations, and the
    backup of a build that can't be read (`backUpSavedConfig`, `:117-128`), now with the build's backup key;
  - an older deploy of the site still opens the first build, and the capture scripts that read or seed
    `clock-generator-config` (`capture-copy.mjs:33`, `capture-expert-bugs.mjs:20`, `capture-messages-undo.mjs:54`,
    `capture-renumber.mjs:22`, `capture-first-problem-warning.mjs:70`) keep working on a fresh context.
- **Empty storage** (a first visit): the index gets one build, `default`, named after its recipe ("Untitled build" while
  it has none). Its form is written on the first save, under `clock-generator-config`, as today.
- **A corrupt index** (not JSON, or the wrong shape) is rebuilt from the keys: `clock-generator-config` as `default`,
  and every `clock-generator-build:<id>` that isn't a `.backup`, named after their recipes. Nothing is dropped.
- **An index of a newer version** (`version` > 1: a newer site wrote it, and this tab runs a cached older page) is read
  for the fields version 1 knows, and is never written by this page.
- **Saves.** Every change is written to the current build's key only, and skipped when the text equals what is already
  there (one less `storage` event and write). The index is written only when a build is added, removed, renamed or
  opened, or when its target recipe changes, never on an ordinary edit.
- **Storage full.** A failed save shows one warning ("This browser's storage is full, so your latest changes are not
  saved. Delete builds you no longer need, or save this one to a file.") and stays quiet until a save succeeds again.
- **Which build a tab opens:** this tab's `clock-generator-tab-build` if the index still has it; otherwise the build with
  the latest `openedAt`.

Rejected:
- **One key holding every build:** each keystroke would rewrite all of them (tens of kB times the build count), and
  every edit in any tab would raise a `storage` event for every build.
- **IndexedDB:** it has no `storage` event, so the other-tab warning would need a `BroadcastChannel` as well. Its reads
  are async, while the first load reads the slot synchronously today (`usePersistedConfigForm.ts:156`). The builds are
  small (see the measurements below). 3.3 uses IndexedDB for results, which are big and keyed by config, not by build;
  the two don't meet.

## Pick: other-tab warning via the `storage` event

- One `window` `storage` listener in `usePersistedConfigForm`. The browser fires it only in the *other* tabs of this
  origin, never in the tab that wrote. `classifyStorageEvent` (pure) sorts each event:
  - `event.key` is this tab's build key, and `newValue` is not `null` and differs from what this tab last wrote or
    loaded: **changed elsewhere**;
  - the same key with `newValue === null`, or the index key no longer listing this tab's build: **deleted elsewhere**;
  - the index key otherwise: **index changed**. The menu re-reads the index, so a rename, a new build or a delete in another
    tab shows up without a reload;
  - `event.key === null` (another tab cleared storage): re-read the index, and treat this tab's build as deleted
    elsewhere if it is gone;
  - anything else is ignored. That includes the `.backup` keys and another build's key: two tabs on two different builds
    never warn.
- **Changed elsewhere** raises one message, through `notify`: severity `warning`, `durationMs: null`, text "This build was
  changed in another tab. Your next edit here will save over that change.", and action **Load the other tab's version**.
  After 1.5 F every message is announced once through the polite region, so this one is too, with no `role="alert"`.
  - **Once per episode.** The other tab saves on every keystroke, and a new message replaces the current one. Replacing an
    Undo message ends its offer (`useUndo.ts:97-98`). So the warning is raised only when the episode starts.
    Later events only update the stored text the action loads. The episode ends when the warning is closed, its action is
    used, this tab saves an edit of its own, or this tab opens another build. A new episode needs the other tab to save
    again after that. Pure: `nextConflict(state, event)`.
  - **Load the other tab's version** is a replace of the current build, so it is undoable like Import:
    `offerUndo('Loaded the version from the other tab.')`, then the form is set from the stored text. The text goes through
    `readSavedConfig` and the engine's `saved-config` check first. If the check fails, the error is shown and nothing
    changes.
- **Deleted elsewhere** shows a warning with the default duration: "This build was deleted in another tab. It is still
  open here, and your next edit saves it again." The next save writes the key and puts the build back in the index.
- Rejected: syncing silently (the form would change under the player's cursor, and the plan asks for a warning); a lock,
  where one tab owns a build (a crashed tab would hold it forever).

## Pick: share-link format, versioning and size

**Format:** `{origin}{pathname}#build=1.{data}`.
- `1` is the format version.
- `{data}` is base64url without padding, of the `deflate-raw` bytes, of the UTF-8 of
  `JSON.stringify({ name, config })`:
  - `name` is the build's own name, or `null` when it is named after its recipe. The receiver then names it in their own
    words, with 2.8's game names;
  - `config` is `formDataToConfig(form)`, the same object Save build file writes (`exportableConfig`), compact.
- **Why the hash:** the browser never sends it to the server, so no server or CDN limit applies, nothing lands in Vercel's
  logs, and Vercel serves `index.html` as for any visit. Chat apps that fetch a link preview don't see the build either.
- **No new dependency.**
  - The page compresses with `CompressionStream('deflate-raw')` and decompresses with `DecompressionStream`. Both are
    built into Chrome and Edge 103+, Firefox 113+ and Safari 16.4+ (all from 2023), and into Node 21.2+. CI runs Node 24,
    so Vitest runs the real code.
  - base64url is `btoa`/`atob` over a byte string, built in chunks, with `+/` mapped to `-_` and `=` stripped.
  - TypeScript's `DOM` lib already in `tsconfig.app.json` has the types.
  - Where `CompressionStream` is missing, Copy share link and opening a link show "This browser cannot make or open share
    links. Update it, or use Save build file."
  - A library such as lz-string or fflate would only add browsers from before 2023, and it is a new dependency, which
    is an owner checkpoint. Not recommended.
- **Versioning:**
  - A version above 1 reads "This share link was made by a newer version of the site. Reload the page, then open the
    link again."
  - A version that is not a positive integer, or is 0, is treated as broken.
  - A later format bumps the number, and this decoder keeps reading version 1 forever.
  - The build inside is checked like a file: `readConfigFile` (its chest migration) and then
    `askEngine({ kind: 'config-file' })`. Older builds are migrated, and a broken one is refused with the engine's
    message. So the link version covers only the wrapper (compression and the `{ name, config }` shape), and the build
    format keeps one versioning path.
- **Size, measured** (all 48 builds in `clock-generator/resources/config-samples/`, Node 25, this exact encoding; the
  decoded text was checked equal to the source each time):

  | Build | JSON as saved | Compact JSON | deflate-raw | base64url `{data}` |
  |---|---|---|---|---|
  | `intermediates/processing-units/processing-units-belt-export.json` (largest: 6 machines, 12 inserters, 3 belts) | 4,700 B | 2,589 B | 503 B | **671 chars** |
  | `science/utility-science/utility-science-direct-insert-lds.json` (worst ratio) | 3,982 B | 2,241 B | 555 B | 740 chars |
  | Median of the 48 | | | | 514 chars |
  | The largest ×5 (30 machines, 60 inserters; repeated rows compress unusually well) | | 12,496 B | | 1,210 chars |

  - The prefix `https://clock-generator-self.vercel.app/#build=1.` adds 49 characters, so every sample makes a link under
    800 characters. `gzip` would cost 24 more characters than `deflate-raw`; `encodeURIComponent` of the raw JSON would be
    3,700 to 4,400 characters.
  - The real samples compress 4.2 to 5.1 times. So a 60-inserter build with distinct rows (about 12.5 kB compact) would
    make a link of about 3,000 to 4,000 characters.
- **URL limits:**
  - Browsers are not the constraint. Chromium accepts URLs up to 2 MB, and Firefox and Safari take far more than these
    links.
  - Chats are. Discord allows 2,000 characters a message (4,000 with Nitro), and Reddit 10,000 a comment. So:
    - **Above 2,000 characters**, the link is still copied, with a warning instead of the success message: "Share link
      copied. It is {n} characters long, too long for some chats (Discord allows 2,000). Save build file is the safer
      way to share this build."
    - **Above 64,000 characters** (`MAX_LINK_CHARS`; about 20 times the biggest real build), no link is made: "This build
      is too big for a share link. Use Save build file to share it." A link that long is refused when opened, as too big.
  - Decompression stops past 1,000,000 bytes (`MAX_JSON_BYTES`; the largest sample is 2.6 kB). This guards against a
    crafted link that inflates to gigabytes.
- **Copying:** the link is encoded when the ⋮ menu opens (it takes milliseconds), so the click calls
  `navigator.clipboard.writeText` with a ready string, inside the click's user activation. If it isn't ready yet, the
  click awaits it first, which Chromium and Firefox allow. If `writeText` is refused, a small dialog, "Share link", shows
  the link in a read-only `TextField`, focused and selected, with "Your browser did not let this page copy. Copy the link
  below:" and a Close button. Copy share link is disabled when `config` is `null`, as Save build file is.
- **What a link reveals:** the build and its name, to anyone with the link. The menu item's message says so ("Anyone who
  opens it gets a copy of this build.").

## Pick: opening a link, with a confirm and Undo

- **When:** once the page is initialized (workers up, saved build loaded), for the hash it was opened with, and on every
  `hashchange` (a link pasted into the address bar of an open tab).
  - The hash is read once at start-up, and removed at once with `history.replaceState(null, '', pathname + search)`. A
    reload doesn't ask again, and the address bar doesn't keep showing a build that may since have been edited.
  - Hashes other than `#build=` are left alone.
- **Decoding** (`useSharedBuildLink`, async): `readShareHash` → `decodeShareData` → `readConfigFile` + `askEngine({ kind:
  'config-file' })`. Any problem gives one error message, through `notify`, and nothing else happens:
  - broken, cut short, not base64url, not deflate, not JSON, or the wrong shape: "This share link is broken or was cut
    short, so nothing was opened. Ask for the link again.";
  - a newer version: the message above;
  - too big: "This share link is too big to open.";
  - the engine refuses the build: "The build in this share link has a problem, so nothing was opened: {message}".
- **The confirm**, `OpenSharedBuildDialog`, title "Open a shared build?":
  - the build's name (or its recipe name), then one line: "{recipe} at {rate}/s · {copies} copies · {n} machines,
    {n} inserters, {n} belts, {n} chests" (rates printed with `utils/numberText.ts`, counts with `countOf`, zero counts
    left out);
  - then either "It is added to Your builds as a new build. {current name} stays as it is." or, when the current build
    is blank (2.1's `isBlankBuild`) and has no name of its own, "It takes the place of your empty build.";
  - Cancel (`color="inherit"`) and **Open build** (`variant="contained" color="secondary"`, `autoFocus`). Escape cancels.
  - After either button, focus goes to the build switcher (the dialog had no opener).
- **Open build:**
  - `offerUndo(\`Shared build opened: {name}.\`, { revert })`, with no `resultsCleared` (see "Cross-item API with
    3.3");
  - then the library adds the build (or puts it in place of the blank one, which keeps the id), named as in the link, and
    opens it;
  - then `handleBuildReplaced()` (clears the clocks, goes to Configure).
- **Undo** takes the shared build out (or puts the blank form and its old name back) and reopens the previous build. The
  offer ends as every Undo offer does, including when a check or generation starts (1.5 F).
- **Why a new build instead of replacing the current one** (as Open build file does): the library exists so builds are
  not lost. A link someone else sent should not cost the player their own build after the Undo offer ends at the next
  edit. A blank build is replaced, so a newcomer who opens a link doesn't get an empty "Untitled build" next to it.

## Undo and switching

- `useUndo`'s `offerUndo` gains an option `revert?: (snapshot: ConfigFormData) => void`. When it is given, Undo (the
  button and Ctrl/Cmd+Z) calls it instead of `setConfig(snapshot)`. It is used by Delete build and Open build (a shared
  link), whose Undo must change *which* build is open, not only the form.
- **Opening another build ends the Undo offer** (`withdrawUndo()`, which 1.5 F adds). That covers the switcher, New build,
  Duplicate build and the reopening after a failed load. Opening another build replaces the form, which the owner's rule
  already treats as an edit ("the next edit"). Without the explicit call, `settleUndoEntry` would end it only when the
  forms differ by value (`undoSnapshot.ts:63-71`). With `_uuid`s in the form they nearly always do, but the rule
  shouldn't hang on that. No announcement: the player's own action ended it, as with a check (1.5 F).
- The two undoable actions that open another build (Delete build, Open build) make their offer just before acting and
  do **not** call `withdrawUndo`, since their own offer replaced any earlier one.

### Cross-item API with 3.3 (orchestrator decision)

3.3 (`spec-3.3-cancel-keep.md`, Files 17-19 and its Must follow row for 3.4) removes `resultsCleared` from `offerUndo`.
With 3.3, the clocks set aside when a build is replaced come back on Undo (its `keyToShow`), so the "clocks were cleared"
note goes. The signature, copied verbatim from 3.3's spec:

> `offerUndo(message, options?: { restoredLabel?; …3.4's revert })` has no `resultsCleared`; a switch only calls
> `handleBuildReplaced()` after replacing the form, and its Undo and a switch back bring the clocks back by key (rules
> 1–2 of Pick 4). Whichever lands second drops the option.

So the full options type, once both have merged, is `{ restoredLabel?: (form: ConfigFormData) => string | null; revert?:
(snapshot: ConfigFormData) => void }`. 3.4 adds `revert`, and 3.3 removes `resultsCleared`.

- **3.4 never passes `resultsCleared`.** Not for Delete build, Open build (a share link), Load the other tab's version, or
  any switch. Every path that replaces the form only calls `handleBuildReplaced()` after the form is replaced.
- **Either may merge first:**
  - **3.4 first:** 3.4 uses today's signature without passing `resultsCleared`. The option is optional, so today's
    `offerUndo` accepts that, and it leaves the option in `useUndo.ts` for 3.3 to remove. Until 3.3 lands, Undo of a
    Delete build or Open build restores the build but not its clocks, and no "clocks were cleared" note follows. That is
    accepted for the gap, and 3.3 then brings the clocks back by key with no change to 3.4's calls.
  - **3.3 first:** the option is already gone, and 3.4's calls compile as written.
  - Either way, 3.4's `useUndo.ts` change is the `revert` option only, which doesn't touch `resultsCleared`. A merge
    conflict there is two separate lines in the same options type and the same `undo` function, resolved by keeping both.

## Risks and checkpoints

- **For the orchestrator to confirm (not owner questions):**
  - A link opens as a **new build**, or in place of a blank one. It never replaces a build the player made, so
    "imports it with a confirm and Undo" holds without risking their work.
  - Opening another build ends the Undo offer. That reads the owner's "next edit" as covering a replaced form; see "Undo
    and switching".
  - The first build keeps `clock-generator-config` as its key. That is the safest migration (nothing is copied or
    removed), at the cost of one special case in `buildKey`.
  - New storage keys: `clock-generator-builds`, `clock-generator-build:<id>` (and their `.backup`), and the
    sessionStorage key `clock-generator-tab-build`. 2.1 listed a new localStorage key as a checkpoint candidate.
  - Save build file's new file name (B20 cites the old one).
- **Owner checkpoints:** see "Owner decision needed" below.
- **Not checkpoints:** no new dependency, no CI or release change, no `.claude` or settings change, no version bump.
- **Merge care:**
  - `App.tsx` and `ConfigImportExport.tsx` are touched by 2.1, 1.5 F, 2.5, 2.7 and 3.3. Rebase on the phase head, find
    code by name, and don't re-indent untouched blocks.
  - `useUndo.ts` changes only inside 1.5 F's `useMemo` and `undo`.
- **Two tabs on one build by default.** A new tab opens the most recent build, so two tabs often share one. The warning
  is the designed answer. A duplicated tab copies sessionStorage and shares the build too.
- **The other tab saves on every keystroke,** so `storage` events are frequent. `nextConflict` raises once per episode,
  so this tab's Undo message isn't replaced over and over. The test and the capture's "with an Undo offered" step guard
  it.
- **The form and its id must change together.** One `{ id, form }` state stops the save effect from writing build A's
  form under build B's key. A capture step checks every key after a quick switch-and-edit.
- **Delete is immediate.** Closing the tab during the Undo offer makes it final, as every Undo here does (no timer).
- **The engine checks each build when it opens.** A build that a newer schema rejects is backed up under its
  `.backup` key with today's message, and the switch doesn't happen.
- **Forced flags.** `_forced_always` is not in a link, as it isn't in a saved file (Phase 1 end, N47). An opened link shows
  a forced Always as the player's own, the same as Save then Open build file. That stays a follow-up; 3.4 doesn't widen
  it.
- **Clipboard activation.** The encode is started when the menu opens, so the copy runs inside the click. Safari may still
  refuse after an `await`, so the fallback dialog covers it.
- **Privacy.** A link carries the build and its name. The copied message says anyone with it gets a copy. The hash never
  reaches the server.
- **`check:icons`** scans string literals: test fixtures use recipes with icons, and no sample paths.
- **Model:** opus. The item crosses storage, Undo, the app bar and async flows (ORCHESTRATOR: Phase 3 is opus). It edits 8
  existing files, so it counts as one unit.

## Owner decision needed

   wait for the owner before any copy ships with them. Where they appear:
   - **share link:** the ⋮ item "Copy share link", its messages, and "Open a shared build?";
   - **Your builds:** the switcher's tooltip, its menu heading, and the share dialog's "It is added to Your builds…".

   The README rows (Files 16):
   - **share link**: "A link that carries a copy of a build; opening it adds the build to Your builds." Use instead of
     "permalink", "URL".
   - **Your builds**: "The builds kept in this browser, one per name." Use instead of "library", "saved configs".

   **Recommendation: approve both.** They are plain words, built on the glossary's "build", and players already say
   "share link". If the owner prefers other words, only the constants in `utils/buildLibrary.ts` and
   `utils/shareLink.ts` and the README rows change.
2. **No new dependency, so share links need a browser from 2023 or later.**
   - The links use the built-in `CompressionStream('deflate-raw')`: Chrome and Edge 103+, Firefox 113+, Safari 16.4+.
   - Older browsers get "This browser cannot make or open share links. Update it, or use Save build file.", and
     everything else works, including Save and Open build file.
   - Covering older browsers needs a compression library (lz-string or fflate), which is a new dependency and a
     checkpoint, with lockfiles regenerated with npm 11.19.0.

   **Recommendation: no dependency.** The fallback is only for browsers about three years out of date, and Save build
   file covers them.
